**What Windows is for here.** `fennec-server --file`, the `fennec` shell and the native library (`fennec-ffi`, for an app that keeps its database on the machine): a developer's machine, a desktop app's server, a single-node server on Windows Server. ## 1. The mapped file on Windows

**What the documentation settles.** A section -- Windows' file mapping object -- is made at a size and keeps it: "After a file mapping object is created, the size of the file must not exceed the size of the file mapping object; if it does, not all of the file contents are available for sharing" ([CreateFileMappingW](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-createfilemappingw)). A writable section larger than its file grows the file to its size, "not guaranteed to be zero"; the page grants a read-only one no such growth, and slice 2's test asserts its refusal. So the room Unix maps past a file's end, which the appends grow into and Linux and macOS both show through a mapping made before them (`Mapping::with_room`, [storage.md](storage.md#handover)), has no counterpart in one view. Views of one file are coherent whatever section each came from ("file views derived from any file mapping object that is backed by the same file are coherent", remote files the exception); a view and `ReadFile`/`WriteFile` are, in the same page's words, "not necessarily coherent", no case named. A local file's cached writes go through the one data section a file has, the one every view of it maps, so a view made after a `WriteFile` reads its bytes: the handover rests on that, and slice 2's test holds it, not the documentation. `VirtualAlloc2` reserves a placeholder; `VirtualFree` with `MEM_RELEASE | MEM_PRESERVE_PLACEHOLDER` splits one; [MapViewOfFile3](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-mapviewoffile3) with `MEM_REPLACE_PLACEHOLDER` puts a view of a section in its place -- "*BaseAddress* and *ViewSize* must exactly match those of the placeholder", the size a multiple of the page, and "the 64k alignment requirements on *Offset* and *BaseAddress* do not apply", the offset page-aligned (Windows 10 1803; Server 2016 in the page's table).

**Taken: a placeholder of the file's length and its room, the file's views laid end to end in it.** At an open and after a rewrite, `VirtualAlloc2` reserves the file's length and its room as one placeholder -- `ROOM`'s rule, the file's length again and a gigabyte at the least, address space alone as on Unix -- and the file's pages replace its start as a view of a section made at the file's length (`CreateFileMappingW` with `PAGE_READONLY` and no size, `MapViewOfFile3`), the section's handle closed once mapped, since a view holds its section. A handover past the views (`Sink::written_through`) splits the placeholder where the last view ends and maps there the file's pages from that page to its end, from a section made then: the stores' addresses stay, a reader keeps the pages it touched, and the write lock pays one split, one section and one view, a few system calls. A view's last page holds the bytes past its section's end that later writes fill -- the file's own page, as on Unix, which the next view does not map again since it starts at the following page; whether a view made before those writes shows them is *to be verified* in slice 2 -- it does, CI found ([below](#built-in-slice-2)) -- and if it does not, a view ends at the last page the file filled and the records past it wait for the next handover (whether `Store::hand_over`, which takes runs in order and stops at the first it cannot account for, already leaves them is slice 2's to check). A file outgrowing its room is mapped anew, as on Unix; `Drop` unmaps each view and frees the placeholders left. The calls are declared `extern "system"`, as `lock.rs` declares kernel32's: `VirtualAlloc2` and `MapViewOfFile3` are kernel32.dll's but named by onecore.lib rather than the import library the toolchain links, so they are linked `raw-dylib` (slice 2 settles it on CI: looked up at run time instead, [below](#built-in-slice-2)). A system that refuses `VirtualAlloc2` -- before 1803 -- maps each handover anew (the first alternative below) rather than open unmapped.

**What comes with it.** The open's cut of a torn tail: `SetEndOfFile`'s page asks every view of the file unmapped and its mapping closed first, the refusal otherwise `ERROR_USER_MAPPED_FILE` ("the requested operation cannot be performed on a file with a user-mapped section open"), and `open_mapped_into` maps before it cuts, so on Windows an open that finds a torn tail lets the database and its views go, cuts the file and opens it again -- a crash's tail costs a second open there, nothing else. `fs::open_read_only` maps (one view, no room), as does `SideFile::map`. `touch` asks the pages in with `PrefetchVirtualMemory` (Windows 8), `MADV_WILLNEED`'s counterpart. `Database::maintain` -- `compact` and `create index` beside the queries -- comes with the mapping, as on Unix. The thirty-odd `cfg(all(feature = "std-fs", unix, target_pointer_width = "64"))` naming the mapped path become one name for it, so a reader sees what the condition means and Windows joins in one place.

**What the fallback cost before slice 2, read.** `fs::open` on Windows was `fs::open_in_memory`, the path `--no-mmap` takes elsewhere: a 1 GB file of 2.3 million rows with a hash and an ordered index holds 1 095 MB in the process against 188 mapped, its `compact` peaks at 2 012 MB against 236, and a 10 GB file does not open on an 8 GB machine ([storage.md](storage.md#the-mapped-file), measured where both run); with no mapping nothing is handed over, so every write's documents stay in the heap until a restart or a compact; and with `Database::maintain` mapped-only, a server's `compact` holds the write lock throughout -- at 100 000 x 128 reads waited up to the build's whole ~20 s, against 21 to 30 ms beside it ([storage.md](storage.md#maintenance-beside-the-database)). The 1 GB case on Windows itself is owed to a Windows machine ([below](#built-in-slice-2)).

Rejected:

- *A view made anew at each handover* (`CreateFileMappingW` and `MapViewOfFile` over the whole file, calls Windows 7 has): the old view torn down at each handover -- under the write lock unless handed to a thread -- and every page a reader touches faulted again through the new view, a soft fault each since the pages are shared and nothing is read from disk: a 1 GB working set is 262 144 faults after each handover, and a handover comes every 16 MB, 65 536 records or 16 384 writes. Kept as the fallback where placeholders are refused, and as what slice 2 measures them against.
- *ntdll's sections* (`NtCreateSection`, `NtMapViewOfSection` with a reserved view larger than its section, how LMDB maps on Windows without growing its file): undocumented for user mode, and how such a view follows a file that grows is the kernel's behaviour, not a contract.
- *A writable section larger than the file*: grows the file on disk, zeros not promised, where a file's length is its records' -- a torn tail is cut by it, a replica is sent by it.
- *`MapViewOfFileEx` at an address just freed*: another thread may take it between the free and the map, the race placeholders were made to close.
- *Handing over less often on Windows*: the memory the handover exists to give back.

**Tested on Windows CI** (slice 2, as designed; what was built follows): the seven files of fennec-core's tests then `cfg(unix)` for the mapped path -- `mapped.rs`, `handover.rs` (the file and a checkpoint the same byte for byte), `pinned.rs`, `prepared.rs`, `spill.rs`, `limit.rs`, `autocompact.rs` -- and the gated tests of `alter.rs` and `persist.rs`; and new ones: a record written after a view and read through the next across the page the two share; a torn tail cut by the second open; a file outgrowing its room mapped anew; a thousand handovers' views, and a rewrite mapping the file again in one. Measured on a Windows machine rather than the runner, whose neighbours make its timings noise: the handover's hold of the write lock against macOS's (1 ms for 16 MB of 768-dim documents), the faults readers take after one (none expected), and the 1 GB file's memory, mapped and not.

### Built in slice 2

**The mapping** (`fs/windows/map.rs`, #521). Windows' `Mapping` answers the calls a Unix's does -- `of`, `with_room`, `cover`, `AsRef<[u8]>` -- so `FileSink`, `open_mapped_into`, `open_read_only` and `SideFile::map` are the Unix code, and the thirty-odd conditions of the mapped path say `any(unix, windows)` where they said `unix` -- each spelled out still, not the one name the design asked for (below). `with_room` reserves the placeholder (`ROOM`'s rule, rounded to the 64 KB allocation unit), keeps a handle of the file -- a mapping's one, to make each view's section from, since the sink's goes at a rewrite while a pinned read still holds the mapping -- and lays the file's view at its start; `cover`, under the write lock as a handover asks it, splits the placeholder at the page past the file's end, makes a section and lays a view of the file from the page the last view ended at, the length a reader sees stored after it (`Release`, read `Acquire`). A view's size is the file's bytes from its offset: the page asks for the placeholder's size, a whole number of pages, which `windows-latest` refused past the section's end (5, access denied), as it refused 0 (87), and took the file's length, rounding it to the page and matching the placeholder itself (`a_view_replaces_a_placeholder_at_the_file_s_length`). **A view shows what later writes put into its last page** (`a_view_shows_what_is_written_into_its_last_page`): the next view starts at the following page, and no handover waits for a page to fill. A read-only section asked for more than its file is refused (8, "not enough memory resources"), as the page implies. `Drop` unmaps each view, which frees its addresses, and frees the placeholder left. `VirtualAlloc2` and `MapViewOfFile3` are looked up at run time (`GetProcAddress`), not linked `raw-dylib`: kernel32.dll, the DLL their pages name, does not export them on `windows-latest` -- kernelbase.dll does -- and an import a system lacks keeps a program from starting at all, where a Windows before 1803 should start and map each handover anew; `fs::placeholders` says which, and the server's start line with it. That path, and a file outgrowing its room, are held to a Unix mapping's answers and bytes on CI through `fs::assume_room`, which has a thread's mappings take no placeholder or a room of a few pages.

**What came with it.** A torn tail: `fs::windows::cut_and_open` lets the database and its views go, cuts the file and opens it again as the first open was set up -- a server's leaves its vectors to the linker, the flag read before the load that clears it; another view of the file refuses the cut (`ERROR_USER_MAPPED_FILE`, 1224), and the open fails with it rather than append past the tail, its error naming the view, which the system's words do not: another process's -- a `fennec --read-only` beside a writer that crashed -- or this process's own, a stream or a pinned read still reading the database a storage error stopped when a `--dir` node opens that tenant again, the open failing until they let it go. The second open runs once an open: one finding a tail to cut again fails rather than cut and open again (a thread's flag, `CUTTING`). `open_read_only` and `SideFile::map` map one view and no room; `touch` asks a step's pages in with `PrefetchVirtualMemory`. Decision 3's volume check is `fs::mappable`: a volume with POSIX renames that is no share -- a share known by its device, a network file system's (`NtQueryVolumeInformationFile`'s `FILE_REMOTE_DEVICE`, which the I/O manager answers from the device), or by `GetFileInformationByHandleEx`'s `FILE_REMOTE_PROTOCOL_INFO`, which only a network redirector answers, since a share may name its server's file system and flags as its own -- is mapped; any other, or one that cannot be asked, is read into memory, a server's file and a reader's alike, and the server's start line says how its file is held, once: the line before it, what Windows lacks, says nothing of the mapping. CI holds `mappable` itself, which the mapped path's other tests pass by through `open_mapped` -- had it said no on NTFS, every Windows server would read its file into memory with them green: true on the runner's NTFS and the job's ReFS, false on its FAT32 and through `\\localhost\C$`, the drive's administrative share (`a_file_is_mapped_where_its_volume_allows`). The device is asked first, CI having found the class alone unsure: in one run the redirector refused `FILE_REMOTE_PROTOCOL_INFO` to the handle `fs::volume` opened through the share -- its first, after the file's own open was not found -- and the share was taken for its server's NTFS, read into memory only because SMB reported no POSIX renames; in the next it answered every handle (116 bytes, version 4, SMB's protocol), and the device said remote every time; and a file opened as a server opens it (`fs::open_serving`) mapped on NTFS, read into memory through the share and on FAT32 (`a_server_s_file_is_mapped_on_ntfs_and_read_through_a_share`). `Database::maintain` runs `compact` and `create index` beside the database there as on a Unix, its `.beside` removed before it is made again. `cache::room` is 7j's.

**A mapping's views go beside the write lock.** Each view is an `UnmapViewOfFile` where a Unix mapping is one `munmap`, and the drop that lets the last of a mapping go is a handover's past its room or a rewrite's, under the write lock, unless a pin or a stream holds it on: single small writes hand over every 16 384 (`HANDOVER_DOCS`), 2 MB of 128-byte rows, so 100 GB written into one mapping's room are 50 000 views. A mapping of more than 16 views (`IN_PLACE`) hands them, the placeholders past them and its handle of the file to a thread of its own (`map::Teardown`); fewer -- an open's one -- go in place, as a Unix mapping's do. A cut waits for those threads (`map::unmapped`), since a view one has yet to let go would refuse it (`many_views_are_let_go_of_on_a_thread`). Rejected: a mapping made anew past a count of views -- simpler, but every page a reader touched faulted again through the new view, and the count's teardown still under the lock.

**The one name, not taken.** Stable Rust names a condition only through a build script (`cargo::rustc-cfg`), and slice 2 first gave fennec-core one setting `cfg(mapped)`. Two things undid it. A build script is a dependency of the crate's library, so Cargo's metadata hash of fennec-core moves and the code's layout with it: `fennec-server` for macOS stayed 6 659 728 bytes with millions of them moved -- the same to the byte as main given an empty build script, built from one path into one target directory, so the script alone moved them -- and the browser module compressed 1 byte larger by gzip and 103 by brotli. And `tools/image-cargo.sh` refuses a workspace crate's build script until it holds what each run reads, which cargo tracks by mtime alone (the `deploy` and `monitoring` jobs failed on it). So each condition is spelled out, `any(unix, windows)` in it, and the Unix binaries are main's to the byte. The name is owed to a change that teaches `image-cargo.sh` a build script's inputs and takes the layout's move with it.

**The Unix binaries.** Every Unix-side line is a condition widened in place or a Windows-only line, none moving a line a panic records: `fennec-server --release`, `fennec --profile cli` and the native library for macOS are main's to the byte, built from one path into one target directory. A Windows binary's size, before and after, is in [7l](#7-what-else-windows-differs-in).

**Owed to a Windows machine**, the runner's neighbours making its timings noise: the handover's hold of the write lock against macOS's (1 ms for 16 MB of 768-dim documents) -- a split, a section and a view, against Unix's nothing; the faults readers take after one (none expected: their pages stay mapped); the 1 GB file's memory mapped and read; a thousand handovers' views against a rewrite's one, which CI holds for correctness alone; and a mapping's teardown -- 16 views in place under the lock, and 50 000 on their thread, beside the queries.

## 2. Replacing a file a view still maps

**What the documentation settles.** `SetFileInformationByHandle` with `FileRenameInfoEx`, `FILE_RENAME_POSIX_SEMANTICS` and `FILE_RENAME_REPLACE_IF_EXISTS` will "allow replacing a file even if there are existing handles to it. Existing handles to the replaced file continue to be valid for operations such as read and write. Any subsequent opens of the target name will open the renamed file" ([FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)). std's `fs::rename` takes it since Rust 1.85 ([rust-lang/rust#131072](https://github.com/rust-lang/rust/pull/131072)), falling back to the classic rename where the volume refuses it; #453's CI ran a compact and a checkpoint over a file the server's own handle had open, and every handle fennec opens keeps std's `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`. Deleting a mapped file is refused whichever semantics: "A return value of STATUS_CANNOT_DELETE indicates that either the file is read-only, or there is an existing mapped view to the file" ([FILE_DISPOSITION_INFORMATION_EX](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex)). A running program, its image mapped, can be renamed though not deleted -- what Windows updaters rely on.

**What it does not.** Whether a data view of the *target* refuses a POSIX rename over it -- it does not, slice 1's experiment found, below. The rename's page speaks of handles, not views; `MmFlushImageSection(MmFlushForDelete)`, which a file system asks before it deletes, fails for an image section's views and, by its [page](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-mmflushimagesection), where "there are one or more outstanding write probes on the file's data section"; a file-system developers' thread ([OSR](https://community.osr.com/t/mmflushimagesection-mmflushfordelete-during-rename/53434)) reports NTFS asking it on a rename only where an image section exists. A read-only data view would then not refuse it -- reported, not promised, and #453's sentence "a mapped view would refuse a rename over the file" was its caution, not a measurement.

**Taken: slice 1 settled it by experiment on CI -- (a).** The design held both answers:

- **(a), what Windows did.** A read-only view does not refuse a POSIX rename over its file: every replacement stays std's rename, as on Unix and as on Windows today.
- **(b), not taken.** Had a view refused it: **the retired swap**, kept here as designed for the day a Windows update changes the answer, which fails the experiment's test first. Under `<file>.lock`, the file leaves its name first -- renamed to `<file>.retired-<n>`, which a view of it does not refuse, as a running program is renamed -- then the new file takes the name, which nothing holds, each rename made durable ([decision 3](#3-durability-on-ntfs)). The retired file is deleted when its last view goes (the `Mapping`'s drop asks for it, the path kept beside the view), and an open sweeps what a crash or another process's view left, a refused delete left for the next. A crash between the two renames leaves no file under the name: the open, under the lock and before `FileSink::create` would make an empty database there, puts the newest retired file back -- it holds every write answered, since what was pending at the swap is answered only once the swap is done (`swap_in`) -- and removes the image as a rewrite's leftover. A read-only open, which takes no lock, finding no file names the retired one and opens nothing.

The design had a file a view may map deleted by retiring it first, the documentation saying a delete is refused while a view maps the file. The experiment found otherwise for a read-only data view: on NTFS and ReFS a delete of a file a view maps -- POSIX or classic, std's `remove_file` -- succeeds, its name gone at once, so a tenant's delete and a side file not adopted stay std's `remove_file`; the page's `STATUS_CANNOT_DELETE` is an image section's, a running program's, as the OSR thread reported of the rename. FAT32 refuses it, where nothing is mapped ([decision 3](#3-durability-on-ntfs)'s volume check). The experiment's answer is written here, and its test keeps asserting it, so a Windows update that changes it fails the job rather than a server.

**What Windows did** -- `windows-latest`, Windows Server 2025 Datacenter (10.0.26100), on the runner's NTFS and on a ReFS and a FAT32 volume diskpart made from VHDs in the job (`fs::windows::tests::the_experiment_on_each_volume`). Each operation on a file of its own, against each holder: `ok` where it was done and the names say so -- the new file under the name, or the name gone -- and a view in this process still read the file it mapped; `ok, pending` for a delete whose name stays until the last handle closes; `e<n>` a refusal, its Win32 error (5 access denied, 32 sharing violation, 87 invalid parameter: no POSIX semantics). A view is a section made from the file at its length, `PAGE_READONLY`, mapped `FILE_MAP_READ` whole, its section's handle closed; "its handle closed" closes the file's too. Slice 2's mapping laid in a placeholder keeps one handle of the file for as long as it lives (`Views::file`, each handover's section made from it), so its row is "a view and its handle": std's rename over it is taken, and only `MoveFileEx`, which no path of fennec's calls, is refused (e5); the mapping made whole where there are no placeholders (`Mapping::of`) keeps none, "a view, its handle closed". FAT32 has no POSIX semantics, so std's rename and delete fall back to the classic ones, which a handle refuses -- the sink's own among them, so a checkpoint or a compact there fails, as the server's start says ([decision 3](#3-durability-on-ntfs)) -- and which a view refuses too there, but for a rename of the file away.

Where each replacement is, and what it meets:

- *A rewrite* -- `checkpoint`, `compact` (`rewrite_with`, `swap_in`), an image adopted (`Sink::adopt`, the side file of `Database::maintain`): the database's own file, mapped by its stores, its pinned reads and its streams for as long as they run.
- *`fennec restore --force`, `fennec backup` into a file, `.save`, `fennec unseal`*: under the lock, over a file a `fennec --read-only`, `fennec mcp --read-only` or `fennec types` in another process may map, taking no lock -- the experiment's other-process case.
- *A tenant's install, follow, reclaim and restore on a `--dir` node*: the registry lets the database go first (`RELEASE_WAIT`), but a pin or a stream may still hold its views; its delete retires.
- *The sidecars* -- `.instance`, `.follows`, `<t>.hooks`, `presence` -- and *the archives* (`archive.rs`, `node_archive.rs`): never mapped, so std's rename over handles, as now; their directory syncs become real ([decision 3](#3-durability-on-ntfs)).
- *The sync log*: none on Windows.
- *`<name>~`*: the browser's, in OPFS (`openFile`, [js-client.md](js-client.md#persistence-in-the-page)); the browser's file system API stands between it and NTFS, and nothing here touches it.
- *`.compacting` and `.beside` left by a failed rewrite*: made again with `truncate`, which a view of the old one refuses (`ERROR_USER_MAPPED_FILE`, [decision 1](#1-the-mapped-file-on-windows)); a delete it does not refuse (the experiment), so slice 2 removes `.beside` before it makes it again (`SideFile::create`). `.compacting` is never mapped under its name -- renamed into place, or removed -- and is made as before.

Rejected:

- *Readers dropping their views before a swap*: a pinned read and a stream read with no lock for as long as they run ([engine.md](engine.md#pinned-reads)); a swap would wait on them without bound.
- *A generation's file name*, `<file>` a pointer to `<file>.<gen>`: a database becomes two files, where a backup copies one and `fennec types` reads one -- a format change for one platform.
- *`MoveFileEx` with `MOVEFILE_REPLACE_EXISTING`*: refuses a target open elsewhere (#453), and a refused checkpoint stops every write.
- *Writing the image over the file*: neither atomic nor out of the readers' views.

## 3. Durability on NTFS

**The directory.** NTFS journals its metadata, so a crash leaves a rename done or not, never half; but it writes its log lazily, and a power cut can bring back the name from before -- the file from before a `compact`, without the writes pending at the swap, which the image alone held and which were answered once the swap was done. Subversion's power-cut runs on NTFS (Stefan Fuhrmann, [2015](https://svn.haxx.se/dev/archive-2015-06/0138.shtml)) lost data with no flush after a rename and kept it in 90% of runs with one; the rest is that rig's or NTFS's, unknown. **Taken: `fs::sync_dir` flushes the renamed file, then its directory.** The directory is opened through std with `custom_flags(FILE_FLAG_BACKUP_SEMANTICS)` and write access, every share mode, and flushed (`sync_all`, `FlushFileBuffers`); `ERROR_ACCESS_DENIED` from the open or the flush is taken as nothing to flush, as [Lucene.NET](https://apache.googlesource.com/lucenenet/+/master/src/Lucene.Net/Support/IO/WindowsFsyncSupport.cs) takes it ("like in OpenJDK", its comment says), and any other error is the storage error it is. The renamed file is flushed first -- `swap_in` opens its new handle anyway -- which is what `MOVEFILE_WRITE_THROUGH` ends with (#453): no page says which of the two flushes carries NTFS's log for a rename, so both run, once a rename, never a write. Its open, for write, is refused by a handle that does not share write -- many a reader's -- and by a read-only file: refused so, for sharing once the deadline below is out or for access, it is taken as nothing to flush, as the directory's is, since nothing was written or dropped and before slice 1 nothing was flushed there at all; a reader elsewhere then fails no tenant's create or sidecar's write. Its flush, through a handle that may write, has no such leave: an error there is the file's own, which the sink's next flush would meet, and the storage error it is. `remove_synced` follows, and `node_archive`'s directory sync, `cfg(unix)` today, goes through `fs::sync_dir`. The archive (fennec-http's `Archive`) syncs its directory once for a run of renames -- `put`'s images and `history`, `keep_began`'s `began` -- before the step standing on them, naming a stand-in (`history`) where a Unix fsyncs the directory alone; through `sync_dir` that flushed `history`, renamed or not, and none of the files renamed. So on Windows each `put` and `keep_began` flushes its file again through the handle it wrote it with once it is renamed, and the batched sync flushes the directory alone (`fs::sync_dir_alone`): every renamed file, then its directory, the order `sync_dir` keeps, the directory's flush still one a batch, and the files' one each, as through `sync_dir` it would be. Rejected: *the file's flush alone* (#453's suggestion), of which no page says it carries the directory's entry; *neither*, today's -- NTFS's lazy log.

**The file.** std's `sync_data` and `sync_all` are both `FlushFileBuffers` on Windows: the file's data, its metadata -- the size an append changed -- and the device's cache, unless its owner turned that off (Device Manager's *Turn off Windows write-cache buffer flushing*, which makes every flush a lie, as a disk that ignores `fsync` does elsewhere; the reference page names it). `--sync always` answers after it as on Unix, the fsync after the lock unchanged. `Disk::inherited` holds as it is: a flush is the file's cached pages, whoever wrote them -- the cache is the file's, not the handle's -- so a restart's first durability covers what an earlier process left. Rejected: *`FILE_FLAG_WRITE_THROUGH`* on the database's file, PostgreSQL's default on Windows (`open_datasync`): every write the disk's, the ones `append` makes under the write lock past `WRITE_BUF` among them -- what [buffered writes behind the lock](durability.md#writes-behind-the-lock) exist to avoid; *`NtFlushBuffersFileEx` with `FLUSH_FLAGS_FILE_DATA_SYNC_ONLY`*, `fdatasync`'s counterpart: ntdll's, and an append changes the size it would flush anyway.

**The sync log stays Linux's and Android's.** It may pay on Windows too: an append's flush carries its size through NTFS's log as ext4's `fsync` of a grown file commits its journal -- 356 us against the log's 65 in Docker's VM ([durability.md](durability.md#the-sync-log)) -- and a log of fixed size overwritten in place may not. Measured on a Windows machine -- `FlushFileBuffers` of a growing file against a fixed one's -- and taken only where it wins, with `synclog.rs`'s rules whole.

**The volume.** At an open, `GetVolumeInformationByHandleW` names the file system and its flags. NTFS and ReFS go on; a volume with no POSIX renames (FAT32, exFAT, a network share) opens unmapped, as `--no-mmap` does, and the start says a rewrite there may fail, as one fails there today, loudly ([engine.md](engine.md#single-writer)). The flag is winnt.h's `FILE_SUPPORTS_POSIX_UNLINK_RENAME` (0x400), which the call's own page does not list. It reports it, slice 1's CI found: NTFS's flags 0x03e72eff and ReFS's 0x5fc636cf hold it, FAT32's 0x00020206 does not -- so the flag decides (`fs::volume`, `Volume::posix_renames`), never the name. Built in slice 1: a server says, after `opened:` for `--file` and after `serving tenants from:` for `--dir`, `windows: <path> is on NTFS, whose renames replace a file other handles hold open`, or on a volume without them that a checkpoint or a compact there fails while the file is open and stops the writes; slice 2 opens such a volume unmapped, and a share (`fs::mappable`, [below](#built-in-slice-2)).

**Built in slice 1** (`fs/windows.rs`): `fs::sync_dir` opens `path` -- the renamed file, or a directory -- for write with `FILE_FLAG_BACKUP_SEMANTICS` and every share mode and flushes it, where it is there (a removal's is not) and its open is not refused, then its directory the same way, both opens tried again for sharing within one deadline ([7e](#7-what-else-windows-differs-in)); `swap_in` renames through `fs::windows::swap`, which flushes the file through the handle it opens to append to and then the directory, as a Unix `swap_in` renames, syncs the directory and opens; the archive flushes as above. On the runner a directory's flush was done on NTFS, ReFS and FAT32 alike, never refused. Each rename's two flushes are not measured: that is a Windows machine's, not the runner's ([below](#what-only-windows-settles)). Every line is `cfg(windows)`: `fennec-server` built for macOS is the same to the byte as before it.

**Tested on Windows CI** (slice 1): `sync_dir` on a file, a removed one and a directory answers `Ok` -- flushed, or refused and taken as nothing -- and never another error, and a checkpoint's and a compact's rename is each followed by both flushes, counted under `cfg(test)` as `FSYNCS_HERE` counts a sink's (`a_rename_is_followed_by_both_flushes`); a reader not sharing write, held on the file and then on its directory, leaving `sync_dir` `Ok` with that flush taken as nothing and the other done (`a_flush_another_handle_refuses_is_nothing_to_flush`); `a_durability_covers_what_an_earlier_process_left` on Windows; the volume's name, flags and directory flush on NTFS, ReFS and FAT32, asserted in the experiment's test. The archive's flushes run in no Windows test: fennec-http's suite is slice 4's; the Linux clippy job lints them for the Windows target. A power cut is no CI's: a VM's power-off on a Windows machine, as Subversion ran theirs, before the release ([the owner's ninth decision](#decisions-for-the-owner)).

## 4. Stopping: console events and services

Today the server installs the CRT's `signal` for 1, 2 and 15 (`durability::install_signal_handlers`). On Windows the CRT raises `SIGINT` at Ctrl+C, which reaches the one shutdown; Ctrl+Break is its `SIGBREAK` (21), uncaught, whose default ends the process with no final sync; `SIGTERM` is never raised by Windows, `SIGHUP` is not the CRT's, and closing the console window ends the process at once.

**Taken: `SetConsoleCtrlHandler`, kernel32's, in the CRT's place on Windows,** every console event mapped onto the one shutdown -- `SHUTDOWN` stored, and the syncer's pass within `LOOK` doing the rest as now. The [handler's page](https://learn.microsoft.com/en-us/windows/console/handlerroutine) settles the rest. A handler runs on "a new thread in the process"; Ctrl+C and Ctrl+Break have "no timeout", so their arm stores the flag and returns `TRUE`. For `CTRL_CLOSE_EVENT` -- the console closed, or *End Task* -- returning `TRUE` means "the system terminates the process", and it waits `SPI_GETHUNGAPPTIMEOUT`, 5 000 ms, at most: so that arm stores the flag and waits for the exit the syncer makes, which ends its thread with the process -- the shutdown has five seconds, the final sync what its waits leave of them ([built](#4-stopping-console-events-and-services): it syncs first), and a checkpoint cut short leaves the file whole, as a failed rewrite does, the next open linking again. `CTRL_LOGOFF_EVENT` and `CTRL_SHUTDOWN_EVENT` reach services alone ("Interactive applications are terminated at logoff"), and take the close's arm where they come. Ctrl+Break is the one console event a process can send another -- `GenerateConsoleCtrlEvent` to a process group made with `CREATE_NEW_PROCESS_GROUP`, where Ctrl+C, the page says, cannot be sent to a group, only to every process of the console (CI found otherwise once the server turned it on, [below](#4-stopping-console-events-and-services)) -- so it is a supervisor's `SIGTERM` on Windows and the test harness's. `--exit-on-stdin-close` already works there (a pipe's end is an end of file), the desktop app's way. Exit codes as now.

**Services: wrapped in the first release, natively after it.** A service wrapper that sends Ctrl+C or Ctrl+Break and waits before it kills -- WinSW and NSSM do -- gets the one shutdown; the reference page shows one. A native service mode -- `fennec-server --service`: `StartServiceCtrlDispatcherW`, a control handler taking `SERVICE_CONTROL_STOP`, `PRESHUTDOWN` and `SHUTDOWN` to the flag, `SERVICE_STOP_PENDING` with a wait hint each `LOOK` while the syncer finishes, then `SERVICE_STOPPED` with its exit code, advapi32's calls declared as kernel32's are -- is a slice of its own after the release, when someone runs one ([the owner's fifth decision](#decisions-for-the-owner)). Rejected: *a service with no handler*, which the service manager kills after its timeout, with no final sync.

**Tested on Windows CI** (slice 3): the harness's `terminate()` sends Ctrl+Break to a server started in its own process group, and `shutdown.rs` -- the final sync, the checkpoint, exit 0 -- runs on Windows through it; the Ctrl+C and close arms by a unit test calling the handler as the system would, the close's held until the exit is asked. The harness and its servers must share a console for `GenerateConsoleCtrlEvent`: a runner's step has one, *to be verified* in slice 3, else the harness allocates one (`AllocConsole`).

**Built in slice 3** (#522, `durability/windows.rs`): `install_signal_handlers` is `SetConsoleCtrlHandler` on Windows, the CRT's `signal` never installed there. Ctrl+C and Ctrl+Break store `SHUTDOWN` and are taken; the close, a logoff in a user's session and `CTRL_SHUTDOWN_EVENT` store it and hold the handler (`until_the_exit`, a park) until the syncer's `process::exit` ends its thread, so the exit code is the shutdown's, never the system's. The unit tests call the handler's logic (`answer`) as the system would: Ctrl+C's and Ctrl+Break's flag with no hold and no deadline, the close's, a user's logoff's and the shutdown's deadline and flag stored before the hold and the event taken only once the hold lets go, a service's logoff and an unknown event passed on with neither. Registering the handler is held by the suite: every server a test stops, it stops by Ctrl+Break. *Settled by slice 3's CI*: a runner's step has a console -- the harness had one of its own, `GetConsoleProcessList` listing the server beside it (`the_harness_shares_its_console_with_its_servers`, which prints it) -- so `AllocConsole` is the harness's fallback only, for a process started with none, and `node_archive.rs`' too. `fennec archive` and `fennec import --follow`, which stop between two steps at `SIGINT` or `SIGTERM` (fennec-cli's `stop`), take Ctrl+C and Ctrl+Break through `SetConsoleCtrlHandler` there too: the CRT's `SIGBREAK` left uncaught ended them mid-step, and caught, the MSVC CRT puts a signal's default action back before it calls the handler, so a second Ctrl+Break did. `node_archive.rs` stops its archiver by Ctrl+Break on Windows.

*The budget: synced first.* A close, a logoff and the system's shutdown end the process five seconds after the event, and the shutdown's order spent them before its final sync: `LOOK` (0.2 s) to see the flag, the held requests' grace (`HELD_GRACE`, 2 s), the TLS connections' (`END_GRACE`, 0.5 s), then the `before_shutdown` hooks -- with OTLP tracing a flush of up to 2 s, with `--follow` the mirror's join, up to its `STOP_WAIT` -- 4.7 of the five seconds with tracing on, more with a mirror. Under `--sync <ms>` or `off`, what was buffered and every write acknowledged meanwhile were lost wherever the system ended the process first. **So those three events sync first**: their arm stores a deadline (`DEADLINE`) before the flag, and the shutdown -- a file's (`shutdown`, `windows::sync_first`) and a node's (`Tenants::sync_dirty`, through `before_the_deadline`) -- syncs before the graces and again before the hooks, then runs its final sync and checkpoint as before. What the five seconds cover: every write acknowledged before the event is on disk within `LOOK` and an fsync; a write acknowledged during the graces reaches the disk with the next sync, if the process is still there to make it; a checkpoint cut short leaves the file whole. Ctrl+C and Ctrl+Break, which no timeout follows, keep a signal's order, as on Unix. Not chosen: graces cut to fit, which would answer held requests and end TLS connections more abruptly at every such stop and still not fit the hooks, a mirror's join alone up to five seconds. Tested: `writes_are_synced_first_only_past_a_deadline` (a file's writes left alone with no deadline, synced past one), the arms' deadline in `answer`'s tests; no CI step can close a console or shut the runner down, so the end to end is a Windows machine's ([below](#what-only-windows-settles)).

*Ctrl+C in a group of its own.* `CREATE_NEW_PROCESS_GROUP` turns Ctrl+C off in the group it makes -- `start /b` does the same -- an attribute the group's children inherit, and adding a handler does not turn it back on: a server a harness or a wrapper started in its own group took Ctrl+Break and the close, and a Ctrl+C did nothing. `install_signal_handlers` calls `SetConsoleCtrlHandler(NULL, FALSE)` first, as fennec's `stop` does, so Ctrl+C reaches the handler wherever the server was started; under `start /b` a Ctrl+C at that console now stops the server too, as Ctrl+Break did. `GenerateConsoleCtrlEvent`'s page says a Ctrl+C sent to a group is received by none of it. *Settled by #522's CI*: it is received by the group's processes that turned Ctrl+C on -- `ctrl_c_to_a_servers_group_stops_it_through_the_one_shutdown` sends one to a server's group and the server stops through the one shutdown, exit 0, its `--sync off` write on disk -- so a supervisor may send either; the harness keeps Ctrl+Break, which needs no such step.

*A logoff.* It reaches a service's session at any user's logoff -- an administrator leaving a remote session -- so taking it there would stop a server a wrapper runs as a service each time someone logs off: in session 0, the services' alone since Windows Vista, it is passed on (`ProcessIdToSessionId`, kernel32's), and kernel32's default handler lets a service's own process run on. In a user's session it is that session's end, and **taken as the close is**. This is the JVM's rule: its handler passes a logoff on only where its window station is not visible (`WSF_VISIBLE`) and treats it as the close elsewhere. Its test, though, is user32's (`GetProcessWindowStation`, `GetUserObjectInformationW`), and a process that loads user32.dll or gdi32.dll is taken for a window's, its handler no longer called for a logoff or the system's shutdown (`SetConsoleCtrlHandler`'s remarks): the shutdown's arm would never run. So the server asks its session, and `the_server_loads_no_window_library` asserts on CI that it loads neither, printing the modules it does load: on the runner kernel32, kernelbase, ntdll, ws2_32 and mswsock, advapi32, sechost and rpcrt4, bcrypt, bcryptprimitives and cryptbase, the CRT's ucrtbase, vcruntime140 and msvcrt. *Unverified*: whether a service wrapper's child -- fennec-server under WinSW or NSSM, not itself the process the service manager started -- gets the default handler a service's process gets. If it gets the plain one, a logoff passed on ends it at once, with no final sync -- the case the JVM's `-Xrs` was made for -- and a wrapped server is not safe from another user's logoff until a native service mode ([the owner's fifth decision](#decisions-for-the-owner)) or a run on a Windows machine with a wrapper and a second user settles it.

## 7. What else Windows differs in

- **a. Paths.** std turns a path past `MAX_PATH` into a `\\?\` one itself, so every path stays std's and every Windows call here takes a handle -- `CreateFileMappingW`, `FlushFileBuffers`, `GetVolumeInformationByHandleW`, the rename -- never a path; the directory `sync_dir` flushes is opened through std's `OpenOptionsExt` too. `fs::canonicalize` answers `\\?\` paths, which nothing resolves through (`fs::resolved` does not canonicalize).
- **b. Names.** A tenant's name is `[a-z0-9_-]`, so NTFS's case-insensitive names fold no two together. But `con`, `prn`, `aux`, `nul`, `com1` to `com9` and `lpt1` to `lpt9` are names a Win32 path reads as devices -- with an extension too on releases before Windows 11 -- so `T\con.fennec` is the console. **Taken: refused as tenant names on every system**, so a node's directory and its archive restore on any ([the owner's seventh decision](#decisions-for-the-owner)). **Built in slice 4** (`tenants::check_name`, `tenants::a_device`): the 22 names, in any case and with any extension as the naming page reads them, a 400 naming the rule; a region's, a zone's and a node's names keep the shape alone (`tenants::shaped`), naming no file. The check is one call out of line (`no_device`), the stem lowercased into four bytes and matched: inlined, and split and compared word by word, the first build of it was ~1.9 KB of a Unix `fennec-server` -- `a_device` 852 bytes, and 16 to 100 more in each of the twenty-odd callers `check_name` is inlined into. **A tenant a node on a Unix took under such a name before the rule** -- alpha, none known -- is out of reach once its node is upgraded: no longer listed (`Tenants::names`), opened (400), deleted, reclaimed, archived, nor its hooks file loaded. So no listing skips one silently: `tenants::listed`, which the node's listing, the hooks' load and an archive's lines read a name by, logs the file it passes over, once a process, with the way back -- the node stopped, the file and every file beside it named `<t>.*` renamed by hand, `schedules.hint` removed for the node to learn its schedules again (a hint naming one reads as none, and is learned again once anyway). And no stream fails for one: an archiver passes over a node's tenant named so -- a node from before the rule sends it -- reporting it, rather than refusing the message and ending the stream of every tenant, and a node passes over an older archiver's place for one. The reference page says how to copy one under another name before the upgrade. *Settled by slice 4's CI*, printed by `what_windows_makes_of_a_device_s_name` on Windows Server 2025 (10.0.26100): `GetFullPathNameW` reads every name alone as its device (`\\.\con`) and with `.fennec` as a file; in a directory's full path `nul` is still the device, and every other name, with or without an extension, made a file -- Windows 11's narrowing, where the page has every one a device. A node's paths are full, so on the runner's Windows only `T\nul` would have been no file; the refusal stands for the Windows the page describes, a name alone and a directory carried between systems.
- **c. `fs::resolved`.** `symlink_metadata` and `read_link` answer for Windows' symbolic links, and `is_symlink` is true for every name-surrogate reparse point, a junction among them, which is a directory's and never a database file's; a relative target joins the link's directory as on Unix. A file's link needs the privilege above; `a_file_served_through_a_link_stays_one_file_across_a_compact` runs on Windows from slice 4. A hard link is a name of its own, as on Unix. **Built in slice 4**: fennec-cli's link tests -- a served file through a link across a compact, a node's tenant through one -- fennec-abi's (a file's link absolute, relative, chained and dangling, and a directory's, `symlink_dir`) and `instance`'s run on Windows, each passing over, said, where the privilege is not held; the runner's account holds it, and every link was made.
- **d. Locks and views.** A `LockFileEx` lock is mandatory -- it refuses another handle's `ReadFile` and `WriteFile` in its range -- which is why it is on `<file>.lock` and never on the database's file, whose views and appends meet no lock. Kept so.
- **e. Other processes' handles.** Windows Search's indexer, a cloud folder's sync (OneDrive, Dropbox), a backup agent or an antivirus may open the file without `FILE_SHARE_DELETE`, and a rename over it is then refused (`ERROR_SHARING_VIOLATION`, `ERROR_ACCESS_DENIED`) -- and `swap_in` fails the sink at any error, so every write would stop. **Taken**: a rename refused for sharing, which changed nothing, is tried again for a bounded time -- a second, chosen rather than measured (below) -- before it fails as now; a file fennec makes is marked `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`, its image before the rename; the page says to keep a database out of a synced folder. This is no retried fsync: [a failed fsync is never retried](durability.md#storage-errors) because the kernel may have dropped what it could not write, where a refused rename has written nothing. **Built in slice 1** (`fs::windows::swap`, `tried_again`): std's rename and the open after it are tried again while they answer `ERROR_SHARING_VIOLATION` or `ERROR_ACCESS_DENIED` -- std's rename answers 5 over a handle without `FILE_SHARE_DELETE`, the experiment found, where the POSIX call answers 32 -- waiting a millisecond and twice as long each time up to 50, never past the deadline, then the error fails the sink as before. The deadline is one a call, a second after it begins (`REFUSED_FOR`), shared by the rename, the open after it and the directory's open: two tries' seconds were two seconds under the write lock and the `Disk` mutex. The second is chosen, not measured against a real indexer or backup agent, which no runner has: it is what a write waiting on a checkpoint may wait, and a Windows machine's run with one beside the file may lengthen it. `sync_dir`'s two opens, the renamed file's and the directory's, share a deadline the same way, and refused still, for sharing as for access, take the flush as nothing to flush rather than fail ([decision 3](#3-durability-on-ntfs)). On FAT32, whose rename falls back to the classic one, the refusing handle is the sink's own: tried again for the second, and then failing, as the start line says. `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED` is set through a handle, `SetFileInformationByHandle`'s `FileBasicInfo`, on the database's file as its open makes it and on a rewrite's image before the rename -- advice, a refusal ignored; `CreateFileW` takes no such attribute at the making, CI found. The install page says to keep a database out of a synced folder. Tested on CI: a rename over a file held without `FILE_SHARE_DELETE`, taken once the holder lets go after a refusal (an event: the count of refusals moving), refused once held past the second -- the file and the image as they were -- and through a sink, the rewrite failing it and every sync after (`a_rename_another_handle_refuses_is_tried_again`); a swap's three tries and a `sync_dir`'s two each held to one deadline, and a deadline already out tried once (`one_deadline_holds_every_try_of_a_call`); the attribute read back after an open and a checkpoint (`a_file_fennec_makes_is_not_content_indexed`).
- **f. A view's I/O error** is `EXCEPTION_IN_PAGE_ERROR`, the process's end, as `SIGBUS` is on Unix: a network share opens unmapped ([decision 3](#3-durability-on-ntfs)'s volume check, and the redirector's `FILE_REMOTE_PROTOCOL_INFO`, slice 2's `fs::mappable`) and `--no-mmap` stays the word for any other doubt, as the reference page says now.
- **g. What is keyed by a Unix descriptor.** `conn.rs`' TLS connections, which the one shutdown ends with `close_notify` (`end_all`), and the TLS key's warning (`warn_if_open`), `cfg(all(feature = "tls", unix))`: ported to `AsRawSocket` in slice 3, so a Windows server's shutdown ends its TLS connections with their `close_notify` too, but for the two cases below. `accept::widen` listens again with a longer queue, which Winsock ignores on a socket already listening (its `listen` page: success "without changing the value for the backlog"), so on Windows the queue stays std's -- *to be verified* in slice 3, and named. The router's `Flight::shut` stays the router's ([the owner's first decision](#decisions-for-the-owner)). **Built in slice 3**: the list of open TLS connections keys a socket's `SOCKET` on Windows, through stand-ins for std's descriptor traits (`conn/windows.rs`), the list's code the same on both. Shutting a socket's read side, which on Unix wakes a thread blocked reading it, does not on Windows: a connection waiting for its next request held its thread until the exit cut it with a reset, its client reading no `close_notify` (`every_tls_end_is_a_close_notify_the_shutdown_s_too`, failing on the first run). Its pending I/O is cancelled after the shutdown (`CancelIoEx` on the socket's handle -- std makes every socket overlapped, and a cancel on the list's duplicate reaches the read on the original), the read after it meets the shut side, and the connection ends with its `close_notify`; the test passes on Windows. What does not hold as on Unix: `CancelIoEx(handle, NULL)` cancels every request pending on the socket, not its reads alone -- std's overlapped is not ours to name -- so a send blocked on a slow reader fails too, and an answer in the middle of its write is cut there with no `close_notify`, where on Unix it goes on through the shutdown's grace; and `SD_RECEIVE` on a TCP socket with bytes queued that the server has not read, or that arrive after it, resets the connection (Winsock's `shutdown` page), so a client that had sent more -- a pipelined request, a body the server had not read -- reads a reset, not a `close_notify`. The key's warning stays Unix's until a DACL is read ([7h](#7-what-else-windows-differs-in), slice 4). *Settled by slice 3's CI*: Winsock answers a second `listen` with success and keeps the queue -- of 300 connections made at once to a listener nothing accepts, 128 to 129 queued behind std's `listen` and one more after a second of 1 024, run after run (`listening_again_leaves_the_queue_as_it_was`) -- so `widen` stays Unix's and a Windows listener keeps std's 128, which [http.md](http.md#connections-without-a-thread) names.
- **h. Secrets' files.** `fennec backup`'s key file (`0600`), a tenant's `<t>.hooks` (`mode_private`) and the TLS key's warning read Unix modes; on Windows a file inherits its directory's ACL, which `C:\ProgramData` opens to every user. **Taken** (slice 4): such a file is made, given an owner-only protected DACL (advapi32's `SetSecurityInfo`) and only then written; the TLS key's warning reads its DACL for `Everyone`, `Users` and `Authenticated Users`. **Built in slice 4** (`fennec_http::owner_only`): `fennec key`'s file and a tenant's `<t>.hooks` are opened through std with `GENERIC_WRITE | WRITE_DAC | READ_CONTROL` and shared with no reader (`FILE_SHARE_WRITE | FILE_SHARE_DELETE`: the hooks' sidecar is renamed into its name and flushed by `fs::sync_dir` with its handle open), so no other open reads it meanwhile; given a protected DACL of one entry, the token's user with every right, through that handle; and only then written. A reader whose handle was open before -- on a file there already, a crash's `.hooks.writing` -- keeps what it was granted, as a Unix descriptor keeps its file. The entry names the token's user, not the file's owner: run elevated, the owner is the Administrators group, the token's default, and an owner may rewrite a DACL -- any administrator's reach, as a Unix root's. And what the entry leaves out, another account meets: `fennec restore`, `unseal` or `backup --force` run by an account other than the node's, over a tenant's file, puts its hooks file away (`tenant_hooks::put_away_beside`), which needs `DELETE` on `<t>.hooks` or `FILE_DELETE_CHILD` on the directory -- a folder's Modify grants neither, Full Control the second -- and is refused, the command with it, where a Unix's directory write lets it (the runbook and the webhooks page say so). The TLS key's DACL is read through a handle that may read its security alone (`GetSecurityInfo`): an entry allowing Everyone, Authenticated Users or Users a read, none denying it before, is warned of naming the group, a missing DACL as every user's. The server loaded advapi32 already, and loads neither user32 nor gdi32 since (`the_server_loads_no_window_library`). Rejected: `CreateFileW` given the descriptor at the making -- a path where every call here takes a handle (7a), and a file there already keeps its DACL; `SetNamedSecurityInfoW` after the write -- a reader that opened the file meanwhile keeps its read; a DACL keeping `SYSTEM` and `Administrators` -- a Unix's `0600` keeps no group, and an administrator takes ownership where one must. Tested on CI: a secret's file refused to a reader while it is made (32), owner-only once restricted, renamed and made again over an older file (`a_secret_s_file_is_its_owner_s_alone`); `fennec key`'s file (`a_new_key_is_its_owner_s_alone`) and a tenant's hooks file read back owner-only; whom an ACL's bytes open a file to (`a_dacl_says_whom_a_file_is_open_to`); a key Everyone may read warned of, an owner-only one not (fennec-server's `a_key_open_to_others_is_warned_of`). *Settled by slice 4's CI*: a file the runner's temporary directory gives is open to none of the three groups -- its user's profile -- where `C:\ProgramData` grants Users a read.
- **i. The lease's clock.** `lease::now` reads the boot clock -- `CLOCK_BOOTTIME`, `mach_continuous_time` -- so a suspended primary does not wake believing its lease. On Windows `QueryInterruptTimePrecise` (kernel32, Windows 10) is that clock: interrupt time counts sleep and hibernation, where `QueryUnbiasedInterruptTime` leaves them out. **Built in slice 4** (`lease/windows.rs`): looked up at run time in kernel32.dll, then kernelbase.dll, as the mapping's calls are -- its page names kernel32.dll and Mincore.lib, an import library the toolchain does not link -- and `Instant` throughout where neither exports it, before Windows 10. *Settled by slice 4's CI*: kernelbase.dll exports it, kernel32.dll does not, as with `VirtualAlloc2`; the clock's test holds it between the unbiased count, which never passes it, and `GetTickCount64`, the milliseconds since the system started, within a second: 235 435.8 ms on the runner against 235 434.9 and 235 421.
- **j. The page cache's room.** `cache::room`: `GlobalMemoryStatusEx`'s available physical memory, the standby list among it as Linux's `MemAvailable` counts the cache, and a job object's limit where the process is in one -- a container's. `cache::faulting`: Windows counts a process's faults soft and hard together (`GetProcessMemoryInfo`), with no count of the ones that waited for the disk, so it answers `false` there and `CompactPolicy::memory` fires on the room alone. `SideFile::past_cache` takes no advice on Windows: no call keeps a buffered write out of the cache, and `FILE_FLAG_NO_BUFFERING` asks for sector-aligned writes the image's writer does not make. Built in slice 2 (`cache.rs`'s Windows `imp`), `the_room_is_some_of_the_machine` held there too: a job's limit bounds the room rather than being subtracted from it, a job charging what its processes commit and not the file's cached pages, so a container's process compacts as one held to its memory would.
- **k. The shell.** Its `pending()` -- a paste's lines read as one -- polls stdin on Unix and answers `false` elsewhere, so on Windows a pasted block runs line by line; `GetNumberOfConsoleInputEvents` could say it, left until someone pastes there. Its line ends are read with their `\r` trimmed already.
- **l. Size.** Every line of this is `cfg(windows)`: a Unix binary is the same to the byte, as #453's was, and the browser module compiles none of `fs.rs`. Each slice says so, and names a Windows binary's size before and after. Slice 2's Unix binaries are main's to the byte ([above](#built-in-slice-2)); on Windows, built as a release builds them on `windows-latest` (a job #521 ran once), `fennec-server.exe` went 8 814 080 -> 8 889 344 bytes (+73.5 KB, 0.9%) and `fennec.exe` 4 191 232 -> 4 211 712 (+20 KB, 0.5%) -- most of it the mapped path a Unix compiled already and Windows now does too, the compact beside the database and its side file among it, beside the views' own code.

**Tested on Windows CI**, each in its slice: a rename over a file a test's handle holds without `FILE_SHARE_DELETE`, tried again and then failing the sink as now, and taken once the handle closes within the bound (e); a tenant named `con` or `lpt1` refused on every system's CI (b); a secret's file's DACL read back owner-only, and the TLS key's warning on a key `Everyone` reads (h); the lease's clock moving forward, and fennec-http's `lease` tests passing on it (i); `cache::room` answering a part of the machine, as `the_room_is_some_of_the_machine` asks on Unix (j); the link's test (c); a TLS connection ended with `close_notify` at a Windows server's shutdown (g).

## Risks

- *A Windows update changing the experiment's answer*: the matrix asserts what Windows does, so CI fails before a server meets it.
- *Retired files piling up* under (b), where another process keeps an old file mapped for days -- a `fennec --read-only` left open: a file a rewrite until it closes, swept at each open and each rewrite, named in a line at each. Not met: slice 1's experiment took (a).
- *Another process's handle* refusing renames ([7e](#7-what-else-windows-differs-in)): tried again for a bounded time, then the sink fails as it does now -- loud, writes stopped until a reopen.
- *A power cut* NTFS's log was not flushed for: two flushes a rename, an evidence of 90% where others measured; the VM's run before the release.
- *Views adding up*: one a handover, until a rewrite maps the file again in one or the file outgrows its room and is mapped anew. Single small writes hand over every 16 384 (`HANDOVER_DOCS`), about 2 MB of 128-byte rows, so 100 GB written is about 50 000 views, a mapping holding no more than its room takes -- the file's length at its open or last rewrite, a gigabyte at least -- about 500 a GB of it. Their teardown, an `UnmapViewOfFile` each, goes to a thread past 16 ([above](#built-in-slice-2)). CI holds a thousand to their bytes and a rewrite to one view (`a_rewrite_maps_the_file_again_in_one_view`); what 50 000 cost -- the address space's bookkeeping, a handover's split and the teardown -- is a Windows machine's to measure.
- *A Windows before 1803*: placeholders refused, a view made anew at each handover, slower and named at the start (`fs::placeholders`).
- *SmartScreen and Defender* warning of, or quarantining, an unsigned binary: the checksum stands, and signing is the owner's decision.
- *The Windows jobs' time*: three jobs, each under the Linux test job's.

## Decisions for the owner

Each recommended, its alternative what the owner can still choose before the slice it bites in.

1. **Scope.** *Recommended:* the file server, the shell and the native library; a `--dir` node built and tested, its docs Linux's; the router not shipped for Windows. The alternative, nodes and the router first-class there, owes the router's failover cut on Windows sockets and the lease's clock before any release.
2. **The mapping.** *Recommended:* views laid end to end in a placeholder (Windows 10 1803), a view made anew at each handover where refused. The alternatives: the latter everywhere (simpler, any Windows 10, a soft fault a page a reader touches after each handover), or no mapping on Windows, today's, said as `--no-mmap`'s costs.
3. **Replacing a mapped file.** *Recommended:* the experiment picks -- std's rename if a view does not refuse it, the retired swap if it does. *Taken; slice 1's experiment picked std's rename.* The alternative, the retired swap on Windows whatever the experiment says: one path no update can break, at the price of a crash window an open repairs and files left while views live.
4. **A rename's durability.** *Recommended:* the directory flushed and the renamed file. The alternatives: the file's flush alone, `MOVEFILE_WRITE_THROUGH`'s; or none, NTFS's lazy log, today's.
5. **Services.** *Recommended:* console events in the first release, a wrapper for a service, a native `--service` mode after it. The alternative, the native mode before the release.
6. **The release.** *Recommended:* an x86_64 `.zip` with a static CRT and `install.ps1`, checksummed and unsigned; aarch64 where its runner builds it. The alternatives: an MSI; Authenticode signing first, a certificate and a secret to keep.
7. **Device names as tenant names.** *Recommended:* refused on every system. The alternative, refused on Windows alone, where a directory made on Linux may then not restore. *Taken* (slice 4): refused on every system; a tenant a Unix node held under one before is out of reach after the upgrade -- passed over by every listing, said in the log with the way back by hand, and copied under another name before the upgrade where it matters (7b).
8. **Line endings.** *Recommended:* `.gitattributes`, `* text=auto eol=lf`. The alternative, `core.autocrlf false` in the Windows jobs alone.
9. **A power cut before the release.** *Recommended:* a VM's power-off on a Windows machine, a compact and `--sync always` writes in flight, run by hand once before slice 5. The alternative: ship on CI's evidence and the documentation's, the page saying so.
10. **The desktop app on Windows.** *Recommended:* a project of its own after the release. The alternative, with the release, its signing with it.
