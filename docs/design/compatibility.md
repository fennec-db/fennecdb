# The 1.x compatibility contract

What fennecdb 1.x promises, surface by surface, and the check that holds each promise today. The rule across them is one sentence: **a 1.x release only grows a frozen surface, and a break is a major version.** A surface no check holds yet names the item of the 1.0 plan that adds it; until that item lands the promise is held by review alone, and the table says so.

This file holds no invariant of the code on its own: each row's rule lives in the CLAUDE.md of the area that enforces it. The user's page is [site/content/docs/compatibility.html](../../site/content/docs/compatibility.html); what a release must check is RELEASING.md's *1.0* section.

## What grows, what breaks

*Grows* is an addition no existing caller, file or peer can meet as a change: a record kind or type tag a file takes only once a feature uses it, a route, an optional field, a flag, a statement. *Breaks* is anything else: a record or tag removed or reread, a statement that read one way and reads another, a route, field, flag, exit code, metric name or exported symbol removed or changed in type, a release asset renamed. A deprecation is not a removal: a surface is deprecated in a minor, kept through the rest of 1.x, and removed only in 2.0.

A feature whose first use moves the file format -- it writes a new kind or tag -- is named in that release's notes, because an older binary refuses the file (see [the upgrade order](#upgrade-order)).

## Fixture sets

A release's set is what its own binaries wrote and the answers it gave, in `crates/fennec-core/tests/compat/v<version>/`, written once from its tag (RELEASING.md's step 6, `make compat-fixtures V=<version>`) and never again. `tools/compat_fixtures.py build` takes the tag's tree alone -- no release asset, its `Cargo.lock` as released (`--locked`) -- and builds its `fennec-server`, `fennec`, module (its own `make wasm`) and `tools/compat/writer.rs` as an example of its fennec-core. Nothing is downloaded: cargo builds `--offline`, from its own cache, and the release binaries' one set of crates from outside the workspace -- rustls, ring and webpki-roots behind their default `tls` feature -- is either there, as on a machine that built the tag, or the build stops naming them and the `cargo fetch --locked` that brings them once. `write` runs the binaries, and writes `SHA256SUMS` last. The server writes a file whose image and log hold every record kind a server's writes take, every change a field record names, a block holding every schema change a block takes, every type tag, a collection (`shapes`) holding every alternative a schema's field writes -- `required`, each combination of a collation, `nocase` and a `@text` beside another index, each text index's options, a list of every type a list takes, a descending part of an index over several fields, a path's every index -- statements of every op among them (a binding of each set of events, a scheduled slot that ran and one refused, schedules of months, a cron, a named zone and an offset, a webhook consumer's event), and its own collections (`_idempotency`, `_consumers`, `_migrations`, `_hook_events`); a replica's file of it and that file promoted; a checkpoint's graphs of every metric, precision and quantization -- a bit index's codes and centres past the 2 048 vectors it codes at, tombstones in each arena, aliases, an 8-byte document id; a sealed backup, a sealed archive and a plain one; and, started again on its file, its answers over HTTP. The shell writes a file of its own; the web client its IndexedDB records and OPFS file, a replica's sync with the release's server and a migration among them, through stand-ins for both stores (`tools/compat/web.mjs`). The answers are `json::response_to_string`'s, read by the release's engine from each file opened read-only (a sealed file or an archive restored first by its `fennec restore`), the page's `run`'s, and the server's bodies.

What no binary writes at a few kilobytes, or on the machine writing the set, the release's engine writes through `writer.rs`, by the knobs its own tests turn -- each file still one a process of that release writes:

| File | Lowered or bypassed | Why it is still the release's layout |
| --- | --- | --- |
| `spill.fennec` | The spill threshold, 16 MB (`SPILL_AT`), through `set_spill` | A spill's and a land's records are the block's own, cut where it outgrew the threshold, whatever the threshold -- every schema change a block takes among them, in the first spill and in the land; a block put back leaves its spills dead the same way. The record kinds and bodies are a 16 MB block's; its widths are not: at 2 KB every claim is a byte and every length one or two, where a 16 MB block's spills take lengths of four bytes and its land a claim of two -- which `torn-wide.fennec` holds |

| `waiting.fennec` | A server's open (`fs::open_serving`) and checkpoint called back to back, before a linker runs | The race a server can lose made certain: the checkpoint's own record, nodes flagged waiting |
| `synclog.fennec`, `synclog-torn.fennec`, `.sync` | The sync log, Linux's and Android's, kept on macOS (`keep_sync_log`, as the release's own tests keep it); the crash made by `mem::forget` and a truncation to the log's base; in `synclog-torn` the back half of the log's last entry zeroed | The log's format is the same on every Unix that keeps it; a power cut leaves the file at its last fsync and the rest in the log, which the cut makes, and one inside the log's own write an entry whose bytes did not all reach the disk. `synclog`'s log is in its first pass, zeros after its entries; `synclog-torn`'s past it, as a server's soon is: syncs of 60 KB filled its room, the file was synced and a generation begun, the writes after it over the front of the last pass's entries, the rest of them behind its torn entry |

The plan's next item, T3, runs v0.2.0's released Linux binaries against HEAD in CI: there a real Linux server's files, its sync log among them, a tenant node's directory and a router's file meet HEAD.

A later build holds each file to its checksums (a torn one refused naming its damage), opens it as a tool does and as a server does, answers every statement alike, writes two rows into every collection -- a value in every field, each found through its index by that index's own operator, a path into a json field and an index over several fields among them -- reads them back, and again once opened anew (the release's records and this build's after them, as a server upgraded in place reads its file), takes them out, answers alike, compacts -- this build rewriting the release's rows -- opens again, answers alike and verifies the file; a replica's file is held to refusing a write of its own. Three opens and one compact a file: each close and compact is an fsync, `F_FULLFSYNC` on macOS, most of what a file costs. `fennec verify` reads every file as it lies and once this build wrote into it and compacted it, fennec-core holding those answers. Every graph the file keeps is restored rather than built again (`Persisted`), a rebuild answering a small `near` alike; one no later write touched serializes back to its record's bytes. A copied sync log is stamped with its copy's device and inode first: a log names the file it was written beside, so a copy's is never applied, which the test asserts before the stamp; the log's opens run on a Unix alone, no Windows build reading a log. An answer that differs is a finding: fixed, or named in `tests/compat/answers.rs`'s `ACCEPTED` with the change and why, never written again. `FENNEC_COMPAT_SETS` points every `compat::` test and the web test at a directory of sets `write` has just written, held to them before it lands; a directory holding no set, a set itself (its `archive/` no set), a set with no README or sums, or a file asked fewer than four statements fails, never passes over nothing.

The walk (`crates/fennec-core/tests/compat/walk.rs`) reads every byte of every file of a set by the release's own layout, written from its encoders, never through this build's readers: each record's head, claim and sum, each kind's body to its end -- a schema's places and each field's tags, type, `required` byte, index, paths and the indexes over several fields; each frame and every value in it, held to its schema's places; a graph record; the id counter's index of the frames and its shares; a history; a block's, a spill's and a land's records; a field change; a statement record of each op, past its op to its end; a close's mark -- and the files around them: each sync log's header, this generation's entries (put back into the file's bytes and held to this build's own reading of the log) and what follows them, an earlier pass's bytes or an entry torn; the page's IndexedDB records, the sealed ones turned back by the walk's own AES (FIPS-197's and GCM's vectors hold it); in fennec-http's walk, a seal's frames and each archive's names, images, segments and history, the plaintext through this build's `seal.rs`. A byte nobody read fails naming its file and offset, as does a record kind, a tag, an op or a flag byte the release writes none of. Where a byte changes no answer, this build's reading of it is held to the walk's: every claim through `engine::checked_claim`, the point it names to the byte, and every collection's schema as an open reads it -- each field's `required` byte, collation, `nocase`, index and the `@text` beside it, each index over several fields unique or not and each part descending or not (`every_claim_a_release_wrote_reads_as_its_bytes`, `every_schema_a_release_wrote_reads_as_its_bytes`). Where the open's own reading of a claim decides what it reads -- the durable point, below which it reads records unchecked and past which it cuts damage -- `torn-wide.fennec`'s answers hold it, both ways: a two-byte claim read as naming an earlier point refuses the open at its synced flipped row, one read as naming a later point keeps the page past the fsync a power cut lost. `RELEASES` there holds the walk to each release both ways -- for v0.2.0 record kinds 1 to 14, statement ops 1 to 6, graph versions 9 and 10, schema tags 1 to 12 and 14 to 18, value tags 0 to 10, 13 and 15, index kinds 0 to 11, each in a file and none other in one -- and `ALTERNATIVES` names every form inside them the walk tells apart (163 of them: the claim and head varint widths, each kind's body's forms, a field's every tag and flag byte, each list type, each graph arena and list form, the sync log's ends, a seal's frames, an archive sealed or plain, the page's records), each in a file of the newest release's set, held both ways, or absent with why, which the set's README names: for v0.2.0 claims of 3 and 4 bytes and a record length of 5 (256 MiB to 64 GiB of file), collection ids of 5 bytes (past 268 435 455 collections made in one file's life: half an hour of writes, where `torn-wide.fennec`'s 2 097 152 take 12 seconds), graph links and steps of 3 and 4 bytes (a graph past 65 536 nodes: 1.5 MB of links git cannot compress, restored and written again in every run) and a seal of several frames (a mebibyte of ciphertext; its frames an appended segment's, which the archive holds), and `_follow` (PostgreSQL). A set with no line fails, and so does a line with no set in the tree, whichever sets `FENNEC_COMPAT_SETS` names; `tools/test_version.py` fails it too, from v0.2.0's on, a later set beside it or not. A release writing something new adds the statements writing it, its forms to `ALTERNATIVES` and its line to `RELEASES`, before its set is written.

The suites: fennec-core's `compat::` takes 4.5 s in a debug build on an M1 at rest (the one run the machine was quiet for); under other builds' load (14 to 22) fennec-http's took 0.3 s, fennec's 6 s, fennec-server's 2 s and the web test 0.7 s. fennec-core's answers test and fennec's run each file on a thread of its own. The Windows jobs run the four Rust suites well inside their bounds (`.github/workflows/ci.yml`).

What cannot be the same twice is written once: a history's id (random at a fork, a promotion and a restore), a seal's and AES-GCM's nonces and a sealed page's generation, a scheduled slot's time, a hook's arrival, a kept key's time, a queued sync write's key, an archive's file names, and the sync log's generation and identity. The sync logs are their fixed 260 KB as written.

## Not frozen

- The Rust crates' API: none is published, and `fennec-core`'s items change in any release. Their behaviour through the frozen surfaces is what holds.
- `fennec-wasm`'s exports: internal to `@fennecdb/web`, which ships `web/fennec.js` and `web/fennec.wasm` together.
- The IndexedDB and OPFS layout. A page's stored data restores in every later 1.x; how it is laid out may change.
- The studio's pages and the desktop app (beta). The studio's calls are the API's, frozen as it is.
- Measured numbers, benchmarks and their harnesses, `examples/`.
- 0.x: it promises nothing, and a 0.x client has no compatibility with a 1.x server.

## Upgrade order

Replicas before primaries, and files go one way. `deploy/RUNBOOK.md`'s *Upgrading with no downtime* is the long form: archivers, then routers, then every node holding a replica or standby, then primaries.

1. A newer replica follows an older primary: it reads every record the older one writes.
2. An older replica meeting a record kind or tag it does not know stops by name, never reading it as another: it refuses the write ("record kind 13 is not a write") and connects again, an archiver keeps the stream's bytes and takes no image of its own, and an older `verify` or `restore` refuses what it kept. `make upgrade-check` drives kind 13 today, by hand and not yet checked in CI (T3); T3 drives it with released binaries, and tags 17 (`nocase`) and 18 (a text index beside another).
3. A newer file's first use of a feature, not its install, is what an older binary refuses: kind 13 at the first `create statement`, tag 18 at a field's second index. Roll forward; a rollback is promised only before a feature's first use.

## The grammar epoch

`GRAMMAR_EPOCH` is `pub const GRAMMAR_EPOCH: u32 = 4` in `crates/fennec-core/src/named.rs` (`fennec_ql::GRAMMAR_EPOCH` is that one). A named statement is stored as its text, the epoch it was parsed under and its tree's digest; an open parses it again and marks it broken, its calls refused until it is defined again, where the digest differs. It was 4 at v0.2.0 and is 4 now, but 2, 3 and 4 each marked stored definitions broken. Under 1.x:

- The epoch stays 4. A change that would raise it is not made.
- A text a 1.x release read is not refused by a later 1.x: the corpus holds a refusal to the epoch as it holds a moved digest. Against a 0.x base -- v0.2.0's corpus, main before 1.0 -- a refusal whose stored reading holds is let through by an `ACCEPTED` entry alone ([fennecql.md](fennecql.md#the-corpus)).
- A text a 1.x release read is read alike by a later 1.x. A schema change, a listing or a `call` is compared by a hash of its tree's form, which moves where the tree changed shape and the meaning did not -- a field renamed -- as where the meaning changed; so against a 1.x base one read otherwise passes only with the epoch raised, or with an `ACCEPTED` entry's `same_meaning`: why it means what it meant, a claim the corpus prints for the review to judge. Against a 0.x base an entry alone is enough.
- Raising it is a major version, and its notes name the stored statements it breaks.
- A statement an open marks broken under a 1.x release is a bug in that release.

## Support

The latest 1.x minor gets every fix. The previous minor gets security fixes for six months after the next minor's release. `release/1.N` branches are cut when a backport needs one. Release candidates are tagged `1.0.0-rc.N`; the owner pushes tags.
