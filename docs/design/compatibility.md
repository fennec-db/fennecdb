# The 1.x compatibility contract

What fennecdb 1.x promises, surface by surface, and the check that holds each promise today. The rule across them is one sentence: **a 1.x release only grows a frozen surface, and a break is a major version.** A surface no check holds yet names the item of the 1.0 plan that adds it; until that item lands the promise is held by review alone, and the table says so.

This file holds no invariant of the code on its own: each row's rule lives in the CLAUDE.md of the area that enforces it. The user's page is [site/content/docs/compatibility.html](../../site/content/docs/compatibility.html); what a release must check is RELEASING.md's *1.0* section.

## What grows, what breaks

*Grows* is an addition no existing caller, file or peer can meet as a change: a record kind or type tag a file takes only once a feature uses it, a route, an optional field, a flag, a statement. *Breaks* is anything else: a record or tag removed or reread, a statement that read one way and reads another, a route, field, flag, exit code, metric name or exported symbol removed or changed in type, a release asset renamed. A deprecation is not a removal: a surface is deprecated in a minor, kept through the rest of 1.x, and removed only in 2.0.

A feature whose first use moves the file format -- it writes a new kind or tag -- is named in that release's notes, because an older binary refuses the file (see [the upgrade order](#upgrade-order)).

## Fixture sets

A release's set is what its own binaries wrote and the answers it gave, in `crates/fennec-core/tests/compat/v<version>/`, written once from its tag (RELEASING.md's step 7, `make compat-fixtures V=<version>`) and never again. `tools/compat_fixtures.py build` takes the tag's tree alone -- no release asset, its `Cargo.lock` as released (`--locked`) -- and builds its `fennec-server` and `fennec` as its `release.yml` does (`--release`, `--profile cli`) for the host's target, its module (its own `make wasm`) and `tools/compat/writer.rs` as an example of its fennec-core, by the compiler the tag pins (its `rust-toolchain.toml`, or `TOOLCHAINS` where that names a channel: v0.2.0's says `stable`, built with 1.99.1) and no other, and writes `MANIFEST.json` beside them: the tag, its commit, the compiler as `rustc --version` said it, the cargo home, the SDK and the tree's path the programs were built under (`cargo_home`, `sdk`, `tree`), how each program was built and the SHA-256 of every program, module and file it kept of the tag's tree (the web client, the collations, @fennecdb/cloudflare's module). `write` holds the directory to its manifest before any program of it runs -- every file named there by its sum and none other, the tag's commit, the pinned compiler, every kept file `git show <tag>:<path>`'s bytes (`tools/test_compat_fixtures.py`, CI's fmt job) -- and copies the manifest into the set under its sums, with the sums of `tools/compat_fixtures.py` and `tools/compat/` that wrote it. The module is a release asset: v0.2.0's `make wasm` gives `fennec-web-v0.2.0.tar.gz`'s `fennec.wasm` byte for byte (SHA-256 5b3513ca..., 852 824 bytes), as its tree gives the tarball's `fennec.js`, so anyone can check the manifest's digest of it against the release's `SHA256SUMS`, which names the tarball by its sum. The three programs -- `fennec-server`, `fennec` and the writer, which is no asset -- are built from the tag, and their digests reproduce only on a machine with the cargo home and the SDK the manifest records (`cargo_home`, `sdk`: for v0.2.0's set macOS SDK 26.2 with ld 1230.1): a program carries the cargo home's path in the panic locations of the crates from outside the workspace, and its layout moves with the SDK and its linker. `build` puts the tag's tree at one path on every machine (`/tmp/fennec-compat-build-<tag>`, the manifest's `tree`): the linker's UUID of a program hashes the paths of the objects it was handed, which the release profile's `strip` then takes out, and two builds of v0.2.0 in two temporary directories differed in their UUID and signature alone. So v0.2.0's published `aarch64-apple-darwin` binaries are not the set's (6 891 744 bytes against 6 908 256, 3 702 400 against 3 702 384: the runner's home in their panic locations, macOS SDK 26.5). Nothing is downloaded: cargo builds `--offline`, from its own cache, and the release binaries' one set of crates from outside the workspace -- rustls, ring and webpki-roots behind their default `tls` feature -- is either there, as on a machine that built the tag, or the build stops naming them and the `cargo fetch --locked` that brings them once. `write` runs the binaries, and writes `SHA256SUMS` last. The server writes a file whose image and log hold every record kind a server's writes take, every change a field record names, a block holding every schema change a block takes, every type tag, a collection (`shapes`) holding every alternative a schema's field writes -- `required`, each combination of a collation, `nocase` and a `@text` beside another index, each text index's options, a list of every type a list takes, a descending part of an index over several fields, a path's every index -- statements of every op among them (a binding of each set of events, a scheduled slot that ran and one refused, schedules of months, a cron, a named zone and an offset, a webhook consumer's event), and its own collections (`_idempotency`, `_consumers`, `_migrations`, `_hook_events`), a collection whose highest row was deleted before the compact (the image's id counter past every live id), numbers past their type's range the release stored (`edges`: a float of `1e400` stored as infinity, a vector's component of `1e39` an f32's, an f16's of 70 000 its own, in fields and lists, and a named statement whose text holds `1e400`, each answered as the release answered it, `null`), numbers below zero (`signed`: ints and times before 1970 in fields, lists and json, ordered indexes across zero) and an index of every kind that takes options with each away from its default (`tuned`: `@text`'s k1, b, prefix and prefix_min on each kind and beside a `@hash`, `@hnsw`'s metric, m, ef_construction and ef_search, plain and int8; rankings and prefix matches that move if one is read as its default); a replica's file of it and that file promoted; a checkpoint's graphs of every metric, precision and quantization -- a bit index's codes and centres past the 2 048 vectors it codes at, tombstones in each arena, aliases, an 8-byte document id; a graph of 70 000 vectors (`graph-wide`, one dimension, `m=2`), whose record takes links and steps of three bytes; two sealed backups, one past a mebibyte in two frames, a sealed archive and a plain one, what `fennec verify` said of each and what the release's `fennec restore --to` said and answered at every moment a later build restores them to (`<archive>.restores.json`); ## Upgrade order

Replicas before primaries, and files go one way. `deploy/RUNBOOK.md`'s *Upgrading with no downtime* is the long form: archivers, then routers, then every node holding a replica or standby, then primaries. Routers before nodes holds the open nodes too: a node asking no data token refuses what a 0.2.0 router forwards it, on loopback or not, unless the node runs `--insecure` -- that router has one mark, the one a router listening past loopback sends ([http.md](http.md#open-servers)) -- and `compat.yml`'s d1 and g1, a 0.2.0 router over this tree's nodes, give those nodes `--insecure`.

1. A newer replica follows an older primary: it reads every record the older one writes, and holds [the four exceptions](#what-1x-does-not-read-of-020s-files) as a newer server holds them -- the deep row taken in an image and refused where it is read, a write touching it not applied, the replica connecting again from 100 ms to 5 s apart until the primary stops writing it.
2. An older replica meeting a record kind or tag it does not know stops in words, never reading it as another: it refuses the write ("record kind 13 is not a write") and connects again, an archiver keeps the stream's bytes and takes no image of its own, and an older `verify` or `restore` refuses what it kept. Where the older binary names the kind, the tag or the version, it names it; where it knew of no other -- 0.2.0 meeting a version 3 sealed file -- its words name nothing ("not a sealed file"), and the release's notes name it instead. `make upgrade-check` drives it by hand against the commits before kind 13, its ops and the checksums; `compat.yml` against the last published release's binaries ([the matrix](#the-compatibility-matrix)), where none is new since 0.2.0: every kind, tag and op of the tree is written by a new primary and the old replica follows them all.
3. A newer file's first use of a feature, not its install, is what an older binary refuses: kind 13 at the first `create statement`, tag 18 at a field's second index. Roll forward; a rollback is promised only before a feature's first use.
4. Every reader of a file or a stream -- a replica, a standby, an archiver, a router, a node, the `fennec` that verifies and restores -- upgrades before any primary. A binary one release back beside a newer one works or stops in words, never reading wrong (point 2 says what its words name); a newer reader reads what an older writer wrote but for the four exceptions (RELEASING.md, *Every reader upgrades before any primary*). Where one node holds both primaries and replicas -- a `--dir` node holding its tenants' primaries and another node's tenants' standbys -- it cannot be upgraded as a reader before every primary: in such a fleet nothing uses a feature that moves the format until every node runs the release.

### A 0.2.0 node and a compact

Every release from 0.1.7 to 0.2.0 takes a dropped field's places out of the documents at a `compact` -- its own `--auto-compact` too, from 0.1.10 on a replica as well -- and tells no copy. The copies keep the places and read the collection's later writes one field early, or one late where the copy compacted first. From 1.0 a compact keeps every place ([storage.md](storage.md#dropped-places)), which a 1.x copy of a 1.x primary relies on. The upgrade order puts the two releases beside each other both ways round:

- *A 0.2.0 primary and a 1.x copy*, the order's own window. The copy reads every write as it was made: the primary's first write of the collection after a stripping compact holds a value less than the copy's places, and is refused by name (`the primary's writes moved the fields of`), as is an `alter` or `create index` of it that comes first. Where no field followed the dropped one, the place was last in every document: the writes agree and read alike, and the copy tells at the primary's next `alter` or `create index` of the collection instead, whose schema holds no such place. A server's follower, a `--dir` node's standby among them, then takes an image of its primary and holds what the primary holds from there ([replication.md](replication.md#a-copy-across-a-compact)). No value read a field off reaches a 1.x copy's file. An archive does not tell: a restore across such a compact, from an image before it, reads the writes after it a field off.
- *A 1.x primary and a 0.2.0 copy*, which point 4 makes unavoidable in a `--dir` fleet: a node upgraded keeps its tenants' primaries while their standbys run 0.2.0 on a node not yet upgraded. A field dropped on the primary keeps its place, and the standby's own compact -- `--auto-compact` runs one once half its file, and 64 MB, is dead -- takes the place out of its documents and tells nobody. The standby then reads every later write of the collection a field late, with nothing to check it, and after a failover onto it those values are the tenant's. A 1.x primary cannot tell an older copy from its stream to refuse the drop: a copy's request (`GET /_replication?since=..&history=..&sums=1`, with `Host` and `Authorization` alone, a `--dir` standby's for each tenant alike) and the hello's version (1) are the same in 0.2.0 and 1.x, and the protocol gains nothing for a window the order closes.

So while 0.2.0 and 1.x run beside each other:

1. Before upgrading the first copy, if a field was ever dropped on the primary, the copies may hold rows read a field off already, by a compact on either side after the drop. Run `compact` on the primary, then seed every copy again from an image taken after it: a replica stopped, its file replaced by a `fennec backup` of the primary, and started again; a `--dir` node's standby from such a file too; an archive begun again in a directory of its own, the old one kept for restores to a moment before the compact.
2. **Drop no field until every node and every copy runs 1.x.** On a 0.2.0 primary the next compact takes the place out -- `--auto-compact` runs one on its own -- and every 1.x copy takes an image at the write or alter after it, and an archive's restores across it misread. On a 1.x primary a 0.2.0 copy's own compact takes it out of the copy, which misreads with nothing to tell it. Where a drop on a 1.x primary cannot wait, every 0.2.0 copy of it runs `--auto-compact off`, and no `compact` is run on one, until it runs 1.x: a 1.x primary's compact keeps the place, so the copy applies the writes after it by the places both hold.
3. A copy that logs `moved the fields of` has met such a compact and takes its image itself; promote none that has not caught up since.

The cases [the compatibility matrix](#the-compatibility-matrix) owes, which it drives none of today: a 0.2.0 primary and a 1.x copy across a drop, a compact and a write -- the 1.x copy refusing the write by name and taking an image, ending with the primary's rows, and, the dropped field last, refusing the primary's next `alter` instead -- and the same with the copy compacting first; a 1.x primary and a 0.2.0 copy across a drop, the primary's compact and a write, the copy's `--auto-compact` off, ending with the primary's rows, and the same with the copy compacting on its own, which reads the writes after it a field late: the window point 2 closes, driven so that a change to it shows (T3). The release fixtures a dropped place and the bound ask for ([storage.md](storage.md#dropped-places), *How many places*) are held, in v0.2.0's [fixture set](#fixture-sets) (`crates/fennec-core/tests/compat/v0.2.0/`, T2) and read by fennec-core's `tests/compat.rs`: `compacted.fennec`, whose dropped field 0.2.0 then compacted (`people`'s `age`, its place taken out of every document and of the schema), and `server.fennec`, whose log after its image drops a field 0.2.0 never compacted (`kinds`' `old`, `shapes`' `last`), each opened, answering as 0.2.0 did, written into and compacted by this build (`every_file_of_every_release_opens_and_answers_as_its_release_did`), `compacted.fennec`'s walk holding no dropped place left (`every_kind_and_shape_a_release_writes_is_in_its_set`); and `many.fennec`, a collection of 4 097 fields, renamed a field of and dropped one, refused a field more and compacted (`a_collection_of_more_than_4_096_places_takes_a_rename_and_a_drop_and_refuses_a_field_more`).

## What 1.x does not read of 0.2.0's files

1.x opens every file written from v0.2.0 on but for four kinds of value or type, each one 0.2.0 took and no write makes any more (`Schema::new`, the parser, `value::held`), refused where it is read because reading it would put back what the limit closed ([crates.md](crates.md#how-deep-a-value-nests): a decoder recursing a level at a time, which a record of nested lists overflowed the stack with; [crates.md](crates.md#limits) for the ranges). fennecdb is alpha, with no user's file to keep; v0.2.0's fixture set holds one file of each, written by its own binaries (`deep`, `points-deep`, `refused-lists`, `refused-dims`).

1. **A `[[json]]` field's row nested past 64 levels** (`[[json]]` took a json value of up to 64 levels inside its two lists, 66 in all). The file opens and every other collection reads. A statement that decodes that row fails whole, answering `{"error":"a value nests more than 64 levels deep"}`; `count`, a read of another row by its id, and the fields stored before the deep one (`select name`) still answer. A `del` or a `set` of the row is refused in the same words, the count unchanged; `alter collection ... drop field` of the deep field is taken and helps only where no field is declared after it: every skip of a dropped place goes through `codec::skip_field`, which refuses a list, an object or a point at depth 64 exactly as the decoder does, so the fields stored before the dropped one read, and any field after it -- one stored after it or one added later, whose place is reached by skipping it -- is refused in the same words, a `select` of it and a `get` of every field alike, and so is a `del` of the row; an index built over a later field is refused in the same words. A backup and an image sent to a replica carry the row unchanged. A newer replica takes such a file in an image, holds the row and refuses its reads alike; a write of the primary's touching the row is not applied, and the replica connects again, 100 ms to 5 s apart, while the primary sends it. On 1.x alone the way out is, where the deep field is its collection's last (nothing is declared after it), to drop it and `del` the row (or write over it); and where a field is declared after it, to read the readable rows out (`select` the fields before the deep one, or every row by id but it), drop the collection and make it again (a3 drives both).
2. **A type nested past 64 lists** (`[[[...int...]]]`, which no version bounded): the schema is refused as it is read, and with it the whole file at the open (`could not open ...: corrupt: a value nests more than 64 levels deep`, exit 1).
3. **A point's type under 64 lists**: a point reads as the list `[lon, lat]`, a level of its own, so 64 lists around a `geo` are 65 levels: the whole file refused at the open, as 2
4. **A schema's number past its range**: an `@hnsw`'s `m` under 2 or past 32 767, a `vector<N>` or a `sparse<N>` whose dimension is 0 or past 10^9, a list of such vectors: the whole file refused at the open, as damage (`Schema::decode`, by the test `Schema::new` asks too, `schema::out_of_range`; [crates.md](crates.md#limits)).

Only 0.2.0 can rewrite a file of kinds 2 to 4. **The advice, which the first 1.x release's notes carry:** rewrite such values with 0.2.0 before upgrading -- the row's value made shallower or the row deleted, the field or the collection made again within the ranges. `compat.yml` drives 1 and 2 with 0.2.0's own binaries writing them (a3 and a3b; a3 drops the deep field in both layouts, a row whose deep field is the last of its collection and one with a field after it). The engine's tests hold the four refused with the stack whole: the deep row by `tests/damage.rs`'s `a_record_nesting_past_the_limit_is_refused_where_a_file_is_opened`, `an_open_reading_past_a_value_nesting_past_the_limit_is_refused` and `a_primarys_record_nesting_past_the_limit_is_refused_by_its_replica`, and `codec.rs`'s `a_value_nests_no_deeper_than_json_may_be_written` (the decoder, `skip_value` and the `skip_field` a dropped place goes through); a type of 65 lists by the same codec test (`decode_type` at 65 and at 100 000 lists); a point's type by `tests/damage.rs`'s `a_point_past_the_depth_a_type_nests_is_refused_where_a_file_is_opened_and_applied` (read into memory, mapped and applied by a replica) and `codec.rs`'s `a_point_is_a_level_as_the_list_it_reads_as`; the ranges by `tests/damage.rs`'s `a_schema_past_the_languages_ranges_is_refused_where_a_file_is_opened_and_applied` and `fennec-ql`'s `tests/numbers.rs` `a_field_made_out_of_range_before_is_refused_at_the_open`; and v0.2.0's own files of each, every build, by fennec-core's `compat::the_files_this_build_refuses_on_purpose_are_refused_in_its_words` (the deep row's steps on copies, the other three at the open).

## The compatibility matrix

`compat.yml` runs `make compat-check`: this tree's `fennec-server`, `fennec` and `fennec-shard` beside the last published release's, through `tools/compat-matrix.sh OLD_BIN_DIR NEW_BIN_DIR`. It runs weekly, on every release tag and by dispatch (naming the release, else the published release, not a draft nor a pre-release, highest in version order up to this tree's version and not tagged at this commit), on Linux x86_64; it is not part of `ci.yml`, no merge waits for it, and a release needs its run on the release commit green (RELEASING.md). Each case prints a line a part, `ok` and what it held or what differed, and a failure prints its logs' tails and uploads them.

**The old side.** `tools/release-bins.sh TAG OUT_DIR` takes the release's tarball for the machine (`fennec-<tag>-<target>.tar.gz`, the musl one on Linux) and its `SHA256SUMS` -- by `gh release download`, as `ci.yml`'s latest-release job does, or from a directory already holding them (`OLD_ASSETS_DIR`) -- and installs `fennec-server` and `fennec` from them through `site/install.sh`, served from 127.0.0.1: the checksum check is the installer's own, the one a user meets, not a third copy of it, and a tarball with a byte flipped is refused with nothing installed (`tools/test_release_bins.sh`, its own test, run by the fmt job and before the matrix). No release ships `fennec-shard` (`release.yml` packs `fennec` and `fennec-server`), so the old router is built from the tag's sources (`git archive`), with the tag's `Cargo.lock` (`--locked`) and this tree's toolchain, a debug build kept in `target/compat-shard` so the cargo cache holds its dependencies: the code the release was cut from, not a binary it published -- "the last release's binaries" means that wherever the matrix's result is quoted. Each binary's `--version` is held to the tag, and nothing reaches `OUT_DIR` before all three are; since both trees may say the same version, the run's first lines tell them apart by path and SHA-256, and a run whose two sides are the same bytes stops. A `gh` that fails stops the script, never read as "no release". A script beside `tools/upgrade-order.sh` rather than its `OLD_BIN_DIR`: that script's cases hold binaries from before kind 13, its ops and the checksums to refusing them, and 0.2.0 has them all, so its binaries there would fail every case by reading what each was written to see refused; its bases stay commits.

**What it drives.** Every write of a case comes from one history, `HISTORY`, and `FORMAT` holds every record kind (`REC_*`), type tag (`TAG_*`) and op (`OP_*`) -- every `u8` constant of those prefixes in any file under `crates/fennec-core/src`, whatever its visibility -- to the write that makes it, or to why none is needed: a kind no write makes (the image's counter, next ids and graphs, which a1's and a2's replicas take in an image; the history; a file's close mark, which c2's file carries), a spilled block and its landing (never sent, and a 16 MB write in every case's history costs more than it shows), and a schedule's mark (written by the clock: a slot each second would move the counter between writes, by which a2 places its replica). The self-test fails on a constant FORMAT does not name, so the next kind, tag or op cannot be forgotten. The other numbered spaces a file or a stream carries are tables of their own, each held both ways (a code with no line, a line with no code) and each line a write of `HISTORY` or a reason: `GRAPHS`, the graph record's versions (`GRAPH_VERSION*` constants; 9 is written into an image, 10 by a server's own saving, 3 to 8 are read only, held by vector.rs's tests that write and restore the older layouts); `INDEX_KINDS`, the byte behind a field's index, a literal in `encode_index`, so the check reads `encode_index`'s `out.push(N)`s and `decode_index`'s match arms and requires the two lists to be one and the table to be it; `SMALL_CODES`, the metric, quantization and collation codes, read from their `from_code` arms; and `STREAM`, the replication stream's message tags, `b'X'` literals the primary writes and the replica matches in `replication.rs`, the two lists one and the table to be it. A function that moves from where the check reads it makes the table fail as empty, never pass; the self-test mutates a copy of each source (a code more, a code written and not read) and each table (a line more). `HISTORY`'s `indexed` collection makes the index kinds, metrics, quantizations and the second collation that `kinds` does not; a release that adds one adds its write and its line; a release that adds one the last release does not read adds its write's text to `UNKNOWN_TO_OLD` with the words its old replica must stop with, the number named where the old binary names it. Each state compared is the same reads -- every collection, `call`, `describe`, `statements`, a `nocase` `where`, a `match`, a `near`, a collation's order and an index over several fields -- each answer normalized, any refusal reduced to `"error"`, a score and a schedule's `next` and `last` left out, so two versions' words never differ a state.

**What holds the harness.** A case runs in a subshell under `set -eE`: a command failing anywhere is written down by its line whatever the case printed before, a case exiting other than 0 fails, and each part a case owes (`CASES`, written once) must print exactly one line: a part unsaid fails by name, and the run ends held to every part of the cases it ran. `--self-test` holds this with toy cases and no binary -- a case dying after its first part, one printing a part too few, one dying in a command substitution (b2's path with no image), one printing a part not its own, one dying on an unset variable after every part, one exiting other than 0 with every part said and its sentinel written (the status check alone), one failing a check in a helper used as an `if` condition, each failing the run -- and every table to the tree and to a tree with a code more or a line more. Two things about bash 3.2, which runs `make compat-check` on a Mac, are held: a subshell with an `EXIT` trap that dies on `set -u` exits 0, so each case writes a `finished` sentinel after it returns and the run requires it beside the parts; and `set -e` does not act in a function used as an `if` condition, so a check in a helper is `|| fail`, never a bare command. The script is held to that bash and to the Linux runner's, the self-test run under both. A server that must refuse to start (a3b, f1) is started in the background and waited for by its exit or its `listening on:` line, bounded: one that listens fails the case by name rather than hanging the job. A state compared across releases is held by the older release's answer (`state_holds`: every key it has, with its value, so a field a later release adds to `describe` or `statements` is no difference), and every state a case compares is first required to be answers, none a refusal.

### What it found against 0.2.0

Driven on 2026-11-15 against v0.2.0's aarch64-apple-darwin tarball and the router built from its tag (`e5d5424e`) by this tree's toolchain, beside debug builds of this tree (main and the next landings at `65ac238f`, #665's seeds in parts among them), on macOS, every part held:

- **Nothing is new since 0.2.0 in the format.** Record kinds 1 to 14, type tags 0 to 18, kind 13's ops 1 to 6 and the data records' two ops are the same in both trees (`FORMAT`, read from `crates/fennec-core/src`), so the old replica follows a new primary through every write to the primary's change counter (a2), and kind 13 and tags 11 to 18 are driven as writes 0.2.0 reads, not ones it stops at. `UNKNOWN_TO_OLD` is empty.
- **Promised, and held in the promised words.** A sealed archive and backup of this tree are version 3, which 0.2.0's `fennec` refuses ("not sealed, where the archive is", "not a sealed file"), naming no version and writing nothing (b4, c3); a hooks file's `key delivery` stops the new server, exit 2 (f1), and a kept set's events are answered 409 until it is set again (f2).
- **Found by the first run on Linux**, which the Mac's had not: `compat.yml` on main at `61d67750` (2026-11-21) failed f2, the upgraded node putting away the 0.2.0 node's `<t>.hooks` as naming "another file than the tenant's" and answering the hook 401 ("the event does not verify"), every secret of the tenant lost until set again. 0.2.0's Linux tarball is musl, whose std reads no birth time, so its sidecars name a file by its device and inode and a birth time of 0; this tree's debug build is glibc, read the file's birth time, and compared the two as written. A bug, not a break: 0.2.0 has it between its own musl and glibc builds (#454 bound the birth time, #507 the hook set), and nothing is held by refusing a set its own binary would read. Every comparison of two bindings now holds a birth time only where both name one (`instance::same`), the identity's too, which a node moved so lost as well ([tenants.md](tenants.md#replicas-tried-again)); f2's expectation was right and stands. On a Mac both sides read birth times, which is why the run there held.
- **The four exceptions, decided.** 0.2.0 takes a `[[json]]` row nested 66 levels deep and reads it; this tree refuses it where it reads it, as [crates.md](crates.md#how-deep-a-value-nests) chose -- reading it would put back the unbounded recursion the limit closed, and fennecdb is alpha, with no user's file to keep -- and holds everything else of the file (a3, exception 1's list). A type of 65 nested lists, which 0.2.0 takes, refuses the file at the open (a3b). This contract names the four [above](#what-1x-does-not-read-of-020s-files); the first round's run, which found the row before they were named, failed a3 until they were.
- **The rolling upgrade (e)**: 208 writes sent through the router, 206 acknowledged and every one read back from the primary and the standby, 2 not sent (no connection while the router restarted, or the router's "was not sent" while the primary's node did; a run of e alone saw one, curl's exit 7 as the router restarted) and neither landed, none unknown, no `seq` twice; 50 writes acknowledged after each step, the standby caught up by the runbook's condition before each node. The counts move with the machine's speed and a restart's timing; the classes' rules do not.
- **Where RELEASING.md was not exact enough to follow**, written there and in the runbook since: a node pair's standby's node goes first; the wait between two nodes' restarts is the standby's status (connected, `behind` 0) or the primary's listing (`sent` its `durable`), not `FennecTenantsWithoutReplica`, which counts only a tenant with no copy at all over 15 minutes; a node holding both primaries and replicas cannot be a reader upgraded before every primary; restarting a primary's node in place costs its tenants' writes for the restart; and "upgrade every router" means building it from the tag, no release publishing `fennec-shard` yet.

## Unicode

The engine decides a text's case, a word and a name by the standard library's Unicode tables, and a release is built by one pinned compiler ([crates.md](crates.md#toolchain)), so a release's answers are of that compiler's Unicode version: 18.0.0 under Rust 1.100.0. One test names it, `case::tests::the_unicode_version_is_the_one_the_answers_are_of`, failing by name when a toolchain bump moves it, its message listing what the bump owes ([RELEASING.md](../../RELEASING.md#a-toolchain-bump)). The clients' builders, the studio and the Worker read names by their own runtime's Unicode, a version of their own. Owning tables pinned to a named version -- the compiler moving no answer -- was weighed and not done before 1.0: the version is named and tested instead.

**What is promised.**

- A 1.x minor release may move the Unicode version its answers follow; a patch release never does.
- The notes of a minor that moves it name every code point assigned before whose `upper()`, `lower()`, case fold (`nocase`) or word-hood (`@text`, a name) changed, and the ranges that become letters or digits. Rust 1.100.0's move, 17.0.0 to 18.0.0: `upper()` of ɷ, ɼ, ꭋ and ꭌ (U+0277, U+027C, U+AB4B, U+AB4C) answers their new capitals (U+A7DD, U+A7E2, U+AB6C, U+AB6D); everything else that moved is a code point 17.0 left unassigned -- 12 833 new letters (11 328 of them at U+3D000..U+3FC3F), 323 new digits, 20 new capitals with their small letters, and U+1DF95 uppercasing to `SS` and folding to `ss`. No code point stopped being a letter, a digit or a space.
- No stored byte follows it. The hash, text, ordered and sparse indexes are built at the first read and the HNSW graph holds vectors, so every release reads a file alike; answers move, not files.
- A name using a letter newer than a peer's Unicode is refused by that older peer in words -- `invalid collection name`, a statement that does not parse, a stored statement marked broken at the open -- never read as another name. A move that took a code point out of the letters or digits would refuse a name an earlier 1.x read, which [FennecQL's row](#the-frozen-surfaces) forbids: a bump that does so is not taken in 1.x.

**What a deployment of two versions sees.**

- *A rolling upgrade.* Replication ships records, not statements, so the writes land alike; a read answers by the binary that serves it, so a replica and its primary of two releases answer the moved code points apart -- `upper()`, `nocase`, `@text` -- until both run one. A stored statement whose text only the newer lexer reads can be made only on a newer primary, which upgrades last; an older `fennec` that verifies or restores that file marks it broken at the open, in words, and reads the rest. A `@unique nocase` field could hold two values that only the newer fold makes equal, each holding a code point the older release left unassigned: the newer release's bucket, built at the first read, takes both, and a later write of either meets the other.
- *A router and its nodes.* The router parses no FennecQL; it merges the nodes' rows of a `nocase` order across tenants by its own fold, so beside nodes of another release a row holding a moved code point may stand elsewhere in the merged order than its node put it. No row is lost or repeated.
- *A page's module against a server.* `fennec.wasm` ships with `web/fennec.js`, so a page's local reads answer by its package's release and the server's by its own: a replica in a page and its server answer the moved code points apart; the writes sync as records.
- *A native app's library against a server.* The library reads its shape's names by the compiler that built it (`shape.rs`): one older than the server refuses a shape whose collection or field name uses a letter newer than its Unicode, `invalid collection name: "..."`, and cannot sync that collection until the app ships a newer library. A newer library sends an older server a name it refuses in words.
- *A client's builder.* In a browser, Node or a Worker the JavaScript builder reads a name by its engine's Unicode, and every other SDK by its runtime's, each a version of its own: a builder behind the server's Unicode refuses a name the server takes, nothing sent, and the caller writes that statement as text; one ahead of it sends a name the server refuses in words. None reads a name as another.

## The grammar epoch

`GRAMMAR_EPOCH` is `pub const GRAMMAR_EPOCH: u32 = 4` in `crates/fennec-core/src/named.rs` (`fennec_ql::GRAMMAR_EPOCH` is that one). A named statement is stored as its text, the epoch it was parsed under and its tree's digest; an open parses it again and marks it broken, its calls refused until it is defined again, where the digest differs. It was 4 at v0.2.0 and is 4 now, but 2, 3 and 4 each marked stored definitions broken. Under 1.x:

- The epoch stays 4. A change that would raise it is not made.
- A text a 1.x release read is not refused by a later 1.x: the corpus holds a refusal to the epoch as it holds a moved digest. Against a 0.x base -- v0.2.0's corpus, main before 1.0 -- a refusal whose stored reading holds is let through by an `ACCEPTED` entry alone ([fennecql.md](fennecql.md#the-corpus)).
- A text a 1.x release read is read alike by a later 1.x. A schema change, a listing or a `call` is compared by a hash of its tree's form, which moves where the tree changed shape and the meaning did not -- a field renamed -- as where the meaning changed; so against a 1.x base one read otherwise passes only with the epoch raised, or with an `ACCEPTED` entry's `same_meaning`: why it means what it meant, a claim the corpus prints for the review to judge. Against a 0.x base an entry alone is enough.
- Raising it is a major version, and its notes name the stored statements it breaks.
- A statement an open marks broken under a 1.x release is a bug in that release.

## Support

The latest 1.x minor gets every fix. The previous minor gets security fixes for six months after the next minor's release. `release/1.N` branches are cut when a backport needs one. Release candidates are tagged `1.0.0-rc.N`; the owner pushes tags.
