# The 1.x compatibility contract

What fennecdb 1.x promises, surface by surface, and the check that holds each promise today. The rule across them is one sentence: **a 1.x release only grows a frozen surface, and a break is a major version.** A surface no check holds yet names the item of the 1.0 plan that adds it; until that item lands the promise is held by review alone, and the table says so.

This file holds no invariant of the code on its own: each row's rule lives in the CLAUDE.md of the area that enforces it. The user's page is [site/content/docs/compatibility.html](../../site/content/docs/compatibility.html); what a release must check is RELEASING.md's *1.0* section.

## What grows, what breaks

*Grows* is an addition no existing caller, file or peer can meet as a change: a record kind or type tag a file takes only once a feature uses it, a route, an optional field, a flag, a statement. *Breaks* is anything else: a record or tag removed or reread, a statement that read one way and reads another, a route, field, flag, exit code, metric name or exported symbol removed or changed in type, a release asset renamed. A deprecation is not a removal: a surface is deprecated in a minor, kept through the rest of 1.x, and removed only in 2.0.

A feature whose first use moves the file format -- it writes a new kind or tag -- is named in that release's notes, because an older binary refuses the file (see [the upgrade order](#upgrade-order)).

## Fixture sets

A release's set is what its own binaries wrote and the answers it gave, in `crates/fennec-core/tests/compat/v<version>/`, written once from its tag (RELEASING.md's step 7, `make compat-fixtures V=<version>`) and never again. `tools/compat_fixtures.py build` takes the tag's tree alone -- no release asset, its `Cargo.lock` as released (`--locked`) -- and builds its `fennec-server` and `fennec` as its `release.yml` does (`--release`, `--profile cli`) for the host's target, its module (its own `make wasm`) and `tools/compat/writer.rs` as an example of its fennec-core, by the compiler the tag pins (its `rust-toolchain.toml`, or `TOOLCHAINS` where that names a channel: v0.2.0's says `stable`, built with 1.99.1) and no other, and writes `MANIFEST.json` beside them: the tag, its commit, the compiler as `rustc --version` said it, how each program was built and the SHA-256 of every program, module and file it kept of the tag's tree (the web client, the collations, @fennecdb/cloudflare's module). `write` holds the directory to its manifest before any program of it runs -- every file named there by its sum and none other, the tag's commit, the pinned compiler, every kept file `git show <tag>:<path>`'s bytes (`tools/test_compat_fixtures.py`, CI's fmt job) -- and copies the manifest into the set under its sums, with the sums of `tools/compat_fixtures.py` and `tools/compat/` that wrote it. A local build rather than the published assets: the published binaries are one target's each, where the set is written on the machine writing it, and the writer and the module are not assets at all; for v0.2.0 on Apple silicon the local `fennec-server` and `fennec` are not the published bytes (6 908 256 against 6 891 744 and 3 702 384 against 3 702 400), built from the same commit, `Cargo.lock` and compiler: every readable string is alike but the cargo registry's path the binaries carry in panic locations (the runner's home there), and the code's layout moves with that path and the macOS SDK and linker (26.2 here, 26.5 on the release's runner). Nothing is downloaded: cargo builds `--offline`, from its own cache, and the release binaries' one set of crates from outside the workspace -- rustls, ring and webpki-roots behind their default `tls` feature -- is either there, as on a machine that built the tag, or the build stops naming them and the `cargo fetch --locked` that brings them once. `write` runs the binaries, and writes `SHA256SUMS` last. The server writes a file whose image and log hold every record kind a server's writes take, every change a field record names, a block holding every schema change a block takes, every type tag, a collection (`shapes`) holding every alternative a schema's field writes -- `required`, each combination of a collation, `nocase` and a `@text` beside another index, each text index's options, a list of every type a list takes, a descending part of an index over several fields, a path's every index -- statements of every op among them (a binding of each set of events, a scheduled slot that ran and one refused, schedules of months, a cron, a named zone and an offset, a webhook consumer's event), and its own collections (`_idempotency`, `_consumers`, `_migrations`, `_hook_events`), a collection whose highest row was deleted before the compact (the image's id counter past every live id), numbers past their type's range the release stored (`edges`: a float of `1e400` stored as infinity, a vector's component of `1e39` an f32's, an f16's of 70 000 its own, in fields and lists, and a named statement whose text holds `1e400`, each answered as the release answered it, `null`), numbers below zero (`signed`: ints and times before 1970 in fields, lists and json, ordered indexes across zero) and an index of every kind that takes options with each away from its default (`tuned`: `@text`'s k1, b, prefix and prefix_min on each kind and beside a `@hash`, `@hnsw`'s metric, m, ef_construction and ef_search, plain and int8; rankings and prefix matches that move if one is read as its default); a replica's file of it and that file promoted; a checkpoint's graphs of every metric, precision and quantization -- a bit index's codes and centres past the 2 048 vectors it codes at, tombstones in each arena, aliases, an 8-byte document id; a graph of 70 000 vectors (`graph-wide`, one dimension, `m=2`), whose record takes links and steps of three bytes; two sealed backups, one past a mebibyte in two frames, a sealed archive and a plain one, what `fennec verify` said of each and what the release's `fennec restore --to` said and answered at every moment a later build restores them to (`<archive>.restores.json`); a mirror of a PostgreSQL table (`--follow`, against a container of the writer's own from the Makefile's `PG_IMAGE`, pulled by nobody); a tenant node's archive of every tenant (`fennec archive --tenants`) -- a line a tenant, one moved aside as `<tenant>.<history>/` when a tenant was deleted and made again, `began` written by `fennec prune`, `presence` noting a tenant gone and back -- and what the release's `restore --tenants` said and answered at the end and at moments between the node's changes; files the release writes that a later build reads otherwise on purpose (`deep`, `refused-lists`, `refused-dims`, `points-deep`: docs/design/crates.md); and, started again on its file, its answers over HTTP. The shell writes a file of its own; the web client its IndexedDB records, OPFS file and the copy beside one a rewrite stopped in the middle of leaves (`<name>~`), a replica's sync with the release's server and a migration among them, through stand-ins for both stores (`tools/compat/web.mjs`); and the release's @fennecdb/cloudflare its Durable Object storage, a SQLite-backed object's generation table and a key-value backed one's record and pieces (`do-sql.json`, `do-kv.json`), over the module's own stand-ins (`fakes.js`, on `node:sqlite`), in pieces of 2 KB where a real object's are 2 MB so an image and the writes after it span several (`tools/compat/cloudflare.mjs`); this tree's module restores each, answers as the release's did, writes, persists, restores and compacts it. The answers are `json::response_to_string`'s, read by the release's engine from each file opened read-only (a sealed file or an archive restored first by its `fennec restore`), the page's `run`'s, and the server's bodies.

The plan's next item, T3, runs v0.2.0's released Linux binaries against HEAD in CI: there a real Linux server's files, its sync log among them, a tenant node's directory and a router's file meet HEAD.

A later build holds each file to its checksums (a torn one refused naming its damage), opens it as a tool does and as a server does, answers every statement alike, writes two rows into every collection -- a value in every field, each found through its index by that index's own operator, a path into a json field and an index over several fields among them -- reads them back, and again once opened anew (the release's records and this build's after them, as a server upgraded in place reads its file), takes them out, answers alike, compacts -- this build rewriting the release's rows -- opens again, answers alike and verifies the file; a replica's file is held to refusing a write of its own. Three opens and one compact a file: each close and compact is an fsync, `F_FULLFSYNC` on macOS, most of what a file costs. `fennec verify` reads every file as it lies and once this build wrote into it and compacted it, fennec-core holding those answers. Every graph the file keeps is restored rather than built again (`Persisted`), a rebuild answering a small `near` alike; one no later write touched serializes back to its record's bytes. A copied sync log is stamped with its copy's device and inode first: a log names the file it was written beside, so a copy's is never applied, which the test asserts before the stamp; the log's opens run on a Unix alone, no Windows build reading a log. An answer that differs is a finding: fixed, or named in `tests/compat/answers.rs`'s `ACCEPTED` with the change and why, never written again. `FENNEC_COMPAT_SETS` points every `compat::` test and the web test at a directory of sets `write` has just written, held to them before it lands; a directory holding no set, a set itself (its `archive/` no set), a set with no README or sums, or a file asked fewer than four statements fails, never passes over nothing.

The walk (`crates/fennec-core/tests/compat/walk.rs`) reads every byte of every file of a set by the release's own layout, written from its encoders, never through this build's readers: each record's head, claim and sum, each kind's body to its end -- a schema's places and each field's tags, type, `required` byte, index, paths and the indexes over several fields; each frame and every value in it, held to its schema's places; a graph record; the id counter's index of the frames and its shares; a history; a block's, a spill's and a land's records; a field change; a statement record of each op, past its op to its end; a close's mark -- and the files around them: each sync log's header, this generation's entries (put back into the file's bytes and held to this build's own reading of the log) and what follows them, an earlier pass's bytes or an entry torn; the page's IndexedDB records, the sealed ones turned back by the walk's own AES (FIPS-197's and GCM's vectors hold it); in fennec-http's walk, a seal's frames and each archive's names, images, segments and history, the plaintext through this build's `seal.rs`. A byte nobody read fails naming its file and offset, as does a record kind, a tag, an op or a flag byte the release writes none of. Where a byte changes no answer, this build's reading of it is held to the walk's: every claim through `engine::checked_claim`, the point it names to the byte, and every collection's schema as an open reads it -- each field's `required` byte, collation, `nocase`, index and the `@text` beside it, each index over several fields unique or not and each part descending or not (`every_claim_a_release_wrote_reads_as_its_bytes`, `every_schema_a_release_wrote_reads_as_its_bytes`). Where the open's own reading of a claim decides what it reads -- the durable point, below which it reads records unchecked and past which it cuts damage -- `torn-wide.fennec`'s answers hold it, both ways: a two-byte claim read as naming an earlier point refuses the open at its synced flipped row, one read as naming a later point keeps the page past the fsync a power cut lost. `RELEASES` there holds the walk to each release both ways -- for v0.2.0 record kinds 1 to 14, statement ops 1 to 6, graph versions 9 and 10, schema tags 1 to 12 and 14 to 18, value tags 0 to 10, 13 and 15, index kinds 0 to 11, each in a file and none other in one -- and `ALTERNATIVES` names every form inside them the walk tells apart (the claim and head varint widths, each kind's body's forms, a field's every tag and flag byte, each list type and how deep lists nest, a value nested past 64 levels, an image's id counter at or past the live ids, the server's own collections, each scheduled timing alive at a file's end and its mark, the sync log's ends and its header spent or never begun, a seal's frames, an archive sealed or plain, a node archive's lines, `began` and `presence`, the page's records and a rewrite's copy), each in a file of the newest release's set, held both ways, or absent with why, which the set's README names. The README states the count -- forms held, named absent and the numbers of `RELEASES`' line -- as `tools/compat_fixtures.py` derives it from the line, and `every_form_a_release_writes_is_held_or_named_absent` derives it again and holds the README to it: a number no sentence keeps by hand. For v0.2.0, absent: claims of 3 and 4 bytes and a record length of 5 (256 MiB to 64 GiB of file), graph links and steps of 4 bytes (a graph past 16 777 216 nodes); and what v0.2.0 itself refuses to write, named so a reader does not look for it -- an `@hnsw`'s `m` past 32 767, a field's own vector of 0 or past 10^9 dimensions, a list's `[vector<0>]` from FennecQL.

A landed set's README, its list of absent forms among them, is under its sums and is never amended, as no file of the set is: its `RELEASES` line pins the SHA-256 of its `SHA256SUMS` (`sums`), so a set written again whole, its sums with it, fails every `compat::` test (`every_release_named_has_its_set_in_the_tree`, with the walk's own SHA-256 held to FIPS 180-4's vectors) and `make version`, as a file changed under its sums does. The alternative was to keep the README out of `SHA256SUMS` so a later finding could amend the list; it was rejected because the list is a statement about what the release's files hold, and one made after the release is one no file of the set can bear out. A set can be added to instead: a form found after a set landed that the release writes is held by a further set of the same tag, `v<version>+2/` (then `+3`), a directory with its own README, sums, manifest and pinned line in `RELEASES`, written by binaries built from the same tag commit with the statements writing the form added -- the first set as it landed beside it. The tests and the table go over sets: every alternative is placed by the newest release's sets together, in a file of one or absent from it with why. So the first set's list is reviewed before it lands, and is still made as whole as it can be. A release candidate gets no set: its files carry no promise -- a candidate is tried on copies -- and the release's set is written by the release's own binaries, which is what later builds are held to; a change to a file format between two candidates is named in the later candidate's notes (RELEASING.md). A set with no line fails, and so does a line with no set in the tree, whichever sets `FENNEC_COMPAT_SETS` names; `tools/test_version.py` fails it too, from v0.2.0's on, a later set beside it or not. A later release's set deleted together with its line passes all of those, so `make version` also asks the tags: every release this clone has the tag of from v0.2.0 on, a release candidate's aside, has its whole set in the tree -- whole meaning its sums hold and it holds a database file beside the release's answers, a README and its sums alone being no set (`tools/version.py`'s `sets_of_tags_problems`, `tools/test_version.py`). A release writing something new adds the statements writing it, its forms to `ALTERNATIVES` and its line to `RELEASES`, before its set is written.

The suites: fennec-core's `compat::` took 4.5 s in a debug build on an M1 at rest (the one run the machine was quiet for) before `graph-wide`'s 70 000 nodes, restored and walked, and a Durable Object's two stores joined the set; with them, under other builds' load (15 to 18), fennec-core's took 31 s, fennec-http's 4.5 s, fennec's 14 s, fennec-server's 2 s and the web test 2 s. fennec-core's answers test and fennec's run each file on a thread of its own. The Windows jobs run the four Rust suites well inside their bounds (`.github/workflows/ci.yml`).

What cannot be the same twice is written once: a history's id (random at a fork, a promotion and a restore), a seal's and AES-GCM's nonces and a sealed page's generation, a scheduled slot's time, a hook's arrival, a kept key's time, a queued sync write's key, an archive's file names and times, a node's moments, the PostgreSQL slot's positions, and the sync log's generation and identity. The sync logs are their fixed 260 KB as written; `backup-wide.sealed` is a mebibyte of ciphertext nothing compresses, the one part of the set git stores at its size.

The answers are read at a fixed clock, the set's `clock` file (2026-03-01T00:00:00Z), by the release's writer and by every later build's tests: a scheduled statement's `next` is computed from the clock, and no other answer moves with it. A statement's schedule and last mark, a history's forks and change numbers and each collection's next id are held to the walk's reading of their bytes too (`every_statement_and_mark_a_release_wrote_reads_as_its_bytes`, `every_history_a_release_wrote_reads_as_its_bytes`, `every_collection_hands_out_the_next_id_its_release_would`), the next ids also to the release's own answer (`<name>.ids`), at an open and at the first row put into each collection. A spent sync log beside a file cut below its entries is read as the cut file (`a_spent_sync_log_is_never_put_back_again`). An archive restored by this build to every moment the release's own `fennec restore --to` was asked -- before its image (refused), at its image's time, the image alone before the first write, each write's time and the moment before the next, which the walk's times hold the record to covering -- stops at the release's change, says what it said and answers `restore.fennecql` as the release's restore did (fennec-http's `compat::` through the archive's API, fennec's through the binary, exit status and words), and `fennec verify` says of each archive what the release's said, whole (`<name>.verify`). A sync log is put back only over the bytes it fingerprints: each begun log of a set, stamped as its copy's, is put back, and not once a byte below its `base` changed (`a_sync_log_is_put_back_only_over_the_bytes_it_fingerprints`).

The files a later build reads otherwise on purpose (`answers.rs`'s `ON_PURPOSE`) are held by a test of their own and passed over by the rest (`the_files_this_build_refuses_on_purpose_are_refused_in_its_words`): `deep.fennec` opens, the statements its entry names -- `get deep where n = 2`, the row nesting 66 levels -- each refused in the words "a value nests more than 64 levels deep", and every other statement over the file, the deep collection's count, its other row and its field before the deep one among them, answering as the release did. On copies of it, a step each and the file opened anew after each write, the test holds what stands on 1.x ([below](#what-1x-does-not-read-of-020s-files)): a `del` of the row, a `set` of it and a `put` writing over it refused in the same words, every answer unchanged; a `compact` taken, copying the row as it is, every answer the release's once the file opens again; `alter collection deep drop field j`, its last field, taken and the row then read, but a `compact` refused in the same words, and again while the row's record is in the file -- copying the row skips the dropped place, and that skip is depth-bound -- so dropping the field never frees the file by itself; once the row is deleted, or written over, a `compact` taken; and `j` dropped with a field added after it, the row and its `del` refused again, the collection's other row read, and the collection dropped, the ordinary one answering as it did. `refused-lists.fennec` (a schema's type read past the bound), `refused-dims.fennec` (a list's vectors past a dimension's range) and `points-deep.fennec` (a point under 64 lists, 65 levels) are refused at the open, read-only and to write, in their words. `fennec verify`, which holds records to their sums and decodes no schema, says each of the four is whole.

## Not frozen

- The Rust crates' API: none is published, and `fennec-core`'s items change in any release. Their behaviour through the frozen surfaces is what holds.
- `fennec-wasm`'s exports: internal to `@fennecdb/web`, which ships `web/fennec.js` and `web/fennec.wasm` together.
- The IndexedDB and OPFS layout. A page's stored data restores in every later 1.x; how it is laid out may change.
- The studio's pages and the desktop app (beta). The studio's calls are the API's, frozen as it is.
- Measured numbers, benchmarks and their harnesses, `examples/`.
- 0.x: it promises nothing, and a 0.x client has no compatibility with a 1.x server.

## Upgrade order

Replicas before primaries, and files go one way. `deploy/RUNBOOK.md`'s *Upgrading with no downtime* is the long form: archivers, then routers, then every node holding a replica or standby, then primaries.

1. A newer replica follows an older primary: it reads every record the older one writes, and holds [the four exceptions](#what-1x-does-not-read-of-020s-files) as a newer server holds them -- the deep row taken in an image and refused where it is read, a write touching it not applied, the replica connecting again from 100 ms to 5 s apart until the primary stops writing it.
2. An older replica meeting a record kind or tag it does not know stops in words, never reading it as another: it refuses the write ("record kind 13 is not a write") and connects again, an archiver keeps the stream's bytes and takes no image of its own, and an older `verify` or `restore` refuses what it kept. Where the older binary names the kind, the tag or the version, it names it; where it knew of no other -- 0.2.0 meeting a version 2 sealed file -- its words name nothing ("not a sealed file"), and the release's notes name it instead. `make upgrade-check` drives it by hand against the commits before kind 13, its ops and the checksums; `compat.yml` against the last published release's binaries ([the matrix](#the-compatibility-matrix)), where none is new since 0.2.0: every kind, tag and op of the tree is written by a new primary and the old replica follows them all.
3. A newer file's first use of a feature, not its install, is what an older binary refuses: kind 13 at the first `create statement`, tag 18 at a field's second index. Roll forward; a rollback is promised only before a feature's first use.
4. Every reader of a file or a stream -- a replica, a standby, an archiver, a router, a node, the `fennec` that verifies and restores -- upgrades before any primary. A binary one release back beside a newer one works or stops in words, never reading wrong (point 2 says what its words name); a newer reader reads what an older writer wrote but for the four exceptions (RELEASING.md, *Every reader upgrades before any primary*). Where one node holds both primaries and replicas -- a `--dir` node holding its tenants' primaries and another node's tenants' standbys -- it cannot be upgraded as a reader before every primary: in such a fleet nothing uses a feature that moves the format until every node runs the release.

## What 1.x does not read of 0.2.0's files

1.x opens every file written from v0.2.0 on but for four kinds of value or type, each one 0.2.0 took and no write makes any more (`Schema::new`, the parser, `value::held`), refused where it is read because reading it would put back what the limit closed ([crates.md](crates.md#how-deep-a-value-nests): a decoder recursing a level at a time, which a record of nested lists overflowed the stack with; [crates.md](crates.md#limits) for the ranges). fennecdb is alpha, with no user's file to keep; v0.2.0's fixture set holds one file of each, written by its own binaries (`deep`, `points-deep`, `refused-lists`, `refused-dims`).

1. **A `[[json]]` field's row nested past 64 levels** (`[[json]]` took a json value of up to 64 levels inside its two lists, 66 in all). The file opens and every other collection reads. A statement that decodes that row fails whole, answering `{"error":"a value nests more than 64 levels deep"}`; `count`, a read of another row by its id, and the fields stored before the deep one (`select name`) still answer. A `del` or a `set` of the row is refused in the same words, the count unchanged; `alter collection ... drop field` of the deep field is taken and helps only where no field is declared after it: every skip of a dropped place goes through `codec::skip_field`, which refuses a list, an object or a point at depth 64 exactly as the decoder does, so the fields stored before the dropped one read, and any field after it -- one stored after it or one added later, whose place is reached by skipping it -- is refused in the same words, a `select` of it and a `get` of every field alike, and so is a `del` of the row; an index built over a later field is refused in the same words. A backup and an image sent to a replica carry the row unchanged. A newer replica takes such a file in an image, holds the row and refuses its reads alike; a write of the primary's touching the row is not applied, and the replica connects again, 100 ms to 5 s apart, while the primary sends it. On 1.x alone the way out is, where the deep field is its collection's last (nothing is declared after it), to drop it and `del` the row (or write over it); and where a field is declared after it, to read the readable rows out (`select` the fields before the deep one, or every row by id but it), drop the collection and make it again (a3 drives both).
2. **A type nested past 64 lists** (`[[[...int...]]]`, which no version bounded): the schema is refused as it is read, and with it the whole file at the open (`could not open ...: corrupt: a value nests more than 64 levels deep`, exit 1).
3. **A point's type under 64 lists**: a point reads as the list `[lon, lat]`, a level of its own, so 64 lists around a `geo` are 65 levels: the whole file refused at the open, as 2
4. **A schema's number past its range**: an `@hnsw`'s `m` under 2 or past 32 767, a `vector<N>` or a `sparse<N>` whose dimension is 0 or past 10^9, a list of such vectors: the whole file refused at the open, as damage (`Schema::decode`, by the test `Schema::new` asks too, `schema::out_of_range`; [crates.md](crates.md#limits)).

Only 0.2.0 can rewrite a file of kinds 2 to 4. **The advice, which the first 1.x release's notes carry:** rewrite such values with 0.2.0 before upgrading -- the row's value made shallower or the row deleted, the field or the collection made again within the ranges. `compat.yml` drives 1 and 2 with 0.2.0's own binaries writing them (a3 and a3b; a3 drops the deep field in both layouts, a row whose deep field is the last of its collection and one with a field after it). The engine's tests hold the four refused with the stack whole: the deep row by `tests/damage.rs`'s `a_record_nesting_past_the_limit_is_refused_where_a_file_is_opened`, `an_open_reading_past_a_value_nesting_past_the_limit_is_refused` and `a_primarys_record_nesting_past_the_limit_is_refused_by_its_replica`, and `codec.rs`'s `a_value_nests_no_deeper_than_json_may_be_written` (the decoder, `skip_value` and the `skip_field` a dropped place goes through); a type of 65 lists by the same codec test (`decode_type` at 65 and at 100 000 lists); a point's type by `tests/damage.rs`'s `a_point_past_the_depth_a_type_nests_is_refused_where_a_file_is_opened_and_applied` (read into memory, mapped and applied by a replica) and `codec.rs`'s `a_point_is_a_level_as_the_list_it_reads_as`; the ranges by `tests/damage.rs`'s `a_schema_past_the_languages_ranges_is_refused_where_a_file_is_opened_and_applied` and `fennec-ql`'s `tests/numbers.rs` `a_field_made_out_of_range_before_is_refused_at_the_open`; and v0.2.0's own files of each, every build, by fennec-core's `compat::the_files_this_build_refuses_on_purpose_are_refused_in_its_words` (the deep row's steps on copies, the other three at the open).

## The compatibility matrix

`compat.yml` runs `make compat-check`: this tree's `fennec-server`, `fennec` and `fennec-shard` beside the last published release's, through `tools/compat-matrix.sh OLD_BIN_DIR NEW_BIN_DIR`. It runs weekly, on every release tag and by dispatch (naming the release, else the published release, not a draft nor a pre-release, highest in version order up to this tree's version and not tagged at this commit), on Linux x86_64; it is not part of `ci.yml`, no merge waits for it, and a release needs its run on the release commit green (RELEASING.md). Each case prints a line a part, `ok` and what it held or what differed, and a failure prints its logs' tails and uploads them.

**The old side.** `tools/release-bins.sh TAG OUT_DIR` takes the release's tarball for the machine (`fennec-<tag>-<target>.tar.gz`, the musl one on Linux) and its `SHA256SUMS` -- by `gh release download`, as `ci.yml`'s latest-release job does, or from a directory already holding them (`OLD_ASSETS_DIR`) -- and installs `fennec-server` and `fennec` from them through `site/install.sh`, served from 127.0.0.1: the checksum check is the installer's own, the one a user meets, not a third copy of it, and a tarball with a byte flipped is refused with nothing installed (`tools/test_release_bins.sh`, its own test, run by the fmt job and before the matrix). No release ships `fennec-shard` (`release.yml` packs `fennec` and `fennec-server`), so the old router is built from the tag's sources (`git archive`), with the tag's `Cargo.lock` (`--locked`) and this tree's toolchain, a debug build kept in `target/compat-shard` so the cargo cache holds its dependencies: the code the release was cut from, not a binary it published -- "the last release's binaries" means that wherever the matrix's result is quoted. Each binary's `--version` is held to the tag, and nothing reaches `OUT_DIR` before all three are; since both trees may say the same version, the run's first lines tell them apart by path and SHA-256, and a run whose two sides are the same bytes stops. A `gh` that fails stops the script, never read as "no release". A script beside `tools/upgrade-order.sh` rather than its `OLD_BIN_DIR`: that script's cases hold binaries from before kind 13, its ops and the checksums to refusing them, and 0.2.0 has them all, so its binaries there would fail every case by reading what each was written to see refused; its bases stay commits.

**What it drives.** Every write of a case comes from one history, `HISTORY`, and `FORMAT` holds every record kind (`REC_*`), type tag (`TAG_*`) and op (`OP_*`) -- every `u8` constant of those prefixes in any file under `crates/fennec-core/src`, whatever its visibility -- to the write that makes it, or to why none is needed: a kind no write makes (the image's counter, next ids and graphs, which a1's and a2's replicas take in an image; the history; a file's close mark, which c2's file carries), a spilled block and its landing (never sent, and a 16 MB write in every case's history costs more than it shows), and a schedule's mark (written by the clock: a slot each second would move the counter between writes, by which a2 places its replica). The self-test fails on a constant FORMAT does not name, so the next kind, tag or op cannot be forgotten. The other numbered spaces a file or a stream carries are tables of their own, each held both ways (a code with no line, a line with no code) and each line a write of `HISTORY` or a reason: `GRAPHS`, the graph record's versions (`GRAPH_VERSION*` constants; 9 is written into an image, 10 by a server's own saving, 3 to 8 are read only, held by vector.rs's tests that write and restore the older layouts); `INDEX_KINDS`, the byte behind a field's index, a literal in `encode_index`, so the check reads `encode_index`'s `out.push(N)`s and `decode_index`'s match arms and requires the two lists to be one and the table to be it; `SMALL_CODES`, the metric, quantization and collation codes, read from their `from_code` arms; and `STREAM`, the replication stream's message tags, `b'X'` literals the primary writes and the replica matches in `replication.rs`, the two lists one and the table to be it. A function that moves from where the check reads it makes the table fail as empty, never pass; the self-test mutates a copy of each source (a code more, a code written and not read) and each table (a line more). `HISTORY`'s `indexed` collection makes the index kinds, metrics, quantizations and the second collation that `kinds` does not; a release that adds one adds its write and its line; a release that adds one the last release does not read adds its write's text to `UNKNOWN_TO_OLD` with the words its old replica must stop with, the number named where the old binary names it. Each state compared is the same reads -- every collection, `call`, `describe`, `statements`, a `nocase` `where`, a `match`, a `near`, a collation's order and an index over several fields -- each answer normalized, any refusal reduced to `"error"`, a score and a schedule's `next` and `last` left out, so two versions' words never differ a state.

**What holds the harness.** A case runs in a subshell under `set -eE`: a command failing anywhere is written down by its line whatever the case printed before, a case exiting other than 0 fails, and each part a case owes (`CASES`, written once) must print exactly one line: a part unsaid fails by name, and the run ends held to every part of the cases it ran. `--self-test` holds this with toy cases and no binary -- a case dying after its first part, one printing a part too few, one dying in a command substitution (b2's path with no image), one printing a part not its own, one dying on an unset variable after every part, one exiting other than 0 with every part said and its sentinel written (the status check alone), one failing a check in a helper used as an `if` condition, each failing the run -- and every table to the tree and to a tree with a code more or a line more. Two things about bash 3.2, which runs `make compat-check` on a Mac, are held: a subshell with an `EXIT` trap that dies on `set -u` exits 0, so each case writes a `finished` sentinel after it returns and the run requires it beside the parts; and `set -e` does not act in a function used as an `if` condition, so a check in a helper is `|| fail`, never a bare command. The script is held to that bash and to the Linux runner's, the self-test run under both. A server that must refuse to start (a3b, f1) is started in the background and waited for by its exit or its `listening on:` line, bounded: one that listens fails the case by name rather than hanging the job. A state compared across releases is held by the older release's answer (`state_holds`: every key it has, with its value, so a field a later release adds to `describe` or `statements` is no difference), and every state a case compares is first required to be answers, none a refusal.

**What it cannot drive.**

- Other platforms in CI: Linux x86_64's musl tarball alone. `make compat-check` on a Mac takes the darwin tarball (the local run below); Windows not at all, `install.sh` installing no zip.
- More than one release back: the old side is one release.
- The release's own router: none is published, so the router's case is its tag's code, built by this tree's toolchain.
- The sync client's side: `token_expired` (a client told its token is past `exp`) and a seed sent in parts past a mebibyte (#665) are the native library's and the browser module's, neither in the release's tarball nor reachable from a shell; an old client against a new server is T4's, and both runners of this tree are held to the scenario file (`make sync-scenarios-check`).
- A copy keeping its primary's write times (an archive cut from a replica of the other release, restored to a moment): b's archivers follow the primary.
- A replica's follow record synced before the follow is answered: e restarts the standby's node gracefully, and the new node reads as a copy what the old one made to follow; that the record was on disk under a kill is the power-cut rig's.
- A failover between nodes of two releases, by hand or under `--auto-failover`; regions, the global entry and read replicas; `fennec archive --tenants`; the mirror (`--follow`); each SDK against a server of another release (T4); a power cut across an upgrade.
- This tree's release build: the matrix drives debug builds of this tree, behaviour and not speed.

### What it found against 0.2.0

Driven on 2026-11-15 against v0.2.0's aarch64-apple-darwin tarball and the router built from its tag (`e5d5424e`) by this tree's toolchain, beside debug builds of this tree (main and the next landings at `65ac238f`, #665's seeds in parts among them), on macOS, every part held:

- **Nothing is new since 0.2.0 in the format.** Record kinds 1 to 14, type tags 0 to 18, kind 13's ops 1 to 6 and the data records' two ops are the same in both trees (`FORMAT`, read from `crates/fennec-core/src`), so the old replica follows a new primary through every write to the primary's change counter (a2), and kind 13 and tags 11 to 18 are driven as writes 0.2.0 reads, not ones it stops at. `UNKNOWN_TO_OLD` is empty.
- **Promised, and held in the promised words.** A sealed archive and backup of this tree are version 2, which 0.2.0's `fennec` refuses ("not sealed, where the archive is", "not a sealed file"), naming no version and writing nothing (b4, c3); a hooks file's `key delivery` stops the new server, exit 2 (f1), and a kept set's events are answered 409 until it is set again (f2).
- **The four exceptions, decided.** 0.2.0 takes a `[[json]]` row nested 66 levels deep and reads it; this tree refuses it where it reads it, as [crates.md](crates.md#how-deep-a-value-nests) chose -- reading it would put back the unbounded recursion the limit closed, and fennecdb is alpha, with no user's file to keep -- and holds everything else of the file (a3, exception 1's list). A type of 65 nested lists, which 0.2.0 takes, refuses the file at the open (a3b). This contract names the four [above](#what-1x-does-not-read-of-020s-files); the first round's run, which found the row before they were named, failed a3 until they were.
- **The rolling upgrade (e)**: 208 writes sent through the router, 206 acknowledged and every one read back from the primary and the standby, 2 not sent (no connection while the router restarted, or the router's "was not sent" while the primary's node did; a run of e alone saw one, curl's exit 7 as the router restarted) and neither landed, none unknown, no `seq` twice; 50 writes acknowledged after each step, the standby caught up by the runbook's condition before each node. The counts move with the machine's speed and a restart's timing; the classes' rules do not.
- **Where RELEASING.md was not exact enough to follow**, written there and in the runbook since: a node pair's standby's node goes first; the wait between two nodes' restarts is the standby's status (connected, `behind` 0) or the primary's listing (`sent` its `durable`), not `FennecTenantsWithoutReplica`, which counts only a tenant with no copy at all over 15 minutes; a node holding both primaries and replicas cannot be a reader upgraded before every primary; restarting a primary's node in place costs its tenants' writes for the restart; and "upgrade every router" means building it from the tag, no release publishing `fennec-shard` yet.

## The grammar epoch

`GRAMMAR_EPOCH` is `pub const GRAMMAR_EPOCH: u32 = 4` in `crates/fennec-core/src/named.rs` (`fennec_ql::GRAMMAR_EPOCH` is that one). A named statement is stored as its text, the epoch it was parsed under and its tree's digest; an open parses it again and marks it broken, its calls refused until it is defined again, where the digest differs. It was 4 at v0.2.0 and is 4 now, but 2, 3 and 4 each marked stored definitions broken. Under 1.x:

- The epoch stays 4. A change that would raise it is not made.
- A text a 1.x release read is not refused by a later 1.x: the corpus holds a refusal to the epoch as it holds a moved digest. Against a 0.x base -- v0.2.0's corpus, main before 1.0 -- a refusal whose stored reading holds is let through by an `ACCEPTED` entry alone ([fennecql.md](fennecql.md#the-corpus)).
- A text a 1.x release read is read alike by a later 1.x. A schema change, a listing or a `call` is compared by a hash of its tree's form, which moves where the tree changed shape and the meaning did not -- a field renamed -- as where the meaning changed; so against a 1.x base one read otherwise passes only with the epoch raised, or with an `ACCEPTED` entry's `same_meaning`: why it means what it meant, a claim the corpus prints for the review to judge. Against a 0.x base an entry alone is enough.
- Raising it is a major version, and its notes name the stored statements it breaks.
- A statement an open marks broken under a 1.x release is a bug in that release.

## Support

The latest 1.x minor gets every fix. The previous minor gets security fixes for six months after the next minor's release. `release/1.N` branches are cut when a backport needs one. Release candidates are tagged `1.0.0-rc.N`; the owner pushes tags.
