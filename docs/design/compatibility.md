# The 1.x compatibility contract

What fennecdb 1.x promises, surface by surface, and the check that holds each promise today. The rule across them is one sentence: **a 1.x release only grows a frozen surface, and a break is a major version.** A surface no check holds yet names the item of the 1.0 plan that adds it; until that item lands the promise is held by review alone, and the table says so.

This file holds no invariant of the code on its own: each row's rule lives in the CLAUDE.md of the area that enforces it. The user's page is [site/content/docs/compatibility.html](../../site/content/docs/compatibility.html); what a release must check is RELEASING.md's *1.0* section.

## What grows, what breaks

*Grows* is an addition no existing caller, file or peer can meet as a change: a record kind or type tag a file takes only once a feature uses it, a route, an optional field, a flag, a statement. *Breaks* is anything else: a record or tag removed or reread, a statement that read one way and reads another, a route, field, flag, exit code, metric name or exported symbol removed or changed in type, a release asset renamed. A deprecation is not a removal: a surface is deprecated in a minor, kept through the rest of 1.x, and removed only in 2.0.

A feature whose first use moves the file format -- it writes a new kind or tag -- is named in that release's notes, because an older binary refuses the file (see [the upgrade order](#upgrade-order)).

## Not frozen

- The Rust crates' API: none is published, and `fennec-core`'s items change in any release. Their behaviour through the frozen surfaces is what holds.
- `fennec-wasm`'s exports: internal to `@fennecdb/web`, which ships `web/fennec.js` and `web/fennec.wasm` together.
- The IndexedDB and OPFS layout. A page's stored data restores in every later 1.x; how it is laid out may change.
- The studio's pages and the desktop app (beta). The studio's calls are the API's, frozen as it is.
- Measured numbers, benchmarks and their harnesses, `examples/`.
- 0.x: it promises nothing, and a 0.x client has no compatibility with a 1.x server.

## Upgrade order

Replicas before primaries, and files go one way. `deploy/RUNBOOK.md`'s *Upgrading with no downtime* is the long form: archivers, then routers, then every node holding a replica or standby, then primaries.

1. A newer replica follows an older primary: it reads every record the older one writes.
2. An older replica meeting a record kind or tag it does not know stops by name, never reading it as another: it refuses the write ("record kind 13 is not a write") and connects again, an archiver keeps the stream's bytes and takes no image of its own, and an older `verify` or `restore` refuses what it kept. `make upgrade-check` drives it by hand against the commits before kind 13, its ops and the checksums; `compat.yml` against the last published release's own binaries ([the matrix](#the-compatibility-matrix)), where none is new since 0.2.0: kind 13's ops 1, 3, 4 and 6 and tags 17 (`nocase`) and 18 (a text index beside another) are written by a new primary and the old replica follows them all.
3. A newer file's first use of a feature, not its install, is what an older binary refuses: kind 13 at the first `create statement`, tag 18 at a field's second index. Roll forward; a rollback is promised only before a feature's first use.
4. Every reader of a file or a stream -- a replica, a standby, an archiver, a router, a node, the `fennec` that verifies and restores -- upgrades before any primary. A binary one release back beside a newer one works or stops in words naming what it does not know, never reading wrong; a newer reader over an older writer always works (RELEASING.md, *Every reader upgrades before any primary*).

## The compatibility matrix

`compat.yml` runs `make compat-check`: this tree's `fennec-server`, `fennec` and `fennec-shard` beside the last published release's, through `tools/compat-matrix.sh OLD_BIN_DIR NEW_BIN_DIR`. It runs weekly, on every release tag and by dispatch (naming the release, else the newest published one before this tree's version, not one tagged at this commit), on Linux x86_64; it is not part of `ci.yml`, no merge waits for it, and a release needs its run on the release commit green (RELEASING.md). Each case prints one line, `ok` and what it held or what differed, and a failure prints its logs' tails and uploads them.

**The old side.** `tools/release-bins.sh TAG OUT_DIR` takes the release's tarball for the machine (`fennec-<tag>-<target>.tar.gz`, the musl one on Linux) and its `SHA256SUMS` -- by `gh release download`, as `ci.yml`'s latest-release job does, or from a directory already holding them (`OLD_ASSETS_DIR`) -- and installs `fennec-server` and `fennec` from them through `site/install.sh`, served from 127.0.0.1: the checksum check is the installer's own, the one a user meets, not a third copy of it. No release ships `fennec-shard` (`release.yml` packs `fennec` and `fennec-server`), so its router is built from the tag's sources (`git archive`) with this tree's toolchain: the code the release was cut from, not a binary it published. Each binary's `--version` is held to the tag. A script beside `tools/upgrade-order.sh` rather than its `OLD_BIN_DIR`: that script's cases hold binaries from before kind 13, its ops and the checksums to refusing them, and 0.2.0 has them all, so its binaries there would fail every case by reading what each was written to see refused; its bases stay commits.

**What it drives.** Every write of a case comes from one history: a write of each record kind a write makes -- a create, puts, a set, a delete, a block, an alter, a drop -- kind 13's ops 1, 3, 4 and 6 (a definition, a binding and the row it writes, a schedule, a webhook consumer), tag 17 (`nocase`) and tag 18 (`@text` beside a `@hash`), vectors under `@hnsw`. Each state compared is the same reads, each answer normalized and any refusal reduced to `"error"`, so two versions' words never differ a state.

| Case | What it holds |
| --- | --- |
| a1 | An old primary followed by a new replica, half the history in its image and half as records: its reads the primary's, its file opened again (`--promote`, a copy) the same. |
| a2 | A new primary followed by an old replica. A snapshot of the primary is taken after each write; the replica's state must be one of them -- a prefix of the history -- and its file, opened by the old binary, the same. Where it is not the last, the write after it must be one of `UNKNOWN_TO_OLD` (a kind, tag or op the release does not know) and the replica's log must name it ("record kind", "type tag", "version", "does not read"). A release that adds one adds its write to the history and its index there. |
| a3 | An old primary's `[[json]]` value nested 66 levels deep, followed by a new replica. |
| a4 | What the old release writes and this tree refuses to: a stored definition holding `1e400`, a vector component of `1e39`; the new replica reads and calls them as the old primary does, the definition not broken. |
| b1, b2 | The old `fennec archive`'s archive, plain and sealed (version 1, its magic read), verified by the new `fennec`, restored to its end and to a moment between two writes, each restore opened. |
| b3, b4 | The new archiver's, plain, verified and restored by the old `fennec`; sealed (version 2), refused by the old `verify` and `restore` in RELEASING.md's words, no file written, and restored by the new. |
| c1 | The old `fennec backup`, plain opened by the new server, sealed restored by the new `fennec`. |
| c2 | A file the old server wrote, opened and written by the new, verified and typed (`fennec types`) by both, opened again by the old with the new writes: no format moved, so the rollback point 3 promises holds. |
| c3 | The new backup, plain opened by the old server; sealed, refused by the old restore ("not a sealed file"), no file written. |
| d1, d2 | An old router over three new nodes, and a new router over three old ones, `--replicas`: a tenant created, the history written through the router, its replica holding it, moved to the third node with its replica following a write after, and deleted from every node. |
| e | A rolling upgrade: an old router and two old `--dir` nodes, the second the first's standby (`--sync always` on the primary), one writer sending `put`s through the router and counting each answered one; the router restarted in place, then the standby's node, then -- once the standby holds every write the primary does -- the primary's, each on the release and on the port it had, as RELEASING.md and the runbook order it. At the end every acknowledged write is read back from the primary and from the standby. |
| f1, f2 | A hooks file's `github` line saying `key delivery`: the old server starts on it, the new one exits 2 naming the line. A tenant's `github` hook a 0.2.0 node kept with `key delivery`: once the router and the node are upgraded its verified event is answered 409 naming `key body`, nothing written, the node's log naming the hook, its listing saying `"key":"delivery"`, its statement not armed; set again with `key body`, the redelivery is taken. |
| g1, g2 | A node serving HTTPS recorded at `https://` by a router of the other release, a tenant on it created, written, read and deleted over TLS. |

**What it cannot drive.**

- Other platforms in CI: Linux x86_64's musl tarball alone. `make compat-check` on a Mac takes the darwin tarball (the local run below); Windows not at all, `install.sh` installing no zip.
- More than one release back: the old side is one release.
- The release's own router: none is published, so the router's case is its tag's code.
- A failover between nodes of two releases, by hand or under `--auto-failover`; regions, the global entry and read replicas; `fennec archive --tenants`; the mirror (`--follow`); the app's sync protocol and each SDK against a server of another release (T4); a power cut across an upgrade.
- This tree's release build: the matrix drives debug builds of this tree, behaviour and not speed.

### What it found against 0.2.0

Driven on 2026-11-15 against v0.2.0's aarch64-apple-darwin tarball and the router built from its tag (`e5d5424e`), beside debug builds of this tree at `881ce710` (main at #666 and the next landings), on macOS:

- **Nothing is new since 0.2.0 in the format.** Record kinds 1 to 14, type tags 0 to 18 and kind 13's ops 1 to 6 are the same in both trees (`codec.rs`, `engine.rs`, `engine/stored.rs`), so the old replica follows a new primary through every write (a2), and kinds 13 and tags 17 and 18 are driven as writes 0.2.0 reads, not ones it stops at. `UNKNOWN_TO_OLD` is empty.
- **Promised, and held in the promised words.** A sealed archive and backup of this tree are version 2, which 0.2.0's `fennec` refuses ("not sealed, where the archive is", "not a sealed file"), writing nothing (b4, c3); a hooks file's `key delivery` stops the new server, exit 2 (f1), and a kept set's events are answered 409 until it is set again (f2).
- **Not promised, undecided (a3).** A field `[[json]]`, which 0.2.0 takes, holding a value nested 66 levels deep: 0.2.0 reads the row; a newer replica stops following at it (`replication: could not apply a write: corrupt: a value nests more than 64 levels deep; connecting again`) and answers the collection's read `{"error":"a value nests more than 64 levels deep"}`, and a newer server opening 0.2.0's file opens it and answers that read the same. [crates.md](crates.md#how-deep-a-value-nests) records the refusal as deliberate, for a file only a pathological write makes; this contract does not -- the file row's "1.x opens every file written from v0.2.0 on" and replication's "a newer replica follows an older primary" say otherwise -- so a3 fails until one of them names it or the read changes.
- **The rolling upgrade (e)** lost no acknowledged write: 423 writes sent, 420 acknowledged and read back from the primary and the standby; the 3 others were refused unsent -- one while the router restarted (its port closed), two while the primary's node did (the router's "node `n1` ... was not reached ... the request was not sent") -- and none of them landed.
- **Where RELEASING.md is not exact enough to follow.** Its numbered order (archivers, routers, nodes, then primaries) is written for a feature's first use, and says nothing of a node pair: which node of a pair goes first and whether the primary's is restarted in place or failed over is the runbook's (standbys before primaries; a restart in place, a failover only where it outlasts a lease). The runbook's wait between nodes is an alert, `FennecTenantsWithoutReplica`: `fennec_router_tenants_unreplicated` held for 15 minutes, which counts a tenant with no copy at all, not a standby that is behind after its restart; the case waits for the standby to hold every write the primary does instead.

## The grammar epoch

`GRAMMAR_EPOCH` is `pub const GRAMMAR_EPOCH: u32 = 4` in `crates/fennec-core/src/named.rs` (`fennec_ql::GRAMMAR_EPOCH` is that one). A named statement is stored as its text, the epoch it was parsed under and its tree's digest; an open parses it again and marks it broken, its calls refused until it is defined again, where the digest differs. It was 4 at v0.2.0 and is 4 now, but 2, 3 and 4 each marked stored definitions broken. Under 1.x:

- The epoch stays 4. A change that would raise it is not made.
- A text a 1.x release read is not refused by a later 1.x: the corpus holds a refusal to the epoch as it holds a moved digest. Against a 0.x base -- v0.2.0's corpus, main before 1.0 -- a refusal whose stored reading holds is let through by an `ACCEPTED` entry alone ([fennecql.md](fennecql.md#the-corpus)).
- A text a 1.x release read is read alike by a later 1.x. A schema change, a listing or a `call` is compared by a hash of its tree's form, which moves where the tree changed shape and the meaning did not -- a field renamed -- as where the meaning changed; so against a 1.x base one read otherwise passes only with the epoch raised, or with an `ACCEPTED` entry's `same_meaning`: why it means what it meant, a claim the corpus prints for the review to judge. Against a 0.x base an entry alone is enough.
- Raising it is a major version, and its notes name the stored statements it breaks.
- A statement an open marks broken under a 1.x release is a bug in that release.

## Support

The latest 1.x minor gets every fix. The previous minor gets security fixes for six months after the next minor's release. `release/1.N` branches are cut when a backport needs one. Release candidates are tagged `1.0.0-rc.N`; the owner pushes tags.
