# The 1.x compatibility contract

What fennecdb 1.x promises, surface by surface, and the check that holds each promise today. The rule across them is one sentence: **a 1.x release only grows a frozen surface, and a break is a major version.** A surface no check holds yet names the item of the 1.0 plan that adds it; until that item lands the promise is held by review alone, and the table says so.

This file holds no invariant of the code on its own: each row's rule lives in the CLAUDE.md of the area that enforces it. The user's page is [site/content/docs/compatibility.html](../../site/content/docs/compatibility.html); what a release must check is RELEASING.md's *1.0* section.

## What grows, what breaks

*Grows* is an addition no existing caller, file or peer can meet as a change: a record kind or type tag a file takes only once a feature uses it, a route, an optional field, a flag, a statement. *Breaks* is anything else: a record or tag removed or reread, a statement that read one way and reads another, a route, field, flag, exit code, metric name or exported symbol removed or changed in type, a release asset renamed. A deprecation is not a removal: a surface is deprecated in a minor, kept through the rest of 1.x, and removed only in 2.0.

A feature whose first use moves the file format -- it writes a new kind or tag -- is named in that release's notes, because an older binary refuses the file (see [the upgrade order](#upgrade-order)).

## Fixture sets

A release's set is what its own binaries wrote and the answers it gave, in `crates/fennec-core/tests/compat/v<version>/`, written once from its tag (RELEASING.md's step 6, `make compat-fixtures V=<version>`) and never again. `tools/compat_fixtures.py build` takes the tag's tree alone -- nothing downloaded, no release asset, no registry, its `Cargo.lock` as released (`--locked`) -- and builds its `fennec-server`, `fennec`, module (its own `make wasm`) and `tools/compat/writer.rs` as an example of its fennec-core; `write` runs them, and writes `SHA256SUMS` last. The server writes a file whose image and log hold every record kind a server's writes take, every change a field record names, a block holding every schema change a block takes, every type tag, statements of every op among them (a scheduled slot's mark, a webhook consumer's event), and its own collections (`_idempotency`, `_consumers`, `_migrations`, `_hook_events`); a replica's file of it and that file promoted; a checkpoint's graphs of every metric, precision and quantization -- a bit index's codes and centres past the 2 048 vectors it codes at, tombstones in each arena, aliases, an 8-byte document id; a sealed backup and a sealed archive; and, started again on its file, its answers over HTTP. The shell writes a file of its own; the web client its IndexedDB records and OPFS file, a replica's sync with the release's server and a migration among them, through stand-ins for both stores (`tools/compat/web.mjs`). The answers are `json::response_to_string`'s, read by the release's engine from each file opened read-only (a sealed file restored first by its `fennec restore`), the page's `run`'s, and the server's bodies.

What no binary writes at a few kilobytes, or on the machine writing the set, the release's engine writes through `writer.rs`, by the knobs its own tests turn -- each file still one a process of that release writes:

| File | Lowered or bypassed | Why it is still the release's layout |
| --- | --- | --- |
| `spill.fennec` | The spill threshold, 16 MB (`SPILL_AT`), through `set_spill` | A spill's and a land's records are the block's own, cut where it outgrew the threshold, whatever the threshold; a block put back leaves its spills dead the same way |
| `kept.fennec` | The graph's save thresholds, 10 000 changed nodes and three times the graph's growth (`GRAPH_SAVE_CHANGES`), through `set_graph_saves`; `save_graphs` called as the keeper calls it | The thresholds say when a graph is due, not what its record holds: version 10, as a server's keeper appends it |
| `waiting.fennec` | A server's open (`fs::open_serving`) and checkpoint called back to back, before a linker runs | The race a server can lose made certain: the checkpoint's own record, nodes flagged waiting |
| `synclog.fennec`, `.sync` | The sync log, Linux's and Android's, kept on macOS (`keep_sync_log`, as the release's own tests keep it); the crash made by `mem::forget` and a truncation to the log's base | The log's format is the same on every Unix that keeps it; a power cut leaves the file at its last fsync and the rest in the log, which the cut makes |
| `torn-tail.fennec`, `torn-mark.fennec` | A crash made by `mem::forget` and a cut, or a mark's claim and sum zeroed | What a crash leaves: an unsynced append's last bytes lost, and a close's unsynced mark read back as zeros |

The plan's next item, T3, runs v0.2.0's released Linux binaries against HEAD in CI: there a real Linux server's files, its sync log among them, a tenant node's directory and a router's file meet HEAD.

A later build holds each file to its checksums (a torn one refused naming its damage), opens it as a tool does and as a server does, answers every statement alike, writes two rows into every collection -- a value in every field, each found through its index by that index's own operator, a path into a json field and an index over several fields among them -- reads them back opened again and compacted, takes them out, answers alike once more, compacts, opens again and verifies the file; a replica's file is held to refusing a write of its own. Every graph the file keeps is restored rather than built again (`Persisted`), a rebuild answering a small `near` alike; one no later write touched serializes back to its record's bytes. A copied sync log is stamped with its copy's device and inode first: a log names the file it was written beside, so a copy's is never applied, which the test asserts before the stamp; the log's half runs on a Unix alone, no Windows build reading a log. An answer that differs is a finding: fixed, or named in `tests/compat/answers.rs`'s `ACCEPTED` with the change and why, never written again. `FENNEC_COMPAT_SETS` points every `compat::` test at a directory of sets `write` has just written, held to them before it lands.

`RELEASES` in `crates/fennec-core/tests/compat.rs` names what each release writes -- for v0.2.0 record kinds 1 to 14, statement ops 1 to 6, graph versions 9 and 10, type tags 0 to 18, index kinds 0 to 11 -- and the shapes each kind holds below it, read from the release's own source: every field change (add, drop, rename, expiry), a frame's ops, an id counter with and without its frames' index, a history forked once and twice and following, a block across collections and holding each schema change, a spill landed and one dead, a close's mark, a record cut short and a mark failing its sum, claims of none and of a byte, and a graph's metric, each arena (f32, f16, int8 and bit codes over an f32 and an f16 field, a bit index holding its vectors whole), a bit index's centres, a tombstone in each arena, a waiting node, document ids of 4 and 8 bytes, links of 2 bytes, upper layers, aliases and the copies table's halves. The walk reads every byte of a graph record to its end. A set lacking one fails, as does a set with no line there; what the release writes and no file holds is named in the set's README with why -- for v0.2.0 a claim of 2 to 4 bytes (a durable point past 1 MiB), links of 3 or 4 bytes (a graph past 65 536 nodes) and `_follow` (PostgreSQL). A release writing something new adds the statements writing it, and its shape to `RELEASES`, before its set is written.

What cannot be the same twice is written once: a history's id (random at a fork, a promotion and a restore), a seal's and AES-GCM's nonces and a sealed page's generation, a scheduled slot's time, a hook's arrival, a kept key's time, a queued sync write's key, an archive's file names, and the sync log's generation and identity. The sync log is its fixed 260 KB as written, zeros past its entries.

## Not frozen

- The Rust crates' API: none is published, and `fennec-core`'s items change in any release. Their behaviour through the frozen surfaces is what holds.
- `fennec-wasm`'s exports: internal to `@fennecdb/web`, which ships `web/fennec.js` and `web/fennec.wasm` together.
- The IndexedDB and OPFS layout. A page's stored data restores in every later 1.x; how it is laid out may change.
- The studio's pages and the desktop app (beta). The studio's calls are the API's, frozen as it is.
- Measured numbers, benchmarks and their harnesses, `examples/`.
- 0.x: it promises nothing, and a 0.x client has no compatibility with a 1.x server.

## Upgrade order

Replicas before primaries, and files go one way. `deploy/RUNBOOK.md`'s *Upgrading with no downtime* is the long form: archivers, then routers, then every node holding a replica or standby, then primaries.

1. A newer replica follows an older primary: it reads every record the older one writes.
2. An older replica meeting a record kind or tag it does not know stops by name, never reading it as another: it refuses the write ("record kind 13 is not a write") and connects again, an archiver keeps the stream's bytes and takes no image of its own, and an older `verify` or `restore` refuses what it kept. `make upgrade-check` drives kind 13 today, by hand and not yet checked in CI (T3); T3 drives it with released binaries, and tags 17 (`nocase`) and 18 (a text index beside another).
3. A newer file's first use of a feature, not its install, is what an older binary refuses: kind 13 at the first `create statement`, tag 18 at a field's second index. Roll forward; a rollback is promised only before a feature's first use.

## The grammar epoch

`GRAMMAR_EPOCH` is `pub const GRAMMAR_EPOCH: u32 = 4` in `crates/fennec-core/src/named.rs` (`fennec_ql::GRAMMAR_EPOCH` is that one). A named statement is stored as its text, the epoch it was parsed under and its tree's digest; an open parses it again and marks it broken, its calls refused until it is defined again, where the digest differs. It was 4 at v0.2.0 and is 4 now, but 2, 3 and 4 each marked stored definitions broken. Under 1.x:

- The epoch stays 4. A change that would raise it is not made.
- Raising it is a major version, and its notes name the stored statements it breaks.
- A statement an open marks broken under a 1.x release is a bug in that release.

## Support

The latest 1.x minor gets every fix. The previous minor gets security fixes for six months after the next minor's release. `release/1.N` branches are cut when a backport needs one. Release candidates are tagged `1.0.0-rc.N`; the owner pushes tags.
