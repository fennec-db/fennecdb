Compatibility and upgrades

From 1.0 a release only adds to what is listed here. A change that would break one of them waits for 2.0.

What 1.x promises

A 1.x release grows a surface: a new record kind in the file, a new route or optional field, a flag, a statement. It never changes or removes what was there. A feature is deprecated in a minor, kept for the rest of 1.x and removed only in 2.0. 0.x releases promise nothing.

What is not frozen

  • The Rust crates' API. None is published; use fennecdb through the server, the shell, the C library or the browser module.
  • The browser module's exports, which belong to @fennecdb/web and ship with its glue.
  • How a page lays out its IndexedDB or OPFS data. Only that the data restores.
  • The studio's pages and the desktop app (beta).

Upgrading

Upgrade every reader before any primary, and roll forward. For a cluster the order is archivers and the shells that restore, routers, nodes holding replicas or standbys, then primaries (Sharding reference).

  • No release publishes the router, fennec-shard, yet: upgrading a router means building it from the release's tag (cargo build --release --locked -p fennec-shard).
  • In a node pair, the standby's node goes first. Before the next node, wait until the standby holds what the primary does: on the primary's node /t/<tenant>/_replication/status lists the standby with sent equal to durable, or the standby's own status says "connected": true and "behind": 0 (for a file's replica, the metrics fennec_replica_connected 1 and fennec_replica_behind 0).
  • Restarting the primary's node in place costs its tenants their writes for the restart: the router answers each that it was not sent (503), safe to send again. A router fails a node over only with --auto-failover.
  • A node holding both primaries and replicas cannot be upgraded before every primary: in such a fleet, use no feature that moves the format until every node runs the release.
  • A newer replica follows an older primary, and one a release back beside a newer primary follows it or stops in words. Each release is run beside the last one's server and shell and its tag's router, weekly and at its tag, both ways.
  • An older replica that meets a record kind or type tag it does not know stops and names it, for example record kind 13 is not a write. It never reads it as something else. Where the older release knew of no other version it cannot name it: v0.2.0's shell refuses a sealed file of the second version as not a sealed file.
  • Such a record appears when a feature is first used, not when it is installed: the first create statement, a field with a second index. The release notes name each, so upgrade every reader first.
  • An older binary refuses a file a newer one has written to. Going back is safe only before a feature's first use.

Files from v0.2.0 that 1.x does not read whole

v0.2.0 took four kinds of value or type that no write makes any more. 1.x refuses them where it reads them, rather than read them with the unbounded recursion the limit of 64 levels closed:

  1. A [[json]] field's row nested past 64 levels. The file opens and every other collection reads. Any statement that decodes that row fails whole with a value nests more than 64 levels deep; count, a read of another row by its id, and the fields stored before the deep one still answer. A del or a set of the row is refused. Dropping the field is taken and helps only where no field is declared after it: a field after it, and a del of the row, are still refused in the same words, and so is an index over a later field. Backups and a replica's image carry the row unchanged; a replica holds it and refuses its reads alike. On 1.x alone the way out is, where the field is the collection's last, to drop it and delete the row; otherwise to read out the readable rows, drop the collection and make it again.
  2. A type nested past 64 lists,
  3. a point's type under 64 lists, and
  4. a schema's number past its range (an HNSW m under 2 or past 32 767, a vector<N> or a sparse<N> of 0 or past 109, a list of such vectors): the whole file is refused at the open, and only v0.2.0 can rewrite it.

Rewrite such values with v0.2.0 before upgrading.

The grammar epoch

A named statement is stored as its text with the grammar epoch it was parsed under. An open parses it again and, where the result differs, marks it broken until it is defined again. The epoch is 4, as it was in v0.2.0, and it stays 4 through 1.x. Raising it is a major version, and its notes name the stored statements it breaks.

Support

The latest 1.x minor gets every fix. The previous minor gets security fixes for six months after the next one is released. Release candidates are tagged 1.0.0-rc.N and published as pre-releases.

A patch to the previous minor, or a release candidate, is installed by naming it: what takes "the newest" stays on the latest release. The install script and GitHub's latest release, the image's latest tag, npm's latest and the Homebrew formula keep the newest release; on npm the previous minor's patches go out under release-1.N (npm install @fennecdb/web@release-1.4) and the newest release candidate under next, and every other registry takes the version you ask for. Maven Central is the exception: while a candidate is its highest version, Gradle's latest.release resolves to it, so pin a version there.

Until 1.0.0 fennecdb is 0.x, an alpha: a security bug found in a 0.x release gets no advisory and no patch release. The fix lands on main and ships in the next release, so run the latest release. Report a vulnerability privately, as SECURITY.md says; a report is acknowledged within 3 working days.
