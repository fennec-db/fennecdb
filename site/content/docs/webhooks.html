Webhooks from Stripe and GitHub

Another service's events — Stripe's payments, GitHub's pushes, the events of any sender signing as Standard Webhooks does — taken by a statement, with no code of your own between the sender and the rows.

A statement defined on hook <name> takes the events sent to POST /_hooks/<name>. The server checks each event's signature before it reads anything of it, binds the values the statement names from the event's body to typed parameters, and runs the statement. The writes and the event's key land as one block, so a sender's retry, a duplicate delivery and a crash between the write and its answer never take one event twice. The sender is told 200 only once the event is on disk.

Webhooks are taken by a file's server (fennec-server --file) given a hooks file (--hooks). A tenant node takes none yet. For reacting to a write of your own — calling a URL when a row changes — see Functions and webhooks.

A payment from Stripe

An order is paid when Stripe says its payment intent succeeded. Put the endpoint's signing secret in a file only the server's user reads, and name it in a hooks file:

# /etc/fennec/hooks: a hook a line
stripe  stripe  /run/secrets/stripe-live

fennec-server --file shop.fennec --http 0.0.0.0:8080 \
  --http-token "$TOKEN" --hooks /etc/fennec/hooks

Then define the statement that takes the hook's events, with the server's token:

create statement stripe_paid(
    $intent text from event.data.object.id,
    $order  text from event.data.object.metadata.order,
    $amount int  from event.data.object.amount_received,
    $paid   timestamp from hook.at)
  on hook stripe
  where event.type = 'payment_intent.succeeded' and event.livemode = true
as set orders {status: 'paid', intent: $intent, amount: $amount, paid_at: $paid}
   where ref = $order and (status = 'open' or intent = $intent)
   require 1 else 'no open order for this payment yet'

In Stripe's Dashboard, add an event destination: a webhook endpoint at https://db.example.com/_hooks/stripe, the events payment_intent.succeeded, and the Snapshot payload style. A thin event carries no data.object; fennecdb never calls Stripe's API to fetch it, so a statement reading data.object.* refuses a thin event with a 400 naming the path, which shows in Stripe's delivery log.

Three things in that statement are Stripe's, and worth copying:

  • A mode is a hook. Test mode and live mode sign with secrets of their own at endpoints of their own: name a hook for each (stripe, stripe_test), and have the live hook's statements read event.livemode = true, so a test secret set on the live hook by mistake writes nothing.
  • Its guard is idempotent by the object's id. Stripe may send two events for one change, each with an id of its own, so both are taken. status = 'open' or intent = $intent takes the second as a write over the row it already paid; a guard of status = 'open' alone would refuse it (412) for the three days Stripe retries. A put ... if absent over a @unique field holding the object's id is the other way.
  • require says not yet. Stripe does not promise to deliver events in order: a payment may come before the order's row. The guard refuses it (412, its reason in Stripe's log), and Stripe sends it again until the row is there. A where with no require would take it as a write of no row and answer 200, and Stripe would never send it again.

Stripe's times are seconds since 1970. A timestamp parameter reads a number as milliseconds, so $created timestamp from event.created would be an instant in January 1970. Read it as an int and multiply:

create collection refunds (charge text @unique, at timestamp)

create statement stripe_refunded(
    $charge  text from event.data.object.id,
    $created int  from event.created)
  on hook stripe
  where event.type = 'charge.refunded'
as put refunds {charge: $charge, at: $created * 1000} if absent

hook.at, the time the signature covers, is a timestamp already.

Pushes from GitHub

github  github  /run/secrets/github-webhook

create statement pushed(
    $repo   text from event.repository.full_name,
    $branch text from event.ref,
    $sha    text from event.after,
    $kind   text from hook.event)
  on hook github
  where hook.event = 'push'
as insert pushes {repo: $repo, branch: $branch, sha: $sha, kind: $kind}

In the repository's or organization's settings, add a webhook: the payload URL https://db.example.com/_hooks/github, the content type application/json (GitHub's default, application/x-www-form-urlencoded, is refused 415 with the type to set), the secret in the file, and the events to send. hook.event is GitHub's X-GitHub-Event header; a condition reads it beside the body. GitHub sends a ping when a webhook is made: no condition takes it, so it is answered 200, {"taken":0}, and nothing is written.

GitHub's signature covers the body alone, not X-GitHub-Event. Whoever holds one signed body can send it again under another event's name: under key body the copy is answered from its key while it is kept, and taken again once keep has passed; under key delivery a new delivery id has it taken at once. A condition on hook.event alone can then take an event its statement was never meant for. Write the condition on fields of the signed body as well, which tell one kind of event from another — event.ref for a push, event.action for a pull request: where hook.event = 'push' and event.ref = 'refs/heads/main'.

GitHub's signature covers the body alone, so its key is chosen by the hook's line:

  • key body, the default, keys an event by its body's SHA-256. A copy of the body is taken once whatever header it comes with; two events whose bodies are the same byte for byte are one.
  • key delivery keys it by X-GitHub-Delivery, which GitHub keeps when you redeliver from its log. No signature covers that header, so whoever holds one signed body may send it again under a new delivery and have it taken again; a hook keyed so has statements idempotent by what they write.

Any sender of Standard Webhooks

Senders that sign as Standard Webhooks says — Svix and the services that send through it, among them Clerk and Resend — take the scheme standard. Their headers are webhook-id, webhook-timestamp and webhook-signature, or Svix's names for the same three, svix-id, svix-timestamp and svix-signature, which Clerk and Resend send; an event carrying both sets is refused. Its secret file holds the secret as the sender shows it, whsec_ and base64; a file holding anything else is refused at the start.

clerk  standard  /run/secrets/clerk-webhook

create collection users (clerk_id text @unique, email text)

create statement user_created(
    $id    text from event.data.id,
    $email text from event.data.email_addresses."0".email_address)
  on hook clerk
  where event.type = 'user.created'
as put users {clerk_id: $id, email: $email} if absent

An event's key is its webhook-id (or svix-id). "0" is the first element of a list: a key of digits reads a list by its place, and a key that is no word, such as "order-id", is quoted.

The hooks file

A line a hook, read once as the server starts; # starts a comment. Anything wrong is refused at the start, naming the line and what to write, never the secret's value.

The secrets are the deployment's, as the server's token is: never in the database, an archive, a log line, a trace or an answer. A server with no hooks file has no /_hooks/ route: a request there asks for a token as any unknown path does. A secret changes at a restart: name the new one second, restart, change it at the sender, then drop the old one at the next restart.

The server says at its start what does not meet: a hook of the file no statement takes (its events answered 409), and a statement taking a hook the file does not name (its events answered 401). Each is a line of its log.

Taken once

An event's key is id in a Stripe event's body, webhook-id (or svix-id) for a Standard Webhooks sender, and for GitHub what its hook's key says. The key is kept in _hook_events for the hook's keep, in the same block as the statements' writes. A copy of the event while its key is kept — a retry, a duplicate delivery, Stripe sending again after a slow answer — runs nothing and is answered as the first was, marked Idempotent-Replayed: true, once the first's block is as durable as its answer was to be. A second body under a key that is kept is answered the same, never run, and logged.

The keys cost a little of the file: a row an event, given back by compaction once its keep has passed. An event sent again after its key was let go is taken again, as a new one: keep is what tells a retry from a new event, so keep it longer than the sender's retries and your own redeliveries from its log. A statement whose guard is idempotent by the object's id takes a late copy as a write of what is already there.

Where a hook has several statements, an event runs every one whose condition takes it, in their names' order, in one block: all of them and the key, or none. A refusal by any is the event's answer.

What a sender is told

A sender is told a 2xx once its event is taken and on disk, or when sending it again could change nothing. Every other answer is the refusal's status, so the sender's retries are the queue: Stripe retries for three days, Standard Webhooks senders on their own schedules, and GitHub redelivers from its log when asked. A sender is told what a scoped token would be: the status, a guard's reason and the bound a refusal names — never a statement's name or a value from the database, which the server's log line holds under the request id beside the event's key.

One 401 for everything before the signature

The route is the one that runs a statement without a token, so nothing of an event is read before its signature verifies: the scheme is read from the headers present, each of which must come once; the hook is looked up; the signed time must be within the tolerance; the body must be within the hook's max-body; and two HMAC-SHA256s are computed, always, under the hook's secrets — a random key of the process's own standing in for one that is not there, which never verifies — each compared in constant time with every v1 signature sent. They cover the body up to the largest max-body of any hook, whichever hook the path names. Stripe's v0 and Standard Webhooks' v1a are not read. Every failure is the same 401 after the same work, so an answer's time tells no one whether a hook exists, or what its max-body is.

Which check failed is said where only you read it: the server's log (hook `stripe`: an event from 203.0.113.9 did not verify (stale): answered 401, hook `?` for a path naming no hook's name), the audit log's refused line and fennec_hook_unverified_total{check} — header, scheme, stale, size, hook or signature. A stale run from one sender is a clock to set right; a signature one a secret rolled at one end only. Refusals from one address wait longer each time, as a refused token's do, by a count of the hooks' own, kept by the address and the hook's name: /_hooks/%73tripe counts as /_hooks/stripe, and every path naming no hook's name shares one count. A forged event raises no token's wait, and a verified event clears no token's.

On disk before the 2xx

A client told a buffered write landed can read it back and write it again; a sender told 2xx never sends the event again. So an event's block is fsynced before it is answered, as a write under --sync always is, whatever --sync says for the server's other writes: a crash a moment after a buffered 200 would lose a payment no one sends again. An event no condition takes writes nothing and waits for nothing. Events arriving together share one fsync. On a server under --sync 250 each event is one more fsync among its buffered writes; the buffered writers beside it go on into memory while it runs.

Where the server feeds a replica a promotion could take the event from, the 2xx waits too for that replica's stream to have sent the block, up to the time a durable write waits for its replicas. Past it the answer is 503 with Retry-After: the event is taken and on disk, and the sender's next try is answered from its key once the replica holds it. An archiver's stream is no replica a promotion takes over, and is not waited for.

Who defines and calls one

The server's token defines a hook's statement, as it makes any schema change, and the audit log's schema line names its hook. The statement runs with its own text's authority, as every named statement does: its writes wake the statements bound to them and are held to --call-max-rows. The server's token may call one to try it, with an event as its argument — call stripe_paid {type: 'payment_intent.succeeded', data: {...}} — which runs it as an event would and keeps no key; hook.id, hook.at and hook.event are null there. To every scoped token a hook's statement is the 404 a missing statement is, at /query, /batch and /_call, whatever its policy's call lines say; it is in none of their listings, and an agent gets no MCP tool for it.

A synced replica, the browser module and the native library take no definition: nothing of theirs receives a sender's request. What an event writes reaches them as any write does.

Senders' addresses

The signature is what proves an event is the sender's; fennecdb keeps no list of addresses. Stripe also advises accepting its events only from the addresses it sends from; a firewall in front of the server may hold /_hooks/stripe to them. Behind Cloudflare's proxy the server sees Cloudflare's addresses, so the rule is Cloudflare's: a WAF custom rule blocking http.request.uri.path eq "/_hooks/stripe" and not ip.src in {...}, the list Stripe publishes.

Watching them

/_metrics counts each event once by its outcome in fennec_hook_events_total{outcome} — taken, ignored (no condition took it), replayed, conflict (another body under a kept key), refused, deferred (a 429, 500, 503 or 507 the sender's retry may meet otherwise) and unknown — and the refusals before the signature in fennec_hook_unverified_total{check}. No label names a hook. A server with no hooks file writes neither family. Each refused event, and each copy that came with another body, is a line of the server's log naming the hook, the event's key, GitHub's delivery and why — what the sender was not told — under the request's id; never the body, a signature or a secret.
