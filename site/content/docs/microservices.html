Services and events

Give each service a database of its own, and let other services follow its writes as events.

A database per service

Run one tenant node and give each service its own tenant: a separate file that no other service can read. A token then decides which collections and rows each caller may touch.

How a tenant keeps a service apart

Each service keeps its own data and tells the others what changed. fennecdb gives a service a database of its own on a shared node, a token that reaches only that, and the writes on its disk as a stream of events — which is what an outbox table and a relay are usually built for.

A tenant node (fennec-server --dir) keeps a file per tenant, and a tenant is named by the path, /t/<tenant>/ — never by the query, so one service cannot read another's rows. Give each service its tenant, and a router (fennec-shard) in front of the nodes when there are several: see Tenants and sharding.

Within a database, a JSON Web Token held to a policy gives each caller the collections, and the rows, its role may read or write (Scoped access). A service that only reads can be pointed at a replica, which refuses every write (Replication), or hold a token whose policy grants read alone.

Every write as an event

Turn on --cdc and every write that reaches disk becomes an event a consumer can read. You do not need an outbox table: a batch's rows are announced together.

fennec-server --file orders.fennec --http 127.0.0.1:8080 --cdc

# a consumer the server keeps the cursor of: made if it is not there,
# left where it stands if it is, so a service can do this at every start
curl -X POST http://127.0.0.1:8080/_changes/consumers/billing
Why the collection is its own outbox

An outbox table exists because a service must change its data and announce the change together, or not at all. A fennecdb /batch is one record on disk, so the rows it writes are announced together already: GET /_changes hands over every write once it is on disk, the documents with it (Change data capture). The collection is its own outbox. Where the event should say something the rows do not — a command, an intent — write it into a collection of its own in the same /batch, and it comes in the same record.

A consumer that calls a webhook, with a signature and a dead-letter collection, is on Functions and webhooks, beside the other two ways to react to a write. A consumer in Python:

from fennecdb import Client

db = Client("http://127.0.0.1:8080", token="...")
for batch in db.follow("billing"):        # committed when the loop comes back
    for change in batch:
        if change["collection"] == "orders" and change["op"] == "put":
            bill(change["doc"])           # an exception: the batch is read again

On to Kafka, or anywhere

The relay passes a consumer's events on, as JSON lines or to a webhook. Pipe the lines into Kafka with any tool that writes to a topic.

python -m fennecdb.relay http://127.0.0.1:8080 --consumer kafka \
  | kcat -P -b broker:9092 -t orders
How the relay hands writes on

python -m fennecdb.relay reads a consumer's writes and hands them on — to standard output, one JSON object a line, or to a webhook — and moves the cursor only once they are out. Kafka takes them through any tool that writes lines to a topic, as above; a webhook:

python -m fennecdb.relay http://127.0.0.1:8080 --consumer search \
  --to https://indexer.internal/hook

Delivery and replay

Each event arrives at least once, in order within one database. Make your handler safe to run twice; a consumer that falls too far behind starts over from a fresh read.

The delivery guarantees
  • At least once. A consumer that crashes between reading and committing reads those writes again. Key what you do by seq, or by the collection and id: a put carries the whole document, so applying one twice leaves what applying it once did.
  • In order, one database at a time. seq is the database's change counter; a batch's writes come together. There is no order across tenants.
  • Kept for a while, not for ever. The server keeps as many writes as --replication-buffer holds, 64 MiB unless given. A consumer further behind is answered 410, never handed writes with a gap in the middle. To start over: take the last write on disk (Fennec-Next of GET /_changes with no since), read the collections whole, then go on from that number — a write read in both is applied twice, which a put by id makes harmless.
  • What is on disk. A write the server lost in a crash was never handed to anyone, as it was never sent to a replica.
  • Reading one's own writes. A service that writes on the primary and reads on a replica sends the write's Fennec-Seq back as Fennec-After, and the replica answers once it holds the write (Reading your own writes).
  • Retries. A service that sends a write again after a timeout sends it with an Idempotency-Key, and a write that landed is answered as before rather than made twice (Retrying a write).

A process across services (sagas)

An order touches payments and stock, each a database of its own, and no transaction spans them. Run the process as a saga: a row that says where it stands, steps that are safe to send twice, and a write that undoes each step if a later one fails.

import { connect } from '@fennecdb/web/client';

const orders = connect('https://orders.internal', { token: 'orders token' });
const payments = connect('https://payments.internal', { token: 'payments token' });
const stock = connect('https://stock.internal', { token: 'stock token' });

// The saga is a row in the owning service's database: one write begins it.
await orders.run(
  "put sagas {id: $1, state: 'running', next: 'pay', done: [], deadline: now() + 600000}",
  ['ord-1142'],
  { idempotencyKey: 'ord-1142:begin' },
);

// A step is a write under a key from the saga and the step: sent again, it is made once.
await payments.run('put charges {id: $1, amount: $2}', ['ord-1142', 129.5], { idempotencyKey: 'ord-1142:pay' });
await stock.run('put holds {id: $1, sku: $2, qty: $3}', ['ord-1142', 'TENT-1', 2], { idempotencyKey: 'ord-1142:reserve' });

// A step that fails after one before it was made: the undo, in reverse order, each under a key too.
await payments.run('del charges where id = $1', ['ord-1142'], { idempotencyKey: 'ord-1142:undo-pay' });
  • The next step comes from the change stream. The orchestrator follows the saga collection's writes (/_changes, above): a write that sets next to reserve is the order to run that step, and the step's result is written to the saga row in turn. The row and its event are one record, so a crash loses neither.
  • A retry makes the step once. The key is the saga's id and the step's name, so a worker that dies after the write and runs the step again gets the first answer back (Retrying a write). Keys are kept a day unless --idempotency-ttl says otherwise; a saga that outlives them should write by id, so a repeat leaves what the first left.
  • Compensation is ordinary writes. Set the saga's state to compensating and run the undo of each step in done, last first, each under its own key. An undo must be safe when the step it undoes never landed.
  • A step that keeps failing is parked. Run steps as jobs, and after the fifth attempt the job has no ready time: a dead letter for a person to read (Fail, back off, dead-letter).
  • A step times out by the clock. A scheduled statement turns a saga past its deadline to compensating, and the stream carries that to the orchestrator like any other write.
  • A step that must not act on a state changed underneath it. Read the saga row, which comes with an ETag, and write the next state with If-Match: if the timeout, or a second orchestrator, moved it first, the answer is 412, nothing is written, and you read the row again (Optimistic concurrency).
create statement time_out_sagas every 1m
as set sagas {state: 'compensating'}
   where state = 'running' and deadline < now() order deadline limit 1000
What the saga leaves to you

fennecdb gives the pieces; the saga is yours. It runs each step at least once and in order, never as one atomic whole: another service can read the state between a step and its undo, so write a step so that state is one a reader may see, such as a hold, not a sale.

What it is not

It is not a message broker. To keep events for a long time or share them with many teams, relay them into one.

It does not do two-phase commit across databases, and has no global transaction. A /batch is atomic within one database only; a process across services is a saga, above.

What it leaves to a broker

A consumer reads one database's writes; there are no topics, partitions or retention of their own, and a server keeps its writes in memory up to the buffer. For fan-out to many teams, a long history or events that outlive the database, relay them into a broker and let it keep them.
