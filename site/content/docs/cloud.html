Cloud platforms

Where to run fennec-server on each cloud, or no server at all on Cloudflare, the config for it, and how your apps and functions reach it.

A server is one process over one file on a disk, reached over HTTP. That asks three things of a platform: a block disk that outlives the process, one instance at a time, and a stop that waits for the final sync. Pick yours from the table, then read the rules and the volume's owner, which hold on every platform. Serverless needs none of that: on Cloudflare the engine runs inside a Worker, a database in each Durable Object (Serverless), and a function on any platform is a client, of a server or of that Worker (Functions). Servers in several regions take one URL through a Worker in front of them (Distributed), and Cloudflare's pieces on other platforms says what each part is called elsewhere.

The rules on every platform

  • A block volume, never a network share. EBS, Persistent Disk and Hyperdisk, an Azure managed disk, a DigitalOcean, Hetzner or Linode volume, a Fly volume, a Render disk, a Railway volume. Not EFS, Azure Files or Filestore (NFS and SMB), and not a bucket shown as files (Cloud Storage FUSE, Mountpoint for S3, s3fs): the server holds <file>.lock to keep a second process out, and a network file system may not keep that lock (--file). --no-mmap exists for them; this page does not recommend them.
  • One instance. Replicas 1, no autoscaling, and a deploy stops the old instance before it starts the new: a second process over the file is refused (exit 1), so a platform that starts the new beside the old must be told not to.
  • A token from the secret store. FENNEC_HTTP_TOKEN, in the environment, never --http-token: argv shows in ps. Without a token the server refuses to listen beyond loopback and exits 2. Make it yourself and keep a copy for your apps: most secret stores never show a secret again.
  • Health is GET /_health. It needs no token and takes no lock. The port binds only after the file is opened, so a large file takes a while: give a startup check a grace period of minutes (the image's own check, --ping, waits 120 s). Orchestrators other than Docker ignore the image's HEALTHCHECK.
  • Wait for the stop. SIGINT, SIGTERM and SIGHUP all run the clean shutdown: a final sync, then a checkpoint of the vector graphs. Killed before it ends (SIGKILL, an out-of-memory kill, a grace period that ran out), up to one --sync interval of writes is lost and the graphs are linked again at the next start. Set the platform's stop timeout to 30 to 60 s.
  • Memory. There is no buffer pool: the file is mapped and the page cache holds it; the process holds the indexes. Give --max-memory (in MiB) a third of the memory limit, and a write past it gets 507 rather than an out-of-memory kill.
  • Every flag, when you override the command. The image's is --http 0.0.0.0:8080 --file /data/data.fennec --sync 250; write out whatever you change, or the file is dropped and the database is in memory.

Who owns the volume

Nothing to set on any platform. The image starts as root, and fennec-server becomes 65534:65534, the nobody of Linux, before it opens a file or starts a thread: it never serves as root. A platform's volume is often an empty file system whose root belongs to root, where 65534 could not make its file, so the server hands it over first:

$ docker run --rm --mount type=volume,dst=/data,volume-nocopy=true \
    -e FENNEC_HTTP_TOKEN="$(openssl rand -hex 32)" ghcr.io/fennec-db/fennec-server:{{version}}
handed /data to 65534:65534
running as 65534:65534, started as root (FENNEC_USER)
opened: /data/data.fennec
  • What is handed over. The directory the server writes in (--file's, or --dir) and the database's files in it — data.fennec and the files beside it named after it, a node's tenants' files — where they are not 65534's already. A start after the first hands over nothing, and neither does a Docker named volume, which Docker fills from the image's /data, 65534's in the image.
  • What is not. Only a volume of its own holding nothing but the database and a lost+found: never /, a path through a symbolic link, a directory on the image's or the host's own file system, one anyone may write in, nor one holding any other file, a link or a directory. The server says why in its log and goes on as 65534; if it then cannot write there, make the directory 65534's yourself, or start the server as its owner.
  • Another user. Started as anyone but root — docker run --user 1000:1000, Kubernetes' runAsUser — the server runs as that user and hands nothing over: the volume has to be that user's. FENNEC_USER, or the --user flag over it, names whom root becomes, <uid>:<gid> in numbers.
  • docker exec and the health check. --ping, and anything else run in the container, starts as root and drops it the same way: nothing it makes is root's.
Why the image starts as root

The image holds the static binary and nothing else: no shell, no chown, no gosu. Images with a shell, postgres's and redis's, fix a volume's owner in an entrypoint script that runs as root and then drops to the database's user; here the binary does it, between reading its arguments and opening anything. An image that started as 65534 could not: where the platform makes the volume itself it is root's, and each platform needed a way around it (a derived image running as root, Railway's RAILWAY_RUN_UID=0). Root is kept for the hand-over alone: the supplementary groups, the group and then the user are dropped, and the server checks that root cannot be had back before it goes on; a step that fails ends the start. The image of 0.2.0 started as 65534: on a root-owned volume it needs the volume made 65534's, or the container run as root.

Kubernetes

One StatefulSet with one replica, a ReadWriteOnce claim, and a Service. A Deployment would need strategy: Recreate, since a rolling update keeps two pods up together for a moment. The pod runs as 65534 and its volume is made 65534's by fsGroup; the root file system is read-only and every capability dropped. The image's own user is root, which hands a volume over and becomes 65534 itself (Who owns the volume), so runAsNonRoot: true needs runAsUser beside it: without one the kubelet refuses to start the pod.

Why a StatefulSet, and what the probes allow

A StatefulSet of one replica starts the replacement pod only after the old one has stopped, and ties it to the same claim; a Deployment's default rolling update would start the new pod beside the old one, with two processes over a volume that a block device lets only one node mount, or a network share that lets both and keeps no lock. OnRootMismatch makes Kubernetes change a volume's ownership when its root is not fsGroup's, once, rather than walking every file at each start. A pod that leaves runAsNonRoot, runAsUser and fsGroup out starts the server as root, which hands the volume to 65534 and becomes it; that needs the CHOWN, SETUID and SETGID capabilities, which drop: ["ALL"] takes away: there it cannot drop root, says so and exits 2. With every capability dropped, run it as 65534 from the start, as above. The memory limit is 1 GiB and --max-memory 340 MiB, a third of it, as in the repository's docker-compose.yml. terminationGracePeriodSeconds: 60 holds the final sync and the checkpoint; the default, 30 s, is short for a large graph.

Fly.io

A Machine with a volume, in one region. Fly's private network is IPv6, so the server listens on [::] (which takes IPv4 too on Linux) and the command is written out in a one-line Dockerfile:

FROM ghcr.io/fennec-db/fennec-server:{{version}}
CMD ["--http", "[::]:8080", "--file", "/data/data.fennec", "--sync", "250", "--max-memory", "340"]
app = "my-fennec"
primary_region = "ams"

# The default is 5 s; 300 s is the most it takes.
kill_timeout = 60

[build]
  dockerfile = "Dockerfile"

[[mounts]]
  source = "fennec_data"
  destination = "/data"
  initial_size = "10GB"

[http_service]
  internal_port = 8080
  force_https = true
  # Fly's proxy stops a Machine it sees no traffic for, and apps reaching it
  # over .internal pass around the proxy: keep it running.
  auto_stop_machines = "off"
  auto_start_machines = false

  [[http_service.checks]]
    method = "GET"
    path = "/_health"
    grace_period = "120s"
    interval = "15s"
    timeout = "5s"

[[vm]]
  memory = "1gb"
  cpu_kind = "shared"
  cpus = 1
fly apps create my-fennec
fly volumes create fennec_data --region ams --size 10
TOKEN=$(openssl rand -hex 32)     # keep it: Fly never shows a secret again
fly secrets set FENNEC_HTTP_TOKEN="$TOKEN"
fly deploy --ha=false
fly status
  • One Machine, one volume. A volume attaches to one Machine, so fly deploy --ha=false and never fly scale count 2. A deploy of one Machine with one volume is down for its length; the canary and bluegreen strategies cannot be used with a volume.
  • Public, unless you say otherwise. The first deploy gives the app public addresses, and [http_service] then answers at https://my-fennec.fly.dev, behind Fly's certificate, to anyone holding the token. For a server only your apps reach, deploy with fly deploy --ha=false --no-public-ips, or give back addresses it already has (fly ips list, fly ips release): .internal below needs none of them.
  • Memory. --max-memory 340 is a third of the Machine's 1 GB; change the two together.
  • The volume's owner. Nothing to do: the CMD above keeps the image's FENNEC_USER, and the server hands a new volume to 65534 at its first start, its log saying so (Who owns the volume).
  • Inside Fly. Other apps in your organization reach it at http://my-fennec.internal:8080, over the private network and around Fly's proxy, with the token.
  • Backups. Fly takes a daily snapshot of a volume and keeps it 5 days by default (snapshot_retention, up to 60), and says a snapshot may lack the latest writes: take a backup of your own too.

Render

A private service (or a web service, to be public) with a persistent disk. Render builds it from a repository holding a two-line Dockerfile, which writes out the command with a --max-memory for the plan:

FROM ghcr.io/fennec-db/fennec-server:{{version}}
CMD ["--http", "0.0.0.0:8080", "--file", "/data/data.fennec", "--sync", "250", "--max-memory", "170"]
services:
  - type: pserv           # web, for a public URL
    name: fennec
    runtime: docker
    dockerfilePath: ./Dockerfile
    plan: starter
    numInstances: 1
    healthCheckPath: /_health   # asked of a web service; a private one is checked by its port
    maxShutdownDelaySeconds: 60
    envVars:
      - key: FENNEC_HTTP_TOKEN
        sync: false          # asked for once, when the Blueprint is created
    disk:
      name: fennec-data
      mountPath: /data
      sizeGB: 10
  • Port. A web service is routed to PORT, 10000 unless you set it: set PORT=8080 beside the token, which is where the image listens. A private service needs no routing.
  • Health. Render asks healthCheckPath of a web service alone; a private service passes once its port accepts a connection, which is once the file is open.
  • Memory. The starter plan has 512 MB, and --max-memory 170 in the Dockerfile is a third of it; change the two together. A Blueprint can also deploy the image as it is (runtime: image, image: {url: ...}), with the image's command and no --max-memory.
  • The disk's owner. Render does not document who owns a disk's mount; whoever does, the server hands it to 65534 at its first start (Who owns the volume), as it does an empty Docker volume made with volume-nocopy, which is where that was checked.
  • One instance, and a gap at every deploy. A disk cannot be shared or scaled, and attaching one switches off zero-downtime deploys: Render stops the old instance, then starts the new, a few seconds with a large file's open on top. maxShutdownDelaySeconds takes 1 to 300 and defaults to 30.
  • The disk is mounted at runtime only, not in a build, a pre-deploy command or a one-off job. It can grow but not shrink. Render snapshots it every 24 hours and keeps each for seven days, restoring whole disks: take a backup of your own too.
  • Inside Render. Other services in the workspace reach a private service by its internal hostname and the port it listens on, http://<internal-hostname>:8080, copied from the service's Connect menu, Internal tab.

Railway

A service from the image, a volume at /data, and one replica. A Railway volume is root's, and the server hands it to 65534 at its first start (Who owns the volume): Railway's RAILWAY_RUN_UID=0 is not needed.

  1. New service, from the Docker image ghcr.io/fennec-db/fennec-server:{{version}}.

  2. Variables, three:

    FENNEC_HTTP_TOKEN=<a random string, sealed; keep a copy for your apps>
PORT=8080
RAILWAY_DEPLOYMENT_DRAINING_SECONDS=60

    PORT is where Railway's health check asks, and the server listens on 8080 whatever it says. The draining seconds are the time between Railway's SIGTERM and its SIGKILL, 0 unless set: without them every redeploy kills the server before its final sync.

  3. Add a volume to the service, mount path /data. A service has one volume.

  4. Settings: a health check path of /_health. Railway asks it while a deployment starts, for 300 s unless told otherwise (RAILWAY_HEALTHCHECK_TIMEOUT_SEC), and not again once it is live. Leave the replicas at 1.

  • More flags. A start command replaces the image's entry point, so it is the whole command, the program first: /usr/local/bin/fennec-server --http 0.0.0.0:8080 --file /data/data.fennec --sync 250 --max-memory 340, with --max-memory a third of the service's memory limit. The image's FENNEC_USER is a variable, not a flag, so the server still hands the volume over and drops root under a command of your own.
  • A deploy is a brief outage. Railway never runs two deployments mounted to one volume, so a redeploy stops the old one first, with a health check or not. Replicas cannot be used with volumes.
  • Inside Railway. Services of the same environment reach it at http://fennec.railway.internal:8080 (the service's name). An environment made before 16 October 2025 resolves that name to IPv6 only; then the server has to listen on [::], as Fly's Dockerfile does.
  • The volume's size depends on the plan; it grows live and never shrinks, and Railway makes manual and automatic backups of it: take a backup of your own too.

Cloudflare

Cloudflare carries fennecdb two ways, and they combine. Serverless: the engine runs inside a Worker, a database in each Durable Object, and there is no server anywhere. Distributed: servers in regions of your own with Cloudflare as their only way in, one URL for every tenant through a Worker that sends each request to its tenant's region, over Cloudflare Tunnel and behind Cloudflare Access. Around both, a Worker is an endpoint with logic in front of a database, Access an identity provider whose tokens a server takes, and R2 where files and archives go.

Serverless: a database in each Durable Object

The browser module, @fennecdb/web, opens a database in a Durable Object, and @fennecdb/cloudflare keeps it in the object's storage as a file would hold it: an image, then the writes since, each stored before its answer goes, and the object's alarm deleting expired rows and writing a new image when one is worth it. There is no process to run, no volume and no instance count: an object is one writer, as a file is.

  1. Install the two packages and wrangler.

    npm install @fennecdb/web @fennecdb/cloudflare
npm install -D wrangler

  2. Bind the object's class. A class a new account makes is SQLite-backed, and persist keeps the database in its SQL storage.

    {
  "name": "my-fennec",
  "main": "worker.ts",
  "compatibility_date": "2026-09-01",
  "durable_objects": {
    "bindings": [{ "name": "TENANT", "class_name": "Tenant" }]
  },
  "migrations": [{ "tag": "v1", "new_sqlite_classes": ["Tenant"] }]
}

  3. The Worker: the Tenant class of A database a Durable Object, and a fetch that lets in only the callers holding its token before it sends a tenant's statements to that tenant's object. The class there is typed, so the file is worker.ts. integrations/cloudflare/example/worker.js is the whole Worker in JavaScript, importing from the repository where yours imports the packages, run by its test under wrangler dev; the check below goes at the top of its fetch.

    const enc = new TextEncoder();

/** Whether the request carries the Worker's token, compared in constant time. */
async function allowed(req, env) {
  const [got, want] = await Promise.all(
    [req.headers.get('authorization') ?? '', `Bearer ${env.FENNEC_TOKEN}`]
      .map((s) => crypto.subtle.digest('SHA-256', enc.encode(s))),
  );
  return crypto.subtle.timingSafeEqual(got, want);
}

export default {
  async fetch(req, env) {
    if (!env.FENNEC_TOKEN || !(await allowed(req, env))) {
      return new Response('unauthorized', { status: 401 });
    }
    // then the example's: POST /t/<tenant>/query to that tenant's object
  },
};

  4. The deploy, then the token: until it has one the Worker answers 401 to everyone.

    npx wrangler deploy
TOKEN=$(openssl rand -hex 32)     # keep it: wrangler never shows a secret again
echo "$TOKEN" | npx wrangler secret put FENNEC_TOKEN
curl -X POST https://my-fennec.<account>.workers.dev/t/acme/query \
  -H "Authorization: Bearer $TOKEN" -d '{"sql": "collections"}'
  • The Worker is the access layer. The server's scoped tokens and rules (HTTP security) are a server's; in a Worker, what a caller may run is its own code. One that runs whatever FennecQL it is sent gives every holder of its token the whole database, so a page or an app's users get endpoints for what they may do instead, each its statement, as Functions and webhooks writes them.
  • Collation data for scripts the module does not carry is fetched from a URL unless the Worker hands it from its bundle (Limits).
  • A cold start, after an eviction or a deploy, reads the database back: tens of milliseconds for 10 000 rows, under 200 for 50 000 (A cold start).
  • Apps anywhere reach the Worker as they would a server: its URL and its token (Functions). Data in Durable Objects and functions on Vercel or Lambda make a stack with no server in it.

Distributed: one URL in front of regions

Tenants live on fennec-server nodes, a file each, in regions you run on VMs of any cloud; each region has a router that leases its nodes and fails them over, and a standby in another zone (Tenants and sharding). In front of them all is the global entry, a Worker (integrations/cloudflare/entry): https://db.example.com/t/<tenant>/... reaches the routers of the region the tenant lives in, from wherever the client is.

clients, every continent      https://db.example.com/t/<tenant>/...
                 |
       the entry Worker  (REGIONS, ENTRY_TOKEN, an Access service token)
          |                                  |
   Cloudflare Tunnel + Access         Cloudflare Tunnel + Access
          |                                  |
   region eu: router, standby         region us: router, standby
   nodes in fra and ams               nodes in iad and pdx

  • Homes are learned, not configured. The router that forwards a request to the tenant's node names the node's region in its answer, to the entry alone, and the entry keeps it, shared with its colo's other isolates through the Cache API. A tenant it has not seen goes to the region of the client's continent (Cloudflare's request.cf.continent), whose router serves it or relays it home once; a tenant moved since costs one hop, never an error.
  • Reads near the client. A read marked Fennec-Read: replica goes to the region of the client's continent first, answered there from the tenant's read replica; writes always go home.
  • A router down is passed over for its region's standby. A known tenant's request never goes to another region; an unknown one's goes on to the next region, whose router relays it home.
  • No open port. Each router is reached through Cloudflare Tunnel (cloudflared beside it), whose rules pass a tenant's paths alone: /_shard/, /_replication and /_metrics answer 404 at the edge. Cloudflare Access on each tunnel's hostname admits the service token the entry holds and nothing else, and the routers drop every Cf-Access-* header before a node sees the request.
  • Archives in R2. An archiver on another machine keeps every write of a node with its time, copied to a bucket (R2, S3, B2) by rclone every five minutes, for a restore to any moment.
  • A plain Worker, not a Workers for Platforms dispatch, which would put a dispatch in every database request's path.

The rest of Cloudflare

  • A Worker as an endpoint in front of a server or the objects: a webhook arriving, a check the rules cannot say, a call to a third party before the write, with a token of its own (Functions and webhooks).
  • Cloudflare Access as the identity provider. A server takes Access's JWTs as scoped tokens, its keys from the team's /cdn-cgi/access/certs and --jwt-audience the application's tag; a Worker in front moves the Cf-Access-Jwt-Assertion header to Authorization (Cloudflare Access).
  • R2 for files. The bytes in R2, their facts a row; the backend, a Worker among them, signs a link only after the server has said yes (Files with S3 and R2).
  • Cloudflare Containers is not a home for the server: its disk is ephemeral, and an instance that sleeps starts again from the image. Persistence there would be R2 mounted as files, which this page's rule excludes.

Functions: clients from anywhere

Vercel, Netlify, AWS Lambda, Cloud Run, Cloud Functions, Azure Functions and Deno Deploy keep no disk a database can live on (below), so a function there is a client: of a fennec-server on a platform above, or of a Worker holding the databases in Durable Objects (above). Every client is HTTP, so a function has no connection pool to run out of, and the JavaScript one, @fennecdb/web/client, needs fetch alone, so it runs in Node, Bun, Deno and the edge runtimes as it is.

import { connect } from '@fennecdb/web/client';   // the builder and the HTTP client, no WebAssembly

// Once an instance, outside the handler: the calls after the first reuse it.
const db = connect(process.env.FENNEC_URL, {
  token: process.env.FENNEC_TOKEN,
  timeout: 5000,   // ms to an answer's head, under the function's own limit
});

export async function POST(req) {
  const { id, title } = await req.json();
  // A retried invocation sends the write again: the key makes it once.
  await db.withIdempotencyKey(`note-${id}`).from('notes').insert({ title });
  return Response.json({ ok: true });
}
  • Made once an instance. Python's Client, Go's fennecdb.New and .NET's FennecClient too: at module scope, in Lambda's init phase, not in the handler.
  • Bounded under the function's limit. A client bounds every request in time (timeout, 30 s unless given) and sends one again only where it cannot have run or may run twice: a read, or a write carrying an idempotency key (Retrying a write). Set the timeout under the platform's, so the function answers rather than being cut off mid-wait.
  • A platform's retry is a second write. Lambda tries an asynchronous invocation again, and a queue delivers a message again; key such writes by the event, its id or the message's, and a server answers the second as it answered the first.
  • Private addresses. A function reaching a server's private address needs the platform's VPC attachment (a Lambda in the VPC, Cloud Run's Direct VPC egress, Azure's VNet integration); one without it is given an HTTPS address and the token. A Worker needs neither.

A read-only copy inside the function

A function can also hold a database in its own memory, read-only: a catalog, a search index, data that changes with a deploy. The image is built once, shipped in the bundle or a bucket, and loaded at a cold start; the module runs in Node, Bun and Deno as in a page, as the site's own search runs in the page from an image. Its writes stay in that instance and are lost with it: data that changes goes to a server.

import { readFile, writeFile } from 'node:fs/promises';
import { Fennec } from '@fennecdb/web';

const db = await Fennec.open(await readFile('node_modules/@fennecdb/web/fennec.wasm'));
db.run('create collection products (name text @text, price int @sorted)');
db.run("put products {name: 'red fox mug', price: 12}");
await writeFile('catalog.fennec', db.snapshot());
import { readFile } from 'node:fs/promises';
import { Fennec } from '@fennecdb/web';

// Once an instance: the module and the image read at a cold start.
const db = await Fennec.open(await readFile('node_modules/@fennecdb/web/fennec.wasm'));
db.load(await readFile('catalog.fennec'));

export async function GET(req) {
  const q = new URL(req.url).searchParams.get('q') ?? '';
  return Response.json(db.run('get products select name, price match name $1', [q]));
}

Lambda, Cloud Run and Vercel give a function gigabytes of memory, so an image of tens of megabytes loads; a cold start pays its load, tens of milliseconds for 10 000 rows (A cold start).

Backups, then more than one server

A disk snapshot is a crash-consistent copy: a fine extra, not the backup. fennec backup takes the running database whole through the replication stream, and fennec archive keeps the stream for a restore to a moment. Give the server a replication token, as FENNEC_REPLICATION_TOKEN in its environment beside the HTTP token (the flag, --replication-token, shows in ps), and run them from anywhere that reaches it; both read their token from that variable too, where --token is not given.

fennec backup https://db.example.com nightly.fennec --token "$REPL"
fennec archive https://db.example.com /backups/archive --token "$REPL" --image-every 1h --keep 7d

# to the cloud's bucket, beside the archiver
aws s3 sync /backups/archive s3://my-bucket/fennec --delete      # AWS
gcloud storage rsync --recursive /backups/archive gs://my-bucket/fennec   # Google Cloud
azcopy sync /backups/archive "https://acct.blob.core.windows.net/fennec"   # Azure
rclone sync --local-no-check-updated /backups/archive r2:fennec  # R2, Spaces, B2, ...

--local-no-check-updated, since the newest segment grows while its database is written: rclone otherwise refuses a file that changed as it read it (source file is being updated), and a busy database's newest segment never reaches the bucket. Restoring to a moment, and the bucket's side, are on Replication and In object storage.

A server grows two ways. Reads: --replica-of starts a read replica on a second machine, on its own disk, fed from the primary's (Replication; POST /_replication/promote makes it the primary when the first is gone). Writes, many tenants or regions: a database for each tenant behind a router, each a file on a node (Tenants and sharding; Deploying it has the systemd kit and runbook, and the global entry one URL across regions). Neither is a second process over the same file.
