Cloud platforms

Where to run fennec-server on each cloud, or no server at all on Cloudflare, the config for it, and how your apps and functions reach it.

A server is one process over one file on a disk, reached over HTTP. That asks three things of a platform: a block disk that outlives the process, one instance at a time, and a stop that waits for the final sync. Pick yours from the table, then read the rules and the volume's owner, which hold on every platform. Serverless needs none of that: on Cloudflare the engine runs inside a Worker, a database in each Durable Object (Cloudflare Workers), and a function on any platform is a client, of a server or of that Worker (Functions).

The rules on every platform

  • A block volume, never a network share. EBS, Persistent Disk and Hyperdisk, an Azure managed disk, a DigitalOcean, Hetzner or Linode volume, a Fly volume, a Render disk, a Railway volume. Not EFS, Azure Files or Filestore (NFS and SMB), and not a bucket shown as files (Cloud Storage FUSE, Mountpoint for S3, s3fs): the server holds <file>.lock to keep a second process out, and a network file system may not keep that lock (--file). --no-mmap exists for them; this page does not recommend them.
  • One instance. Replicas 1, no autoscaling, and a deploy stops the old instance before it starts the new: a second process over the file is refused (exit 1), so a platform that starts the new beside the old must be told not to.
  • A token from the secret store. FENNEC_HTTP_TOKEN, in the environment, never --http-token: argv shows in ps. Without a token the server refuses to listen beyond loopback and exits 2.
  • Health is GET /_health. It needs no token and takes no lock. The port binds only after the file is opened, so a large file takes a while: give a startup check a grace period of minutes (the image's own check, --ping, waits 120 s). Orchestrators other than Docker ignore the image's HEALTHCHECK.
  • Wait for the stop. SIGINT, SIGTERM and SIGHUP all run the clean shutdown: a final sync, then a checkpoint of the vector graphs. Killed before it ends (SIGKILL, an out-of-memory kill, a grace period that ran out), up to one --sync interval of writes is lost and the graphs are linked again at the next start. Set the platform's stop timeout to 30 to 60 s.
  • Memory. There is no buffer pool: the file is mapped and the page cache holds it; the process holds the indexes. Give --max-memory (in MiB) a third of the memory limit, and a write past it gets 507 rather than an out-of-memory kill.
  • Every flag, when you override the command. The image's is --http 0.0.0.0:8080 --file /data/data.fennec --sync 250; write out whatever you change, or the file is dropped and the database is in memory.

Who owns the volume

The image is FROM scratch and runs as 65534:65534. A platform's volume is often an empty file system whose root belongs to root, and then the server cannot make its file:

$ docker run --rm --mount type=volume,dst=/data,volume-nocopy=true \
    -e FENNEC_HTTP_TOKEN=t ghcr.io/fennec-db/fennec-server:{{version}}
could not open /data/data.fennec: its lock file: Permission denied (os error 13)

A plain Docker named volume works, since Docker copies the image's /data ownership into a new one; most platforms do not. Each section below says what that platform needs. The ways out are the same everywhere:

  • Make the volume 65534's. chown 65534:65534 on a VM, or securityContext.fsGroup: 65534 on Kubernetes.
  • Run as root there. A platform with no knob for either takes a derived image, two lines: 
    FROM ghcr.io/fennec-db/fennec-server:{{version}}
USER 0:0
    The file it makes is root's; a later move to a non-root user needs a chown of the data first.
Why a scratch image runs as 65534

The image holds the static binary and nothing else: no shell, no chown, no way to repair a mount at start. So the owner has to be right before the process runs, and the image names the unprivileged nobody of Linux (65534) to run as, with a root-owned /data handed over to it at build time. Where the platform makes the volume itself, none of that reaches it. Reproduced here with Docker's volume-nocopy option, which creates the volume as a platform does, empty: the default user fails as above, and the derived image above starts, answers /_health and leaves data.fennec owned by root.

A VM and its block volume

Why a StatefulSet, and what the probes allow

A StatefulSet of one replica starts the replacement pod only after the old one has stopped, and ties it to the same claim; a Deployment's default rolling update would start the new pod beside the old one, with two processes over a volume that a block device lets only one node mount, or a network share that lets both and keeps no lock. OnRootMismatch makes Kubernetes change a volume's ownership when its root is not fsGroup's, once, rather than walking every file at each start. The memory limit is 1 GiB and --max-memory 340 MiB, a third of it, as in the repository's docker-compose.yml. terminationGracePeriodSeconds: 60 holds the final sync and the checkpoint; the default, 30 s, is short for a large graph.

Fly.io

A Machine with a volume, in one region. Fly's private network is IPv6, so the server listens on [::] (which takes IPv4 too on Linux) and the command is written out in a one-line Dockerfile:

FROM ghcr.io/fennec-db/fennec-server:{{version}}
CMD ["--http", "[::]:8080", "--file", "/data/data.fennec", "--sync", "250"]
app = "my-fennec"
primary_region = "ams"

# The default is 5 s; 300 s is the most it takes.
kill_timeout = 60

[build]
  dockerfile = "Dockerfile"

[[mounts]]
  source = "fennec_data"
  destination = "/data"
  initial_size = "10GB"

[http_service]
  internal_port = 8080
  force_https = true
  # Fly's proxy stops a Machine it sees no traffic for, and apps reaching it
  # over .internal pass around the proxy: keep it running.
  auto_stop_machines = "off"
  auto_start_machines = false

  [[http_service.checks]]
    method = "GET"
    path = "/_health"
    grace_period = "120s"
    interval = "15s"
    timeout = "5s"

[[vm]]
  memory = "1gb"
  cpu_kind = "shared"
  cpus = 1
fly apps create my-fennec
fly volumes create fennec_data --region ams --size 10
fly secrets set FENNEC_HTTP_TOKEN="$(openssl rand -hex 32)"
fly deploy --ha=false
fly status
  • One Machine, one volume. A volume attaches to one Machine, so fly deploy --ha=false and never fly scale count 2. A deploy of one Machine with one volume is down for its length; the canary and bluegreen strategies cannot be used with a volume.
  • The volume's owner. Fly staff say on the community forum that the mount is chowned to the image's user, which is 65534 here. If the log shows Permission denied on the lock file, add USER 0:0 to the Dockerfile.
  • Inside Fly. Other apps in your organization reach it at http://my-fennec.internal:8080, over the private network and around Fly's proxy, with the token.
  • Backups. Fly takes a daily snapshot of a volume and keeps it 5 days by default (snapshot_retention, up to 60), and says a snapshot may lack the latest writes: take a backup of your own too.

Render

A private service (or a web service, to be public) with a persistent disk. Render builds it from a repository holding the two-line Dockerfile that runs as root, since the platform's documentation does not say who owns a disk:

FROM ghcr.io/fennec-db/fennec-server:{{version}}
USER 0:0
services:
  - type: pserv           # web, for a public URL
    name: fennec
    runtime: docker
    dockerfilePath: ./Dockerfile
    plan: starter
    numInstances: 1
    healthCheckPath: /_health
    maxShutdownDelaySeconds: 60
    envVars:
      - key: FENNEC_HTTP_TOKEN
        sync: false          # asked for once, when the Blueprint is created
    disk:
      name: fennec-data
      mountPath: /data
      sizeGB: 10
  • Port. A web service is routed to PORT, 10000 unless you set it: set PORT=8080 beside the token, which is where the image listens. A private service needs no routing.
  • One instance, and a gap at every deploy. A disk cannot be shared or scaled, and attaching one switches off zero-downtime deploys: Render stops the old instance, then starts the new, a few seconds with a large file's open on top. maxShutdownDelaySeconds takes 1 to 300 and defaults to 30.
  • The disk is mounted at runtime only, not in a build, a pre-deploy command or a one-off job. It can grow but not shrink. Render snapshots it every 24 hours and keeps each for seven days, restoring whole disks: take a backup of your own too.
  • Inside Render. Other services in the workspace reach a private service by its internal hostname and the port it listens on, http://<internal-hostname>:8080, copied from the service's Connect menu, Internal tab.

Railway

A service from the image, a volume at /data, and one replica. A Railway volume is also not 65534's, and Railway documents the way out: RAILWAY_RUN_UID=0 runs the service as root.

  1. New service, from the Docker image ghcr.io/fennec-db/fennec-server:{{version}}.

  2. Variables: FENNEC_HTTP_TOKEN (a random string, marked as a secret) and RAILWAY_RUN_UID=0.

  3. Add a volume to the service, mount path /data. A service has one volume.

  4. Settings: a health check path of /_health, and a generous timeout for it. Leave the replicas at 1.

  • A deploy is a brief outage. Railway never runs two deployments mounted to one volume, so a redeploy stops the old one first, with a health check or not. Replicas cannot be used with volumes.
  • Inside Railway. Services of the same environment reach it at http://fennec.railway.internal:8080 (the service's name). An environment made before 16 October 2025 resolves that name to IPv6 only; then the server has to listen on [::], as Fly's Dockerfile does.
  • The volume's size depends on the plan; it grows live and never shrinks, and Railway makes manual and automatic backups of it: take a backup of your own too.

Cloudflare Workers: no server

On Cloudflare the engine runs inside your Worker. The browser module, @fennecdb/web, opens a database in a Durable Object, and @fennecdb/cloudflare keeps it in the object's storage as a file would hold it: an image, then the writes since, each stored before its answer goes, and the object's alarm deleting expired rows and writing a new image when one is worth it. There is no process to run, no volume and no instance count: an object is one writer, as a file is, and Cloudflare starts it where it is first asked for.

 a database in a Durable Object
fitsa database for each user, team, tenant or document; a tenant's own RAG corpus

a cold starttens of milliseconds for 10 000 rows, under 200 for 50 000 (A cold start)
does not fitone large database with many writers: a server on a platform above, the Worker its client (a Worker that is an endpoint)

    npm install @fennecdb/web @fennecdb/cloudflare

  2. Bind the object's class. A class a new account makes is SQLite-backed, and persist keeps the database in its SQL storage.

    {
  "name": "my-fennec",
  "main": "worker.js",
  "compatibility_date": "2026-09-01",
  "durable_objects": {
    "bindings": [{ "name": "TENANT", "class_name": "Tenant" }]

  3. The Worker: the Tenant class of A database a Durable Object, and a fetch that lets in only the callers holding its token before it sends a tenant's statements to that tenant's object. integrations/cloudflare/example/worker.js is the whole Worker, run by its test under wrangler dev; the check below goes at the top of its fetch.

    const enc = new TextEncoder();

/** Whether the request carries the Worker's token, compared in constant time. */
async function allowed(req, env) {
  const [got, want] = await Promise.all(
    [req.headers.get('authorization') ?? '', `Bearer ${env.FENNEC_TOKEN}`]
      .map((s) => crypto.subtle.digest('SHA-256', enc.encode(s))),
  );
  return crypto.subtle.timingSafeEqual(got, want);
}

export default {
  async fetch(req, env) {
    if (!env.FENNEC_TOKEN || !(await allowed(req, env))) {
      return new Response('unauthorized', { status: 401 });
    }
    // then the example's: POST /t/<tenant>/query to that tenant's object
  },
};

  4. The token, then the deploy.

    openssl rand -hex 32 | npx wrangler secret put FENNEC_TOKEN
npx wrangler deploy
curl -X POST https://my-fennec.<account>.workers.dev/t/acme/query \
  -H "Authorization: Bearer $TOKEN" -d '{"sql": "collections"}'
  • The Worker is the access layer. The server's scoped tokens and rules (HTTP security) are a server's; in a Worker, what a caller may run is its own code. One that runs whatever FennecQL it is sent gives every holder of its token the whole database, so a page or an app's users get endpoints for what they may do instead, each its statement, as Functions and webhooks writes them.
  • Collation data for scripts the module does not carry is fetched from a URL unless the Worker hands it from its bundle (Limits).
  • Apps anywhere reach the Worker as they would a server: its URL and its token (Functions). Data in Durable Objects and functions on Vercel or Lambda make a stack with no server in it.
  • Servers in several regions take one URL through a Worker in front of them, which sends each tenant's requests to its region: the global entry.

Cloudflare Containers is not a home for the server: its disk is ephemeral, and an instance that sleeps starts again from the image. Persistence there would be R2 mounted as files, which this page's rule excludes.

Functions: clients from anywhere

Vercel, Netlify, AWS Lambda, Cloud Run, Cloud Functions, Azure Functions and Deno Deploy keep no disk a database can live on (below), so a function there is a client: of a fennec-server on a platform above, or of a Worker holding the databases in Durable Objects (above). Every client is HTTP, so a function has no connection pool to run out of, and the JavaScript one, @fennecdb/web/client, needs fetch alone, so it runs in Node, Bun, Deno and the edge runtimes as it is.

import { connect } from '@fennecdb/web/client';   // the builder and the HTTP client, no WebAssembly

// Once an instance, outside the handler: the calls after the first reuse it.
const db = connect(process.env.FENNEC_URL, {
  token: process.env.FENNEC_TOKEN,
  timeout: 5000,   // ms to an answer's head, under the function's own limit
});

export async function POST(req) {
  const { id, title } = await req.json();
  // A retried invocation sends the write again: the key makes it once.
  await db.withIdempotencyKey(`note-${id}`).from('notes').insert({ title });
  return Response.json({ ok: true });
}
  • Made once an instance. Python's Client, Go's fennecdb.New and .NET's FennecClient too: at module scope, in Lambda's init phase, not in the handler.
  • Bounded under the function's limit. A client bounds every request in time (timeout, 30 s unless given) and sends one again only where it cannot have run or may run twice: a read, or a write carrying an idempotency key (Retrying a write). Set the timeout under the platform's, so the function answers rather than being cut off mid-wait.
  • A platform's retry is a second write. Lambda tries an asynchronous invocation again, and a queue delivers a message again; key such writes by the event, its id or the message's, and a server answers the second as it answered the first.
  • Private addresses. A function reaching a server's private address needs the platform's VPC attachment (a Lambda in the VPC, Cloud Run's Direct VPC egress, Azure's VNet integration); one without it is given an HTTPS address and the token. A Worker needs neither.

These run your apps and functions, which are clients of a server elsewhere or of a Worker (Functions, below). None gives a process a block disk it keeps.

Using it from your apps

Every app needs two values, the server's URL and its token, from its platform's environment and secret store, as FENNEC_URL and FENNEC_TOKEN say:

import os
from fennecdb import Client
db = Client(os.environ["FENNEC_URL"], token=os.environ["FENNEC_TOKEN"])
import { connect } from "@fennecdb/web/client";
const db = connect(process.env.FENNEC_URL, { token: process.env.FENNEC_TOKEN });

Go is fennecdb.New(url, fennecdb.WithToken(token)), .NET new FennecClient(url, new() { Token = token }), and Swift, Kotlin and Dart Fennec.connect(url, token: ...); Your language has each in full, and Mobile and native apps the apps'.

Backups, then more than one server

A disk snapshot is a crash-consistent copy: a fine extra, not the backup. fennec backup takes the running database whole through the replication stream, and fennec archive keeps the stream for a restore to a moment; give the server --replication-token and run them from anywhere that reaches it.

fennec backup https://db.example.com nightly.fennec --token "$REPL"
fennec archive https://db.example.com /backups/archive --token "$REPL" --image-every 1h --keep 7d

# to the cloud's bucket, beside the archiver
aws s3 sync /backups/archive s3://my-bucket/fennec --delete      # AWS
gcloud storage rsync --recursive /backups/archive gs://my-bucket/fennec   # Google Cloud
azcopy sync /backups/archive "https://acct.blob.core.windows.net/fennec"   # Azure
rclone sync /backups/archive r2:fennec                           # R2, Spaces, B2, ...

Restoring to a moment, and the bucket's side, are on Replication and In object storage.

A server grows two ways. Reads: --replica-of starts a read replica on a second machine, on its own disk, fed from the primary's (Replication; POST /_replication/promote makes it the primary when the first is gone). Writes, many tenants or regions: a database for each tenant behind a router, each a file on a node (Tenants and sharding; Deploying it has the systemd kit and runbook, and the global entry one URL across regions). Neither is a second process over the same file.
